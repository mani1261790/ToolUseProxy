# ToolUseProxy 現行研究方針

この文書は、2026-08-12時点のToolUseProxyの研究目的、検知モデル、評価方法、実装境界をまとめる正本です。日々の作業順序は[実装タスク](../運用/実装タスク.md)、個別設計は[アーキテクチャ](../設計/アーキテクチャ.md)から参照してください。

## 研究目的

AI coding agentは、local file、tool output、会話contextを組み合わせて作業します。そのため、API keyのように形式が決まったsecretだけでなく、未公開コード、研究計画、設計判断、Git diffなど「由来によってprivateになる情報」も外部へ送られる可能性があります。

ToolUseProxyの目的は、protected source由来の情報が外部sinkへ送られる直前に、localで検知・説明し、十分な根拠がある場合に実行前停止へ接続することです。

成功条件は情報流graphを作ることではありません。次の値を改善できるかで判断します。

- 外部流出の検出recall
- 誤停止の少なさ
- 実行前に止められる割合
- 利用者が判断できる説明可能性
- protected valueの追加露出が0であること
- Hook latencyとlocal保存量

## 中心仮説

研究方針は`Sink-first, provenance-assisted`です。

```text
外部sinkを特定する
  -> 実際の送信payloadを解決する
  -> protected sourceと比較する
  -> 直接比較だけでは不足する場合にprovenanceを加える
  -> 根拠に応じてallow / review / denyを判断する
```

外部流出の最終境界はHTTP request、MCP call、Web search、Git push、file upload、final answerなどのsinkです。途中の全経路を完全に再構成できなくても、実payloadにprotected valueが存在すれば止められます。一方、`curl --data @file`や`git push`のようにtool inputへ本文が現れない場合は、payload resolverやprovenanceが必要です。

## 2つの漏えい検知

### 1. 内容対応による直接検知

protected sourceを型とselectorに基づいてchunk化し、sink payloadとの対応を調べます。

| protected source | 主な比較方法 |
| --- | --- |
| token、password、credential | exact、canonical、encoding、selector |
| JSON、設定値、PII | structured field、canonical、substring |
| 非公開文書、研究ノート | chunk lexical、将来のlocal semantic |
| source code、Git diff | token、identifier、code feature、将来のlocal semantic |
| file、archive、Git publish | payload / objectの解決後にcontent comparison |

現在の実行前blockへ使う強い証拠は、実payloadへ構造的に接続したexact / exact-substringが中心です。semantic similarityは内容対応の候補にはなりますが、情報が因果的に流れた証明ではないため、独立評価なしに単独blockへ使いません。

### 2. provenanceと外部性による検知

Codexから観測できるtool I/O、file operation、resource versionをgraph化し、protected sourceとの内容対応からsource lineageを付けます。そのlineageが外部sink候補へ到達したかを調べます。

```text
protected source
  -> file read / tool output
  -> transformation / generated file
  -> sink payload
```

このgraphはLLM内部の完全なtaint trackingではありません。観測できた構造edgeと内容対応から作るprovenance推定です。説明では次を区別します。

- `observed_transfer`: file operationやtool use IDで確認した移動
- `content_correspondence`: exact、substring、lexical similarityで確認した対応
- `inferred_influence`: semantic similarityなどから推定した影響
- `unobserved_internal_transformation`: Hookから見えないLLM内部変換

## 外部通信可能性の判定

漏えい判定には、「protected flowがあるか」と「そのcallが外部へ出る可能性があるか」の両方が必要です。この2つを一つのLLM判断へ混ぜません。

外部性は次の順序で判定します。

1. tool固有adapterで既知sinkを構造化する
2. shellとworkspace内scriptを実行せず、bounded static analysisする
3. それでも不明なら`unknown`として扱う
4. protected flowがunknownへ到達した場合は、分類を待たず実行前denyする
5. public-only unknownは止めず、値非保持の構造要約をlocal queueへ保存できる
6. 明示実行されたHook外workerが、jobごとのfresh Codex sessionで分類する
7. 人間が確認した完全一致ruleだけをworkspaceへ昇格する

Externality Judgeが扱うのは、tool family、capability、segment数、dynamic codeの有無などclosed enumとbounded countだけです。raw command、argument、source code、URL、host、path、credential、protected valueは渡しません。

workerは`codex exec --ephemeral`をread-only、Hook / Plugin / shell / browser / MCP無効で起動します。ToolUseProxyはOpenAI APIを直接呼ばず、API keyを受け取りません。providerは`off`または`codex`だけで、fallbackやsilent selectionはありません。

LLM結果は自動昇格しません。`local`と分類されたruleを人間が承認しても、解除できるのは同じworkspace・同じrevision・同じ構造の保守的unknownだけです。既存adapterやstatic analysisによるblockを弱めることはできません。

詳細設計は[Externality Judge](../設計/ExternalityJudge.md)、段階導入は[Externality Protectionロードマップ](../運用/ExternalityProtectionRoadmap.md)を参照してください。

## Codex network sandbox / proxyとの関係

Codexのnetwork sandbox / proxyは、local commandのnetwork accessを広く制御する重要な境界です。しかし、2026-08-11の実機調査では、一般Pluginが利用できる安定した実行前callbackとtool use単位の厳密joinを確認できませんでした。

OTLPの`codex.network_proxy.policy_decision`は合成runで3 / 3観測できましたが、実行後の非同期eventであり、tool useとの厳密joinは0 / 3でした。同じendpointには値を含み得る他eventも届きます。そのため現在はevaluation-onlyであり、productionのallow / denyには接続しません。

これはnetwork sandbox / proxyが役に立たないという意味ではありません。Codex側に安定した実行前decision callbackが提供された場合、adapter分類とのdifferential evaluationと、外部性の強い証拠として再評価します。過去の調査経緯とnegative resultは[履歴資料](../履歴/調査/NetworkEgress観測とAudit改善計画.md)に保存しています。

## 現在のpolicy

実行前actionは、外部性だけでなくprotected flowの有無と証拠強度を組み合わせます。

| 外部性 | protected flow | 現在の扱い |
| --- | --- | --- |
| 既知external / static risk | あり | opt-in workspaceでdeny |
| 初見unknown | あり | 分類を待たず保守的にdeny |
| 初見unknown | なし | allowし、設定時だけ値非保持queueへ記録 |
| 人間承認済みlocal rule | あり | 同一構造のunknownだけ解除可能 |
| hosted / Hook非可視 | 不明 | 保護済みと表示しない |

runtime DBが未初期化、破損、未知schemaの場合には既存のdiagnostic / fail-open境界が残ります。このため数学的な偽陰性ゼロとは表現しません。

## 評価計画

評価caseは`Source × Transformation × Boundary × Sink`で整理します。

- Source: credential、structured secret、private prose、code / diff、分析結果
- Transformation: copy、encoding、file、archive、paraphrase、translation、summary、aggregation、split
- Boundary: same task、resumed task、compaction、subagent、branch / worktree、別clone、Plugin update
- Sink: HTTP、MCP、Web search、final answer、upload、Git push

比較する方式は次の4つです。

1. direct lexical
2. resolved payload
3. local semanticを加えたobserve-only評価
4. lineage-assisted

主な指標はpayload extraction recall、externality recall、leak precision / recall、false block、policy action accuracy、raw exposure、Hook p50 / p95、lineageの追加改善量です。合成corpusはdevelopment / validationを分け、private holdoutはrepository外でaggregate-only評価します。

既存の比較設計とbaselineは[Sink中心の情報流評価計画](../調査/Sink中心の情報流評価計画.md)、再現手順は[Sink-first比較評価](../運用/Sink-first比較評価.md)にあります。

## 現在の証拠

- 類似度profile v2.1のversioned synthetic corpusでは、固定gate上のprecision / recall / F1、candidate recall、E2E actionが1.0、false blockとprivacy exposureが0
- file-backed benchmark v1.1では、direct end-to-end recall 0.333に対し、bounded resolver追加後は0.667、precision 1.0、payload resolution 4 / 4
- Desktop fresh runでは、public side effect 1、protected side effect 0、exact block 1、raw exposure 0、setup承認2回
- Externality Judgeの実Codex capability probeでは、固定value-free envelopeに対してlocal 5,208 ms、risk 4,511 msでschema contractを満たした

これらは限られた合成・手動caseの結果です。実project全体の精度、任意programのexternality、cross-platform動作を証明しません。

## 直近の研究課題

1. isolated dogfoodでpublic local、public unknown、protected unknown、static externalを同一条件で検証する
2. Hook内network 0、raw exposure 0、既存block downgrade 0をfresh Plugin dataで確認する
3. 人間review済みruleのrevision、workspace、receiptのstale拒否を実E2Eで確認する
4. 低riskな実project pilotでfalse blockとunknown分布を値非保持で測る
5. Git pushのoutgoing object、hosted tool、session境界を個別評価する
6. local semanticがdirect / resolved / lineageへ追加する価値をobserve-onlyで測る

作業順序とrelease gateは[実装タスク](../運用/実装タスク.md)を参照してください。

## 非目標と保証しないこと

- LLM内部の完全な情報流追跡
- 類似度だけによる因果関係の証明
- LLM verdictの自動承認
- runtimeでの任意tool input書換え
- system-wideな通信傍受やTLS MITM
- hosted tool内部通信の完全観測
- Codex外のterminal、IDE、Git GUIの遮断
- 現段階での数学的な偽陰性ゼロ
