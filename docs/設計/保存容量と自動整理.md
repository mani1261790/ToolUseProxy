# 保存容量と自動整理

更新日: 2026-09-07

## 目的

ToolUseProxyは、操作の入力・出力、検出用の断片、情報のつながり、類似照合用の検索データをローカルDBへ保存します。従来は自動整理がなく、更新前DBの退避も残り続けるため、通常利用と試験を重ねるほど保存領域が増えていました。

この対策では、検出を弱めず、改善用の記録や利用者設定を失わず、詳しい操作記録だけを合意済みの期間で整理します。実データへ最初に適用するときは、変更前の計画を表示し、利用者の確認後だけ変更します。

## 保存するデータの分類

| 分類 | 例 | 方針 |
| --- | --- | --- |
| 詳しい操作記録 | Hookの入力・出力、解析対象、断片、情報のつながり、停止記録 | 30日保持 |
| 再作成できる検出データ | 完全一致索引、類似照合用索引、実行中解析状態 | 30日保持を上限とし、必要に応じて再作成 |
| 改善用フィードバック | 操作評価、自動比較、問題分類、Issueとの対応 | 今回は削除しない |
| 長期設定 | project設定、保護対象登録、利用者判断 | 削除しない |
| 更新前DB | schema更新前の復旧用退避 | 新版確認済み・7日経過・DB検査合格後に整理 |

将来、改善用フィードバックの元になった詳しい記録を30日より長く保持する場合は、Issue作成と対応番号保存が完了した時点を保持解除条件にします。この条件の実装は今回の容量対策から分離します。

## 容量の境界

- 2 GiBを超えたら注意状態を記録する
- 4 GiBを超えたら整理が必要な状態を記録する
- 30日以内の詳しい操作記録は、容量だけを理由に削除しない
- 容量を理由に記録機能や保護機能を自動停止しない
- 4 GiBを超えたまま安全に整理できない場合だけ利用者へ知らせる

## 変更前の確認

`storage cleanup plan`はDBを読み取り専用で調べ、次を本文非表示で返します。

- DB、更新前退避、分類ごとの使用量
- 更新前退避のうち、7日を過ぎて削除できる件数と容量、待機中・未確認・改変疑いの件数
- 30日前の完全なセッション数と、途中で終わったセッション数
- セッション番号のない古い操作数
- 表ごとの削除候補行数
- 回収できる容量の見込み
- DBを安全に作り直すための一時空き容量
- 改善用記録、設定、保護対象登録、利用者判断、元ファイルを残すこと
- 計画後のDB変更を検出する確認番号

計画は保護リストや保護対象ファイルを読みません。絶対path、保存本文、接続先も表示しません。大きいDBでは全ページの分類に時間がかかるため、Hook内では実行しません。

実行環境のSQLiteがページ別容量の計測に対応していない場合も、30日基準の削除候補は表示します。その場合だけ、分類ごとの容量と回収見込みを「取得不可」とし、候補件数や維持対象を隠しません。確認番号にはDB本体だけでなく、未統合の追記領域（WAL）の容量も含めます。

## 自動整理

自動整理は初期状態では無効です。実データについて`storage cleanup plan`を表示し、利用者がその計画を確認した後に限り、同じ境界時刻と確認番号を指定して有効にします。一度有効にした後は、通常のタスク終了時にHookが小さな予約ファイルを作り、待たずに終了します。容量計測、削除、DB縮小はHookとは別の処理が行います。

別処理は、前回の開始から24時間に1回まで、1回20作業単位を上限に整理します。日付が変わっただけでは再実行しません。DB使用中、別の整理処理中、監視処理が直前に動いた場合は何も削除せず延期し、5分を過ぎた次のタスク終了後に再試行できます。DB縮小中に監視処理が始まった場合も縮小を中断し、通常の記録と保護を優先します。

SQLiteのDB縮小は、一時領域を使ってDB全体を作り直す`VACUUM`を使います。必要な空き容量がない場合は行削除後のDBをそのまま維持し、縮小だけを延期します。SQLiteの処理が完了する前に中断されても、作り直し前または完了後の整合したDBを維持します。完了後には未統合の追記領域を整理し、DB簡易検査を行います。

正常終了は利用者へ通知しません。失敗、整理後も4 GiB以上、DB縮小用の空き容量不足だけを次のタスク開始時に1回通知します。未読の通知は、後の正常終了で消しません。`status`と`storage cleanup auto status`では、前回の開始・完了・延期時刻、削除件数、残件数、回収容量、延期理由、次回実行可能時刻を本文非表示で確認できます。

管理命令は次の4つです。

```sh
sh "<PLUGIN_ROOT>/hooks/run_cli.sh" storage cleanup auto status \
  --data-dir "<PLUGIN_DATA>" --json
sh "<PLUGIN_ROOT>/hooks/run_cli.sh" storage cleanup auto enable \
  --cutoff-at "<PLAN_CUTOFF_AT>" \
  --plan-revision "<PLAN_REVISION>" \
  --data-dir "<PLUGIN_DATA>" --json
sh "<PLUGIN_ROOT>/hooks/run_cli.sh" storage cleanup auto disable \
  --data-dir "<PLUGIN_DATA>" --json
```

`auto run`は予約後の別処理が使う内部向け命令です。手動実行しても、有効化確認、24時間制限、使用中判定、1回の上限を迂回しません。これらの正規のローカル管理命令はToolUseProxy自身の外部操作判定で止めません。不正な引数、別の保存領域、追加のshell命令を同じ扱いにはしません。

削除はセッション単位で行い、1つのセッションの途中だけを消しません。関連する解析対象、断片、索引、判断、snapshotを同じ計画へ束ねます。

## 30日を過ぎた記録の削除契約

`storage cleanup apply`は、直前に表示した`cutoff_at`と`plan_revision`を両方指定した場合だけ動きます。計画後に別の記録が追加・更新されていれば、何も消さずに`storage_plan_changed`で終了します。

1回に扱うのは既定20作業単位、最大100作業単位です。古い順に少量ずつ削除し、結果に含まれる次の確認番号を使って続きを実行できます。途中で処理が止まっても、1回分は全て反映されるか、全て元に戻るかのどちらかです。

削除可否は、開始・終了の時刻だけではなく、その作業に属する操作、解析対象、断片、操作結果、資源の状態、情報のつながり、解析結果、送信前編集計画の最終時刻まで見て決めます。いずれかが境界時刻以降なら、その作業全体を残します。時刻を解釈できない記録も残します。

終了記録がない古い作業も、保留中の解析や送信前編集がなければ、作業全体を一つの単位として削除できます。反対に、解析が未完了、または送信前編集が確認待ちの作業は削除せず、計画に件数だけ表示します。

削除時は、次を同じ処理内で整理します。

- 操作の入力・出力と、それから取り出した解析対象・断片
- 操作結果と、その時点で確認したファイル等の状態
- その作業だけに属する情報のつながり、解析結果、機械判定
- 完全一致検索と類似検索の対応情報
- どこからも参照されなくなった共通本文と類似検索用特徴

別の新しい作業から古い断片が直接参照されている場合は、その古い作業全体も残します。複数の作業から使われている共通本文・特徴・解析snapshotも残します。改善用フィードバック、利用者による評価、project設定、保護対象登録、保護対象の分割情報は削除対象の問い合わせにも含めません。作業をまたぐ全体解析のsnapshotは、別の解析結果から参照されている限り残します。

適用後は外部キー検査とDB簡易検査を行います。どちらかが失敗すれば、その回の削除を全て元に戻します。通常のHook処理からこの削除を直接実行することはありません。

開発用の人工DBでは、30日境界、途中終了、保留中処理、直前の同時書込み、処理途中の失敗、複数作業から共有される本文、削除後の完全一致検出を確認します。利用者の実DBへ最初に適用するのは#159で、表示した計画を利用者が確認した後だけです。

## 更新前DBの退避を整理する条件

DBの仕組みを更新する前には、元のDB全体を復旧用として退避します。退避を作った時点で、作成時刻、更新前と更新後のDB形式番号、ToolUseProxy版、ファイルの同一性を専用の管理記録へ保存します。DB本文、操作内容、保護対象の値はこの管理記録へ入れません。

退避は、次の条件を全て満たす場合だけ削除候補になります。

1. 更新後のToolUseProxyが、現在のタスクで監視処理まで届いたことを`setup verify`で確認済み
2. 退避作成時刻と新版確認時刻の遅い方から7日以上経過
3. 現在のDBが現行形式で、簡易整合性検査に合格
4. 新しく作られた未確認の退避や、作成後に変わった退避が一つもない
5. 変更前計画に含めた退避一覧が、削除直前にも同一

旧版が作った管理記録のない退避は、現行版の監視処理を確認するまで削除しません。確認できた場合も、ファイルの更新時刻を作成時刻として安全側に採用し、そこから7日間残します。`setup verify`を繰り返しても、同じ現在DBについて最初に確認した時刻は後ろへずらしません。

削除は1回20件までです。1件消すごとに管理記録を確定するため、途中で止まっても残りを次回続行できます。途中失敗、DB検査失敗、未確認、期限前、ファイルの入れ替わりを検出した場合は、それ以降を削除しません。現在DBそのものは退避整理の対象にせず、整理後にも現行形式の確認と簡易整合性検査を行います。

## 維持する安全条件

- 30日以内の記録を容量だけで削除しない
- 改善用フィードバック、設定、保護対象登録、利用者判断を今回削除しない
- 計画後にDBが変わった場合は適用しない
- 整理失敗時は元DBを維持する
- Hook内で大規模な計測、削除、DB縮小を行わない
- 保護リストと保護対象ファイルを容量計測のために読まない
- raw本文、絶対path、接続先を画面、Issue、CI成果物へ出さない
