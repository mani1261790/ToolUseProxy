# SQLiteによる動的プロパティグラフ

保存先は既存のevents.db。原記録とグラフは同一ファイルの別テーブルに保持する。
ToolCallをノードとし、実行前後は同じノードの観測版として扱う。原記録はイベントIDで参照する。

## 来歴と保護指定の分離

判定モデルには保護一覧を渡さない。モデルは過去の完了ToolCallへの依存と、
読み書き対象のworkspace相対パス・根拠を返す。直接ファイルを送信する操作もread属性を持つ。
プロパティは観測からの推定であり、OSレベルの実アクセス証明ではない。

保護指定はprotected_sourcesを維持する。whole_file指定は、記録開始以降に当該パスから取得した
情報を対象とする。特定内容版の同一性は主張しない。selector指定や対象パスを解決できない場合は
不完全な判定となる。別名、symlink、未観測のcwdを推測して同一視しない。

後から保護指定を追加した場合、最新の取得属性を索引検索して起点を決め、既存辺を逆向きにたどる。
来歴の判定キャッシュに保護一覧は含めない。記録が同じならモデル再実行なしで起点だけを更新する。
不足している来歴は外部通信時に解析する。登録操作自体ではモデルや検証送信を起動しない。

## 保存構造

- graph_revisions: 観測・モデル・prompt版・根拠全体hashで識別する判定版。上書きしない。
- graph_heads: workspace/session別の各ノードの現在版。
- graph_edges: 判定版ごとの情報依存辺。入辺・出辺の索引を持つ。
- graph_accesses: 判定版ごとのread/write属性と根拠。対象パスの索引を持つ。
- graph_revision_links: その版の判断で参照した依存元の判定版。
- graph_policies / graph_policy_checks: 保護指定のスナップショットと、その版での到達判定。
- graph_progress: 解析対象イベントとanalyzing/ready/incomplete。未完了を依存なしとは扱わない。

モデル呼出中は書込みトランザクションを保持しない。キャッシュと現在版が同じならグラフを書き直さない。
最後の保護指定読取り・到達判定・監査記録は同じDBの書込みトランザクションで確定する。
過去の判定結果と根拠は、新しい版の判定によって消さない。

## 性能確認と範囲

`python -m scripts.benchmark_property_graph`は10,000/100,000ノードの人工的な一本の経路で、
差分更新・取得対象検索・祖先探索を測る。LLM、原記録の読み戻し、UI並行読取りは含まない。
今回のローカル計測では10万ノードの全経路探索0.66秒、取得対象の検索0.11ms、
1ノード・1辺の追加commit約1.1ms。一般的な性能保証ではない。

実行時の履歴読取り上限500イベント・256KBはまだ維持する。10万ToolCallの実利用が完了したという
意味ではない。全文検索による候補絞込み、別セッションへの来歴引継ぎ、UIのグラフ画面、
イベント記録との同時負荷試験は別途必要。候補検索で見つからないことを根拠に許可しない。

旧semantic_flow_nodes/edgesは破壊せず保持するが、現在の詳細判定はproperty_graphを使う。
判定結果は既存semantic_flow_decisionsにも記録し、現行ログUIとblock絞込みを維持する。

## 実モデルによる架空ログの確認

直接送信block（37.39秒、初回履歴解析込み）、派生送信block（10.83秒）、無関係な送信allow（11.33秒）。
git addのケースは期待allowに対してunavailable（15.78秒）となり、probeは不一致で終了した。
成功として数えず、実行環境の情報不足を解決する評価課題として残す。送信コマンド自体は実行していない。

## 履歴処理の追加効率化（2026-09-22）

履歴の判定キャッシュキーを連鎖ハッシュに変更した。前の履歴のハッシュと今回の観測、
確定した判定を次に引き継ぐ。毎回それまでの全文をJSON化してハッシュする処理をなくし、
ハッシュ対象の総量を履歴量に比例させた。モデルに渡す証拠は削らない。
途中の出力が変わればそのノード以降、モデルが変われば全体を判定し直す。
保護対象だけの変更では辺の判定を再利用して到達可能性を計算する。
旧形式のキャッシュは保持するが、新形式への切替後の初回は再判定になる。

確定済みノードIDの集合も追記で維持し、毎回全履歴を走査して作り直さない。
解析ループのDB接続は一つを再利用する。各書込みはモデル呼出前にcommitし、
モデルを待っている間に書込みロックを保持しない。接続は例外時も閉じる。

人工データ（各ノードの入出力各300文字）のローカル単発測定では、
ハッシュ処理のみで100ノード24.43ms→1.95ms、400ノード465.71ms→4.30msだった。
これはLLM待ち時間、DB、UI、Hook全体の速度の測定ではない。
テストでは履歴40→80ノードでハッシュ入力総量が約2倍になること、
再実行でモデル呼出0回、1ノード追加で1回、途中の観測変更で後続だけ再判定することを確認した。
モデル待機中に別DB接続が書込みロックを取得できることも確認した。

候補だけを切り出して判断を打ち切る方式は採用していない。
古いファイル生成記録だけ拾い、間にある上書き操作を落とすと、許可だけでなくblockも誤り得る。
安全な候補削減には、未解析操作・上書き・対象の同一性を含む証拠の範囲を確立する必要がある。
現時点では全文の判定材料を保ち、候補がないことを安全の根拠にしない。

### git addの未確定をどう読むか

架空の `git add public.txt` を実モデルの外部通信判定に単独で渡した再確認では、
unknown / complete=falseとなった。理由はシェルの別名やGitのフィルター・フック・fsmonitorが
外部通信するか確認できないためだった。これは以前の詳細判定の内部理由そのものを復元したものではなく、
同じコマンドに対する新しい外部通信判定の結果である。
秘密の内容を送った証拠が見つかったという意味ではない。
現在のallow_with_warningでは未確定やタイムアウトは警告して継続し、blockにはしない。
したがって未確定を減らす課題は残るし、未確定の操作まで流出を防げるとは言えない。
実際のCodex Hookからの操作・受信先を伴う検証は今回実施していない。

## 標準操作と未観測の可能性を区別する（2026-09-22）

旧externality-first-v1の指示は、git addだけではlocalにせず、未確認の別名・Git追加設定も
考慮するよう明示していた。そのため通常の操作までunknownになっていた。
externality-first-v2 / property-flow-v3では、記録された操作と標準的なコマンドの意味から
通信を分類する。存在するか分からない追加設定やバイナリ置換を想像してunknownにはしない。
外部通信の事前判定と詳細グラフ判定に同じ通信規則を適用し、キャッシュ版も更新する。

通常のgit add/status/diffはlocal、push/fetch/pullやHTTP送信はexternalと判断する。
ただし文字列の先頭だけで分類せず、連結コマンド、コマンド置換、明示された追加設定や
記録されたスクリプトを含めてモデルが判断する。ハードコードしたgit addの無条件許可ではない。
未知の自作スクリプト本体など、具体的に必要な情報が欠ける場合はunknownを残し、
理由に不足する証拠を記す。unknownを機械的にlocalへ置換しない。

これは記録に基づく意味判定の範囲を定める変更であり、OSの通信禁止ではない。
実環境のGit設定やシェル設定を収集・検証する処理は追加していない。
記録に現れないカスタマイズを検出する保証はなく、モデルにも誤判定の可能性はある。
未知の自作スクリプトを追加証拠で解決する仕組みは今後の課題。

`scripts/probe_externality.py`は実モデルへ架空のコマンド文字列を渡し、
通常のadd/status、push、連結送信、コマンド置換、明示した送信フィルター、
内容未提示のスクリプトの7条件を確認する。コマンドそのものは実行しない。
既存の`scripts/probe_semantic_flow.py`では直接・派生・無関係な送信とgit addを確認する。

今回の実モデル確認では7条件が期待どおりだった。詳細グラフの架空ログも、
直接送信block（34.54秒）、派生送信block（10.98秒）、無関係な送信allow（11.20秒）、
git add allow（11.17秒）となった。初回は過去ノード解析を含み、事前判定を通さず
詳細判定を直接呼んだ測定である。実Hookや実受信先を伴う動作証明ではない。
