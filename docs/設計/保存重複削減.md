# 保存内容の重複削減

更新日: 2026-09-07

## 対象

Issue #155では、検出に必要な本文を失わず、同じ本文と類似検索用の特徴を何度も保存する構造を見直します。操作時の元記録、改善用フィードバック、保護対象登録、利用者設定は削除しません。

## schema v12

`artifact_contents`は、本文のSHA-256ごとに本文、正規化本文、token数を1行だけ保存します。`artifacts`と`artifact_fragments`は本文を持たず、このSHA-256を参照します。従来と同じ`ArtifactRecord`と`ArtifactFragment`を返すときは共通表を結合するため、検出処理から見える値は変わりません。

同じSHA-256に異なる本文、正規化本文、token数が渡された場合は上書きせず、記録全体を失敗させます。旧DBの移行でも同じ不一致検査を行います。

類似検索の特徴は、従来の「作業領域・セッション・断片・特徴」の組ではなく、`content_similarity_features`へ「比較方式の版・本文SHA-256・特徴」の組として1回だけ保存します。どのセッションのどの断片か、実行順、完全一致用のkeyは、小さい`fragment_exact_index`に維持します。同じ本文が複数回現れても、特徴の本体は増えません。比較方式を更新した場合は旧版と混ぜず、現在の版だけを候補検索に使います。

## 移行と復旧

schema v11からの移行は、Hookでは実行しません。明示的な`init`または`setup apply`が先にSQLite backup APIで旧DB全体を退避し、その後1つのtransactionで次を行います。

1. 旧artifactとfragmentの本文を`artifact_contents`へ重複なしでコピーする
2. 全参照が同じ本文へ戻ることを検査する
3. 本文を持たないartifactとfragment表へ切り替える
4. 再作成可能な実行中解析表を空で作り直す
5. schema検査後にv12として確定する

途中で失敗した場合はtransaction全体を戻し、v11の表と本文を維持します。更新前DBの退避も残します。実DBへの初回移行と圧縮はIssue #159で変更前計画を再表示し、利用者の明示確認後にだけ行います。

Issue #159の実作業では、現行の`storage cleanup plan`がv12だけを受け付けてv11を安全停止したため、この順序を実行できませんでした。更新前DB全体を残してv12へ移行した後に、削除を伴わない計画を表示しています。データ削除はありませんが、移行前確認を満たしたことにはしません。旧形式のまま移行前計画を表示し、確認番号を移行へ結び付ける不足はIssue #169で修正します。

再作成可能な類似検索表を空にしても、元のevent、artifact、fragmentは残ります。次の対象セッションの解析時に、そのセッションの小さい対応表と、必要な本文の特徴だけを再作成します。30日を過ぎた操作記録の削除と、参照されなくなった共通本文・特徴の削除はIssue #156で扱います。

## 維持する条件

- 公開APIが返すartifactとfragmentの本文、hash、正規化本文、token数を変えない
- 完全一致、類似候補、情報のつながり、停止判定を弱めない
- 改善用フィードバック、長期設定、保護対象登録を移行対象にしない
- Hookはschema不足を安全側で拒否し、大規模移行を始めない
- 移行前backupの検査と、移行後のschema検査を省略しない
- 保護リストと保護対象ファイルを容量削減のために読まない
