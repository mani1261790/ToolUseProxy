# ToolCall記録から作る意味依存グラフ

2026-09-22。既存のI/O類似度・スコア伝播を置き換えるための初期実装。
現在のPlugin設定・保護登録・実利用DBは変更していない。

## 調査結果

- ローカルのCodex CLIは0.153.4。`codex exec --help`で、非対話実行、JSON Schemaによる出力指定、独立した一時セッション、ユーザー設定を読まない実行を確認した。
- [公式Hook仕様](https://developers.openai.com/codex/hooks)では、`prompt`／`agent`型は読み取られても実行されない。親Codexの現在の推論に直接問い合わせる公開Hook機構としては使えない。
- コマンド型Hookから独立した`codex exec`を起動し、終了まで待って判定結果を返す構成を採用する。[非対話実行と構造化出力](https://developers.openai.com/codex/noninteractive)に沿う。
- Hookの時間制限は設定可能。現在の7秒はToolUseProxy側watchdogの設定であり、モデルを呼べないというCodexの制約ではない。
- MCP型Hookは接続済みMCPの呼出しであり、親モデルへ推論を委任する機能とは異なる。非同期Hookでは、すでに始まったToolCallを実行前に止められないため、送信のゲートには同期処理を使う。

判定用Codexは別セッションであり、親の会話を暗黙に参照しない。必要な記録を明示して渡す。
既存の外部分類用ランナーを再利用し、判定用セッションではツール・Hook・Plugin等を無効にした空ディレクトリで実行する。親の設定には手を加えない。JSONLにツール活動が出た判定は採用しない。

## 処理

1. 既存の`events.db`へ入力を記録し、ToolCallノードを作る。判定前にもノードを保存する。
2. 登録済み情報源を根とし、同一workspace・sessionの過去のToolCallと実行結果をLLMへ渡す。
3. LLMは「内容の依存元」と「今回の外部通信の可能性」を返す。許可／遮断は返させない。
4. 外部通信があると判断された呼出しについて依存エッジを逆向きに探索し、登録情報源へ到達すればblockする。スコアやI/O類似度の閾値は使わない。
5. PostToolUseの実出力で同じノードを更新する。実行前の判断に未来の出力を混ぜない。
6. モデル・プロンプト・履歴・情報源の組合せが同じ判定だけ再利用する。変更された出力や情報源に基づく古い判定は再利用しない。

`semantic_flow_nodes`、`semantic_flow_edges`、`semantic_flow_decisions`を既存DBへ追加する。元のイベントを消さず、旧グラフとは分ける。ネットワーク待機中はSQLiteの書込transactionを保持しない。同じworkspace・sessionの解析は別のプロセスロックで直列化する。

## 許可・遮断・未判定

- 外部通信＋保護情報源への依存経路：block。
- ローカル操作、または判定が完了し保護情報源への経路を観測しなかった外部操作：このHookでは遮断しない。
- タイムアウト、壊れたモデル応答、履歴の不足・サイズ超過、意味判断の不足：unavailable。流出検出とは扱わない。

この実装で選択できる障害時方針は、明示設定された`allow_with_warning`。未判定のまま操作を通すので、障害時の流出防止を保証しない。名前だけを「保留」にしてdenyを返すことはしない。Codex本体の承認条件を上書きする`permissionDecision: allow`も返さない。

新経路では旧I/O類似度判定・予測による追加停止を実行しない。通常の旧経路は明示切替されるまで従来どおり。管理者による停止の処理は既存Plugin入口で先に行う。

## 初期実装の利用条件

この段階では実利用への一括移行を行わない。明示的に選択したworkspaceだけを対象とする。
`events.db`と同じディレクトリに次の`semantic-flow.json`を置く。

```json
{
  "workspaces": {
    "対象のworkspace_id": {
      "mode": "enforce",
      "provider": "codex_exec",
      "model": null,
      "send_recorded_content": true,
      "failure_policy": "allow_with_warning"
    }
  }
}
```

- `send_recorded_content`は、指定モデルへToolCallの入力・出力と情報源登録メタデータを送る選択。ローカルのみの旧設定と同じ意味ではない。秘密情報を含み得るので、送信先の利用条件を決めてから有効にする。今回の実験は人工データだけ。
- modelがnullなら独立したCodexの既定モデルを使う。CLIの保存済み認証を使い、親セッションのモデル設定を引き継ぐとは限らない。
- 登録元ファイルをこの経路が開き直すことはしない。DBに登録済みのworkspace別情報源を使う。
- `hooks/semantic-flow.example.json`は切替用の例。通常のHookと二重登録しない。環境変数`TOOLUSEPROXY_SEMANTIC_FLOW=1`により新経路を選ぶ。現在のインストールには適用していない。
- 判定1回は60秒まで、解析の追加依頼受付は480秒まで、セッションロック待機120秒、外側watchdog720秒、ホスト設定900秒。時間切れは新経路ではdenyに変換しない。これらは最適化済みの応答性能ではない。
- ロック実装はPOSIX向け。Windowsでの新経路の検証・ロック実装は残件。

## 検証

`python3 -m scripts.probe_semantic_flow`は新規の一時DBだけを作り、架空の記録を実モデルへ渡す。記録中のcurlやgitは実行しない。

2026-09-22の実行結果（固定された小さな人工例、精度評価ではない）：

| 入力例 | 実モデル＋経路探索の結果 | 経路のノード数 | 時間 |
| --- | --- | --- | --- |
| 登録ファイルの送信 | block | 2 | 31.94秒（初回履歴解析を含む） |
| その情報を使って書いたファイルの送信 | block | 4 | 8.32秒 |
| 無関係な公開用ファイルの送信 | allow | 0 | 8.11秒 |
| 無関係なファイルのgit add | allow | 0 | 9.26秒 |

別の単発Codex試験ではJSON応答6.83秒、ツール活動なしを確認した。
Hook runnerから新経路への接続、タイムアウトの扱い、ログUIのblockフィルタは人工DBと固定判定器で試験する。これらを、現在のDesktopに新Pluginを導入して実Hookで遮断した証拠とは扱わない。

## 次に確認すること

1. Desktopの実Hookで、人工データを使ってPre→判定モデル→allow/deny→実行有無まで確認する。現在の無効化状態をエージェントが変更しない。
2. 実Gitのcommit・push対象とローカルgit hookの観測を含む評価を増やす。`git add`という文字列だけでローカルと決め打ちする実装ではない。
3. 読んだ後に無関係な文章を書く、部分的な派生、翻訳、計算、複数ファイルを一度に扱う例で、誤検出と見逃しを測る。
4. 初回履歴の解析、毎回のモデル起動、長い履歴のコストを減らす。現在は500イベント／256KBを超える履歴を黙って切らず、未判定にする。
5. プロジェクト間・セッション間で持ち越した派生ファイルの由来を扱う。現在はセッションを越えてエッジをつながない。

## 限界

機械的にたどれるのは、LLMが推定したエッジである。LLMが依存を見落とした場合、探索の正しさだけで検出は救えない。グラフは観測・推定結果であり、情報流の完全な証明ではない。

ToolCall一つで複数の情報源・複数の出力を扱う場合、単一ノードの到達性だけでは、どの出力部分に秘密が移ったかを十分に区別できない。必要に応じてエッジに入出力部分やファイル版の対応を持たせる。I/Oの単純比較へ戻す理由にはしない。

モデルに渡すログ自体に命令が含まれる場合の誤誘導、記録されないshell内の処理、実行直前のファイル差替えも残る。Codex Hookに届かないhosted toolは、この実装でも実行前に遮断できない。
