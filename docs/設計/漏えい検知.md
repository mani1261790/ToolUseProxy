# Leak Detection

ToolUseProxy の第2段階では、source lineage が外部流出候補へ到達したかを判定します。

第1段階の graph は情報の経路を説明します。

```text
source_chunk
  -> artifact_fragment
  -> resource_version
  -> artifact_fragment
```

第2段階の leak detection は、その経路が `sink_candidate` に到達したかを評価します。

```text
source_chunk
  -> artifact_fragment(Search query)
  -> sink_candidate(external_search)
  -> leak finding
```

## 検知対象

現在の実装では、`lineage_assignments` に保存された到達結果を入力にします。

検知条件:

```text
assignment.node_kind = sink_candidate
sink_candidate.sink_type starts with "external_"
assignment.best_path_score >= threshold
```

この条件を満たす assignment を leak finding として出力します。

`final_answer` は外部送信とは別分類です。defaultではfindingに含めません。`--include-final-answer` を指定した場合だけ、`final_answer` sink candidate もfindingに含めます。`local_persistent_log` はまだ検知対象にしていません。

## Finding model

現在は DB table を作らず、CLI 出力として finding を生成します。finding の保存は、検知ルールが安定してから追加します。

```python
@dataclass(frozen=True)
class LeakFinding:
    finding_id: str
    analysis_run_id: str
    source_node_kind: str
    source_node_id: str
    sink_node_id: str
    sink_type: str
    sink_label: str
    severity: str
    path_score: float
    hop_count: int
    predecessor_edge_id: str | None
    reason: str
```

`finding_id` は、同じ analysis run、source、sink の組み合わせから安定生成します。

```text
sha256(
  analysis_run_id + "\0" +
  source_node_kind + "\0" +
  source_node_id + "\0" +
  sink_node_id
)
```

## Severity

現在の severity は path score から決めます。

```text
critical
  external_* sink に到達
  path_score >= 0.90

high
  external_* sink に到達
  path_score >= 0.60

medium
  external_* sink に到達
  path_score >= 0.30

low
  external_* sink に到達
  path_score < 0.30
```

Search adapter が作る `external_search` は外部送信候補として扱います。Search query は外部サービスへ送られるため、初期検知では `external_*` の一種として判定対象に含めます。

今後、sink type ごとの重みを追加できます。

```text
external_message
external_git_publish
external_package_publish
external_deploy
  -> high以上を優先

external_search
external_http_request
external_api_call
external_file_transfer
  -> path_scoreに応じて判定
```

## CLI

実装は `hook_monitor/analysis/leak_detection.py` と `scripts/detect_leaks.py` に分けています。`leak_detection.py` は finding 生成の純粋ロジック、`detect_leaks.py` はDB読み込みとtext / JSON出力を担当します。

基本コマンド:

```bash
python3 scripts/detect_leaks.py --latest
python3 scripts/detect_leaks.py --format json
python3 scripts/detect_leaks.py --min-score 0.3
```

option:

- `--db`
  - SQLite DB path
- `--analysis-run`
  - 対象 analysis run
- `--latest`
  - 最新 completed analysis run を使う
- `--format text|json`
  - 表示形式
- `--min-score`
  - finding として出力する最小 path score
- `--source`
  - source id または source node id で絞り込み
- `--sink-type`
  - `external_search` などで絞り込み
- `--include-final-answer`
  - Codex最終応答の `final_answer` sink candidateをfindingに含める

`--format text` がdefaultです。`--sink-type` は複数回指定できます。

## Text output

text output は、人間がすぐに確認できる形にします。

```text
analysis_run_id=...
detector_version=...
min_score=0.30
findings=1

[HIGH] external_search path_score=0.92 hops=3
source: source_chunk:private-source:0
sink: sink_candidate:<sink_node_id> Search query
reason: source lineage reached external_search sink candidate
trace: python3 scripts/trace_lineage.py --db .tooluseproxy/events.db --node sink_candidate:<sink_node_id>
```

本文 preview は `trace_lineage.py` に任せます。`detect_leaks.py` は finding summary と trace command を出します。

## Path reconstruction

検知自体は `lineage_assignments` の到達結果だけで行います。

詳細な経路表示は `trace_lineage.py` を使います。

```bash
python3 scripts/trace_lineage.py --node sink_candidate:<sink_node_id>
```

`detect_leaks.py` は finding に `sink_node_id` と `predecessor_edge_id` を含めます。詳細な path を JSON に埋め込む処理は追加していません。

## False positive boundary

現在の検知は conservative ではなく、観測された lineage と sink 到達を素直に finding として出します。

誤検知が起こりやすいケース:

- shingle 類似度だけで source lineage がつながった
- source chunk が短すぎる
- Search query が一般語だけを含む
- protected source の path binding が広すぎる

現在の実装では、次の情報を finding に含め、後から評価できるようにしています。

- `path_score`
- `hop_count`
- `predecessor_edge_id`
- `sink_type`
- `source_node_kind`
- `source_node_id`

将来の抑制策:

- source chunk の最小長
- sink type ごとの threshold
- `content_lexical` のみで到達した経路の severity 調整
- allowlist policy
- user confirmation policy

## 非対象

現在は次を扱いません。

- block / warn / redact
- finding DB table への保存
- allowlist / policy engine
- sourceごとの policy tag 判定
- local log の検知
- sink type ごとの詳細な severity tuning

これらは現在の `detect_leaks.py` の上に追加します。

漏えい検知は finding を生成するところまでを担当します。finding を `allow`、`warn`、`redact`、`block` の判断へ変換する処理は [Policy判断](Policy判断.md) で扱います。

## 実装済みの構成

- `hook_monitor/analysis/leak_detection.py`
  - `LeakFinding`
  - `detect_leaks()`
  - `severity_for_score()`
- `scripts/detect_leaks.py`
  - 最新 analysis run の選択
  - `lineage_assignments` と `sink_candidates` の読み込み
  - source / sink type filter
  - `--include-final-answer` によるCodex最終応答finding
  - text / JSON output
  - `trace_lineage.py --node sink_candidate:<id>` への導線

## Tests

実装済みの主なテスト:

- source lineage が `external_search` sink に到達した場合、finding が1件出る
- `--min-score` より低い assignment は出力されない
- sink がない analysis run では finding 0 件になる
- CLI の text output が finding summary と trace command を出す
- CLI の JSON output が parse でき、sink type filter が効く
- `final_answer` はdefaultではfindingに含まれず、`--include-final-answer` でfindingに含まれる
- `--format json` が parse 可能な JSON を返す
- `--sink-type external_search` で絞り込める
- `local_persistent_log` はfindingに含まれない

## Completion criteria

漏えい検知MVPの完了条件:

- `scripts/detect_leaks.py --latest` が実行できる
- source lineage が `external_search` sink へ到達したケースを finding として出力できる
- source lineage が `final_answer` sink へ到達したケースを明示optionで finding として出力できる
- finding が source、sink、severity、path_score、hop_count、reason を含む
- JSON output が後続処理で使える
- sink がない場合も正常に終了する
