# Sink Candidate

ToolUseProxy は、tool payload を情報流グラフの共通nodeへ変換します。

adapter は tool ごとの payload 構造を解釈する処理です。Filesystem adapter は file read / write を `resource_version` node へ接続します。Search adapter、Bash adapter、MCP adapter などの外部送信系 adapter は、外部へ出る可能性がある tool input を `sink_candidate` node へ接続します。

```text
Filesystem adapter
  Read / Write payload
  -> resource_version

Search adapter
  Search query payload
  -> sink_candidate(external_search)
```

`resource_version` はファイル状態を表す graph node です。`sink_candidate` は外部流出候補を表す graph node です。adapter は、それらの node と artifact fragment の間に structured edge を作ります。

## 基本モデル

第1段階の情報流追跡では、source 由来の情報がどの artifact fragment へ伝わったかを記録します。

```text
source_chunk
  -> artifact_fragment(Read output)
  -> artifact_fragment(Search query)
```

第2段階の漏えい検知では、source lineage が外部流出候補へ到達したかを判定します。

```text
source_chunk
  -> artifact_fragment(Read output)
  -> artifact_fragment(Search query)
  -> sink_candidate(external_search)
```

この形にすると、検知側は tool ごとの payload 形式ではなく、共通の `sink_candidate` node を見ます。

```text
source lineage reaches sink_candidate
```

## Search adapter の位置づけ

Search adapter は、Search tool の query input を `external_search` sink candidate へ変換します。

入力例:

```json
{
  "tool_name": "Search",
  "tool_input": {
    "query": "alpha secret design threshold 0.73 implementation"
  }
}
```

runtime は、この payload を通常の artifact fragment として保存します。

```text
artifact_fragment
  semantic_role = query
  text = alpha secret design threshold 0.73 implementation
```

Search adapter は、Search tool の `query` fragment から `sink_candidate` への edge を作ります。

```text
artifact_fragment(query)
  -> sink_candidate(external_search)
```

edge:

```text
relation = submitted_to
method = search_query
evidence_level = structured
score = 1.0
reason = search query is sent to external search tool
```

source 由来の情報が query に含まれる場合、lineage は `external_search` sink candidate まで伝播します。

```text
source_chunk(private.py)
  -> artifact_fragment(Read output)
  -> artifact_fragment(Search query)
  -> sink_candidate(external_search)
```

この経路が漏えい検知の根拠になります。

## 複数 adapter での利用

`sink_candidate` は外部流出候補の共通nodeです。各 adapter は tool 固有の構造を解釈し、該当する sink type を選びます。

```text
Search adapter
  -> sink_candidate: external_search

Bash adapter
  -> sink_candidate: external_http_request
  -> sink_candidate: external_file_transfer
  -> sink_candidate: external_git_publish

MCP adapter
  -> sink_candidate: external_message
  -> sink_candidate: external_api_call

Final answer adapter
  -> sink_candidate: final_answer
```

adapter は tool 固有の差分を吸収します。sink candidate は検知側が扱う共通の出口です。

## Sink type

初期分類は次の通りです。

- `external_search`
  - Web検索query
- `external_http_request`
  - `curl`、`wget`、HTTP client、browser fetch
- `external_api_call`
  - 外部APIやMCP tool call
- `external_message`
  - Slack、Gmail、Google Docs comment など、人や外部サービスへの送信
- `external_git_publish`
  - `git push`、`gh pr create`、`gh issue create`、gist、release upload
- `external_package_publish`
  - `npm publish`、`twine upload`、`cargo publish`、Docker image push
- `external_deploy`
  - `wrangler deploy`、`vercel deploy`、`aws`、`gcloud` など
- `external_file_transfer`
  - `scp`、`rsync`、`sftp` など
- `final_answer`
  - Codex の最終応答
- `local_persistent_log`
  - ローカルログや transcript

`external_*` は明確な外部送信候補です。`final_answer` と `local_persistent_log` は情報露出につながる可能性がありますが、外部送信とは別の severity として扱います。

## 第1段階と第2段階

第1段階は、情報流を追跡可能にする段階です。

```text
source
  -> artifact
  -> resource
  -> artifact
```

第2段階は、追跡した情報流が外部流出候補へ到達したかを判定する段階です。

```text
source
  -> artifact
  -> sink_candidate
  -> leak finding
```

`sink_candidate` は、第1段階で構築した lineage と、第2段階の漏えい検知を接続する node です。実装上は、最終的な漏えい判定や block より前に、graph 上の到達点として保存します。

## 実装順序

1. `SinkCandidate` model を追加する
2. `sink_candidates` table を追加する
3. `AdapterResult` が `sinks` を返せるようにする
4. `SearchAdapter` を追加し、Search query から `external_search` sink を作る
5. `rebuild_lineage.py` で sink candidate を保存する
6. `trace_lineage.py` と `export_graph.py` で `sink_candidate` を表示する
7. source lineage が `sink_candidate` まで届くことをテストする

最小検知は、lineage 到達先を使って表現できます。

```text
lineage_assignments に node_kind = sink_candidate がある
かつ sink_type が external_* である
```

この条件が `detect_leaks.py` の基本入力になります。

## Data model

`SinkCandidate` は、外部流出候補の node metadata を保持します。

```python
@dataclass(frozen=True)
class SinkCandidate:
    node_id: str
    sink_type: str
    label: str
    tool_name: str | None
    tool_use_id: str | None
    session_id: str | None
    sequence_no: int
    metadata: dict[str, object]
```

各フィールドの意味は次の通りです。

- `node_id`
  - graph node として使う安定ID
- `sink_type`
  - `external_search` などの分類
- `label`
  - 可視化で表示する短い名前
- `tool_name`
  - sink candidate を作った tool 名
- `tool_use_id`
  - 元の tool call ID
- `session_id`
  - Codex session ID
- `sequence_no`
  - 元 event の時系列位置
- `metadata`
  - adapter 固有の補足情報

Search adapter の metadata には次を入れます。

```json
{
  "adapter": "search",
  "query_fragment_id": "<artifact_fragment_id>",
  "query_json_pointer": "/query"
}
```

query text 全体は `artifact_fragments.text` に既に保存されるため、`sink_candidates.metadata_json` には重複保存しません。可視化では、sink node 自体には送信種別を表示し、実際の本文previewは上流の `artifact_fragment(query)` に表示します。

## DB schema

`sink_candidates` table を追加します。

```sql
CREATE TABLE IF NOT EXISTS sink_candidates (
    node_id TEXT PRIMARY KEY,
    sink_type TEXT NOT NULL,
    label TEXT NOT NULL,
    tool_name TEXT,
    tool_use_id TEXT,
    session_id TEXT,
    sequence_no INTEGER NOT NULL,
    metadata_json TEXT NOT NULL,
    recorded_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

index:

```sql
CREATE INDEX IF NOT EXISTS idx_sink_candidates_type
ON sink_candidates (sink_type);

CREATE INDEX IF NOT EXISTS idx_sink_candidates_session_sequence
ON sink_candidates (session_id, sequence_no);
```

保存API:

```python
EventStore.replace_sink_candidates(sinks: list[SinkCandidate]) -> None
EventStore.list_sink_candidates() -> list[SinkCandidate]
```

`resource_versions` と同じく、sink candidates は adapter 解析から再構築できる派生データです。`scripts/rebuild_lineage.py` は adapter 実行後にworkspace-scopedな`replace_sink_candidates_for_workspace()`を呼びます。

## AdapterResult

adapter の出力に `sinks` を追加します。

```python
@dataclass(frozen=True)
class AdapterResult:
    edges: tuple[FlowEdge, ...]
    resources: tuple[ResourceVersion, ...]
    sinks: tuple[SinkCandidate, ...] = ()
```

既存の Filesystem adapter は `sinks=()` を返します。Search adapter は `resources=()` を返し、`sinks` と `submitted_to` edge を返します。

adapter registry は edge、resource、sink をそれぞれ `node_id` / `edge_id` で deduplicate します。

## Edge design

Search query から sink candidate へ structured edge を作ります。

```text
artifact_fragment(query)
  -> sink_candidate(external_search)
```

edge:

```text
src_node_kind = artifact_fragment
src_node_id = <query fragment id>
dst_node_kind = sink_candidate
dst_node_id = <sink node id>
relation = submitted_to
evidence_level = structured
method = search_query
score = 1.0
reason = search query is sent to external search tool
```

`submitted_to` は、tool input が外部または外部相当の sink へ渡される構造的事実を表します。将来の Bash / MCP adapter でも同じ relation を使えます。

例:

```text
artifact_fragment(curl body)
  -> sink_candidate(external_http_request)

artifact_fragment(Slack message text)
  -> sink_candidate(external_message)
```

## Node ID

Search sink candidate の node ID は、同じ tool call と query fragment から安定して生成します。

```text
sha256(
  "sink_candidate" + "\0" +
  "external_search" + "\0" +
  session_id + "\0" +
  tool_use_id + "\0" +
  query_fragment_id
)
```

`tool_use_id` がない場合は `event_id` を fallback に使います。これにより、同じ session 内の別 search call が同じ query text を使っていても別 node として扱えます。

## Search adapter

Search adapter は `hook_monitor/analysis/adapters/search.py` に置きます。

対象 tool 名は正規化して判定します。

```python
normalized = re.sub(r"[^a-z0-9]+", "_", tool_name.lower()).strip("_")
```

初期対応する tool 名:

- `search`
- `web_search`
- `websearch`
- `web_search_query`
- `browser_search`
- `internet_search`

query fragment の選択ルール:

1. `phase == "pre_tool_use"`
2. `artifact_role == "tool_input"`
3. `semantic_role in {"query", "search_query"}`
4. leaf fragment を優先する

`tool_input` 全体を query として扱う fallback は初期実装では使いません。JSON全体を sink にすると、query 以外の option や path が混ざり、可視化と検知の根拠が粗くなります。

Search output は sink candidate にしません。Search output は外部から返ってきた情報であり、外部流出先ではありません。将来、外部由来情報を追跡する場合は inbound source として別モデルを設計します。

## Rebuild flow

`scripts/rebuild_lineage.py` の処理順は次のようになります。

```text
load artifact contexts
  -> run adapters
  -> replace resource_versions
  -> replace sink_candidates
  -> build / reuse artifact graph
  -> include adapter edges in information_flow_edges
  -> bind protected sources
  -> propagate lineage
```

Search adapter が作る `submitted_to` edge は `information_flow_edges` に保存されます。source lineage が query fragment に到達している場合、その edge を通って `sink_candidate` まで伝播します。

## Visualization

`trace_lineage.py` と `export_graph.py` は `sink_candidate` node を表示します。

label:

```text
sink:external_search
Search query seq=<sequence_no>
```

tree 表示例:

```text
source_chunk:private-source#0
`- Search pre_tool_use query seq=4 path_score=0.92
   via derived_from/substring evidence=content_lexical edge_score=0.92
   `- sink:external_search seq=4 path_score=0.92
      via submitted_to/search_query evidence=structured edge_score=1.000
```

Mermaid / DOT では `sink_candidate` を artifact や resource と異なる色で表示します。

推奨色:

```text
sink_candidate: amber / orange
```

## Tests

SinkCandidate 基盤のテスト:

- `sink_candidates` table が初期化される
- `replace_sink_candidates()` と `list_sink_candidates()` が round trip できる
- `AdapterResult` が `sinks` を保持できる
- `rebuild_lineage.py` が sink candidates を保存する

Search adapter のテスト:

- Search tool の `query` fragment から `external_search` sink candidate が作られる
- query fragment から sink candidate へ `submitted_to/search_query` edge が作られる
- source lineage が Search query から `sink_candidate` まで到達する
- Search output だけでは sink candidate が作られない
- Search 以外の tool 名では sink candidate が作られない
- 同じ query text でも別 tool call は別 sink candidate になる

Visualization のテスト:

- `trace_lineage.py --analysis-run "$RUN_ID" --source "$SOURCE_ID"`に`sink:external_search`が表示される
- `export_graph.py --analysis-run "$RUN_ID" --format mermaid`にsink nodeが表示される
- `export_graph.py --analysis-run "$RUN_ID" --format dot`にsink nodeが表示される
- `export_graph.py --analysis-run "$RUN_ID" --format json`のnode listに`kind = sink_candidate`が含まれる

## Completion criteria

SinkCandidate と Search adapter の実装完了条件:

- `scripts/rebuild_lineage.py --db PATH --workspace-root PATH --rebuild-graph`後に、そのworkspaceの`sink_candidates`が保存される
- protected source 由来の query が `external_search` sink まで lineage として伝播する
- tree / Mermaid / DOT / JSON で sink node を確認できる
- Search output や非Search tool input を誤って external search sink にしない
- 次の `detect_leaks.py` が `node_kind = sink_candidate` と `sink_type = external_*` を入力として使える
