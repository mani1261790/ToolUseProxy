# 利用者向け文章の設計

ToolUseProxyの利用者は、決まった文を覚える必要がありません。自然な言葉で目的を伝えれば利用できます。次の2文は短い入力例であり、機能を呼び出す合言葉ではありません。語尾、表現、詳しさが異なっても、意図が同じなら同じ操作として扱います。

```text
ToolUseProxyをこのプロジェクトで使えるようにして
守った方がよいファイルを探して
```

例えば「このprojectでToolUseProxyを使いたい」「ToolUseProxyの準備をして」も初期設定の依頼として扱い、「秘密にした方がよいファイルはある？」「保護候補を見つけて」も候補探しの依頼として扱います。利用者に入力例の完全な言い直しを求めません。

skillは会話の意図から処理を選びます。上記の日本語をliteralな文字列一致で判定するparserや分岐は設けません。文書やテストで入力例を維持する場合も、その文字列自体をruntimeの機能要件にしてはいけません。

## 文章の順序

ToolUseProxyから利用者へ説明するときは、次の順序を守ります。

1. 何ができるようになるか
2. 何を実行するか
3. 何が変更されるか
4. 外部通信があるか
5. 何を許可してよいか
6. 必要な場合だけ技術情報

`init`、`doctor`、`status`、`scan`、`selector`、revision、manifest hash、candidate IDは内部処理または技術情報です。主文や利用者の選択肢には使いません。

## 承認画面

承認画面は改行が失われても読める短いplain textにします。

```text
ToolUseProxyの確認｜内容：...｜変更：...｜通信：...｜理由：...｜許可：...
```

プロジェクト外のToolUseProxy専用保存領域を読み書きする場合は、それが承認を求める理由だと明記します。外部通信を行わない操作を、network permissionのように説明してはいけません。

## 保護候補

候補確認は「このファイルをToolUseProxyで守りますか？」から始め、次を表示します。

- ファイル
- 守る内容
- できること
- 「守る」を選ぶと変わるもの
- 「守る」「今回は見送る」「今後は候補に出さない」の3選択肢

内部ではそれぞれapprove、reject、ignoreへ対応します。値を含まないexact JSONは改ざん防止のため残しますが、「技術情報（判断には読まなくてもかまいません）」の後へ置き、利用者に解読を要求しません。

## 完了と失敗

成功時は、内部statusではなく「このプロジェクトではToolUseProxyが動作しています」と先に伝えます。保護対象が未登録なら、その事実と次に送る短い一文を続けます。

失敗時は、「保護機能が有効になっていない」「ここで停止した」を先に伝えます。エラーcodeや再実行commandだけを表示して終えてはいけません。
