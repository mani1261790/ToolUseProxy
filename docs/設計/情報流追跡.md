# 情報流追跡の設計指針

ToolUseProxy の第1段階である「情報流を追跡可能にする」ための設計方針です。

## 結論

このgraphは、LLM内部を含む完全な情報流や因果的なtaintを表すものではありません。Codexから観測できるtool I/O、file operation、resource、sinkの間に、構造的証拠と内容対応からprovenanceを再構成する近似モデルです。

製品上の第一目的はgraph構築ではなく、外部sinkへ送られる実payloadを実行前に検査することです。今後は `sink-first, provenance-assisted` とし、sink固有adapterでpayloadを解決したうえでprotected sourceと型別比較し、lineageは直接比較だけでは不足する場合の補助証拠・説明として使います。比較評価の正本は[Sink中心の情報流評価計画](../調査/Sink中心の情報流評価計画.md)です。

ただし、protected source とsink tool inputを毎回直接比較するだけでも、多段の情報流やtool inputに本文が現れないsinkは扱えません。

たとえば、次の流れを考えます。

```text
.env
  -> tool output
  -> xx.md
  -> search query
```

`.env` と search query が十分に似ていなければ、直接比較では見逃します。一方で、それぞれの中間状態に情報が引き継がれていることを記録できれば、search query から `.env` まで経路を逆にたどれます。

そのため、現在のlineage処理を次の2層に分けています。

1. protected source とは独立に、artifact 間の情報流グラフを作る
2. protected source をグラフ上の最初の一致箇所へ接続し、そこから lineage を伝播する

source との比較は、情報流全体を判定する処理ではなく、既存グラフへ source を接続する seed 探索です。source と一致した全nodeへ直接edgeを張るのではなく、一致nodeのうち上流に別の一致nodeを持たない入口だけをseedにします。これにより、中間経路を残したままlineageを伝播できます。

このlineageがsink直接検査へどれだけ追加価値を持つかは未確定です。`curl @file`、file upload、Git push、session境界などを含む比較で、検出率・誤検知・latency・説明理解が改善する場合だけruntime上の複雑さを正当化します。

## 基本モデル

### event

Hook が1回発火した記録です。時系列、session、turn、tool、phase を保持します。

各 event には `sequence_no` を付けます。時刻文字列だけでは同時刻の event を安定して並べられないため、情報流の前後関係にはこの連番を使います。

### artifact

Hook payload から取り出した tool input または tool output 全体です。raw payload を後から再解析するための保存単位です。

### artifact fragment

artifact 内で、実際に比較する文字列です。

たとえば tool input が次のJSONだった場合、

```json
{
  "path": "private.py",
  "query": "独自アルゴリズムの閾値は0.73"
}
```

artifact 全体だけでなく、次の fragment を作ります。

```text
/       -> tool_input全体
/path   -> path
/query  -> query
```

これにより、path、query、command、content、stdout など、役割の違う値を分けて比較できます。

`tool_input`ではscalar valueに加えてJSON object keyも`json_key` fragmentとして保存します。MCP argumentsのkey fragmentはkey name lineage用のcanonical候補にしますが、sinkへ接続するのはshape不一致またはunprofiledなwrite-like callだけです。key fragmentのsource bindingとartifact間edgeはraw case-sensitive exact一致だけを認め、protected文章に`content`などの一般keyが含まれただけのsubstring / shingle taintを作りません。MCP以外の同一artifactで同じsemantic role / normalized textを持つpayload fragmentは、監査用rowを保持したまま比較時にdedupします。

apply_patchとBashでは、payload fragmentに加えてoperation用fragmentを保存します。

- `operation_container`
  - tool call全体を監査する親fragment。一般類似度からは除外する
- `operation_added`
  - apply_patchの1 file operationに追加される内容。content-bearing fragmentとして扱う
- `operation_removed`
  - 削除内容の監査証拠。新resourceへ流れた情報とはみなさない
- `operation_control`
  - add/update/delete/moveとsource/target pathの制御情報
- `bash_segment`
  - 静的に分割できた`;`、`|`、`&&`、`||`間のcommand fragment

`bash_segment`からは、直接実行される`curl`の静的body optionを解析時だけtransient projectionします。projection本文をfragmentや別tableへ保存せず、抽出値とprotected source chunkが完全一致した場合だけ、元の`bash_segment`へ`bash_submission_exact`の`source_binding`を追加します。これにより、command全体では短すぎてcriticalにならなかった送信値をscore 1.0で結び付けつつ、一般的な部分文字列をcriticalへ昇格させません。

解析はshellを実行・展開しません。quote provenanceとcurl optionのarityを静的に証明できないsegment、body以外を含むdynamic expansion、dynamic redirection、`@file` / `@-`、上限超過は値projectionを作らず、既存のsegment-level sink、path、pipeline evidenceへfallbackします。一つのcurl segment内に不確かなbody candidateが混ざる場合も、確実に見えた一部だけを採用しません。command前の環境代入として除外するのはraw spellingがunquotedなASCII `NAME=` / `NAME+=`だけで、引用・escapeにより見かけだけが代入形になったcommand wordをcurl wrapperとは誤認しません。

### tool operation

`PreToolUse`の入力から、静的に確定できたfile操作を保存する単位です。`operation_id`、adapter、operation index/kind、source/target path、Bashのsegment index/connector、content fragmentへの参照を持ちます。

apply_patchではfileごと、Bashではsegment内のread/overwrite/appendごとにoperationを分けます。これにより、複数file patchや`;`で区切られたcommand全体を1つの情報fragmentとして各resourceへ接続しません。

### tool operation outcome

`PostToolUse`が各operationの実行結果を`succeeded` / `failed` / `unknown`のどれと判断したかを保存します。履歴の主キーは`(post_event_id, operation_id)`で、同じtool useに複数のPostがあっても上書きせず保持します。解析時点のevent sequenceを超えない最新outcomeだけを採用し、未来のPost結果が過去のgraphへ混ざることを防ぎます。

### resource snapshot

成功したPostToolUse後に、operationから静的に確定したpathの実状態をbounded captureした証拠です。workspace root、requested/lexical path、source/target role、resource state、capture status、file kind、byte size、captured bytes、SHA-256、encoding、任意の本文、error code、durationを分けて保存します。

本文は既定で保存せず、全体を安定して読み切れたfileのSHA-256だけをresource versionへ接続します。patch文字列のhashはfile hashに使いません。move/deleteの不在確認は`deleted` tombstoneとして表現します。PostToolUseのsnapshot capture失敗は、すでに完了した操作のpolicyを変更せずadvisoryとして扱います。path単位の失敗はcapture statusを、capture全体の例外はoutcome evidenceへ例外型を残し、断定可能な範囲だけhashless resourceへfallbackします。PreToolUseの保護判定失敗は別境界で実行前denyします。

### workspace

workspaceは情報流を分離する最上位scopeです。明示した`TOOLUSEPROXY_WORKSPACE_ROOT`、未指定時はHook payloadの`cwd`を、走査なしで検証してcanonical rootを得ます。rootのSHA-256から`workspace_id`を作り、lexical rootと実行時cwdは監査・相対path解決用に別保存します。

`workspace_id`はevent、artifact、operation、snapshot、protected source、source chunk、resource、sink、edge、analysis cursor、analysis runへ伝播します。runtimeの照会条件は常に現在eventの`(workspace_id, session_id)`で、同じsession ID、source ID、resource pathが別workspaceに存在しても比較・lineage・policy判断へ混ぜません。初期化後のPreToolUseでworkspaceまたはsession identityを安全に確定できない場合は、別workspaceを推測せず実行前denyします。PostToolUseとStopは断定不能な監査を作らずadvisoryに留めます。

### source chunk

`protected_sources.json` で指定した保護対象ファイルを、比較可能な単位へ分割したものです。

- Python: 関数・class単位
- Markdownやテキスト: 段落単位

### edge

情報がどの node からどの node へ伝わった可能性があるかを表します。

現在は次の relation を使用します。

- `derived_from`
  - exact または substring により、内容の伝播を強く確認できた
- `similar_to`
  - shingle Jaccard により、内容が近いと推定された
- `source_binding`
  - protected source chunk が artifact fragment と一致した
- `read_from`
  - resource versionからtool outputが読み出された
- `written_to`
  - tool inputのcontentがresource versionへ書き込まれた
- `read_by`
  - resource versionをBash segmentが入力として読む
- `updated_from`
  - updateまたはappendが以前のresource内容を引き継いだ
- `moved_to`
  - move sourceからtarget resourceへ内容が移った
- `deleted_by` / `deleted_to`
  - delete操作と、Post snapshotで確認したtombstoneを表す
- `piped_to`
  - Bash pipelineの前segmentから次segmentへstdoutが渡る
- `submitted_to`
  - tool input fragmentが外部sink candidateへ送信される

同じtool callのPre/Postに複製された入力は保存しますが、情報の新しい移動ではないため`same_content` edgeは作りません。

## 観測事実と推定を分ける

すべての edge を同じ強さで扱ってはいけません。

```text
structured
content_exact
content_lexical
content_semantic
```

- `structured`
  - tool_use_id、phase、role、Filesystem adapterなど構造上の対応から得た証拠
- `content_exact`
  - hash完全一致
- `content_lexical`
  - substring、n-gram、shingleなど文字列上の近さ
- `content_semantic`
  - embeddingなど意味上の近さ

単に時系列で近いだけのartifactは、比較候補にはできますが、情報流edgeにはしません。

## artifact 間グラフ

artifact 間グラフは protected source の設定と無関係に作ります。

比較対象は次の条件で絞ります。

- 同じ session に属する。sessionがない場合は同じturnに属する
- sessionもturnもないfragmentは一般類似度比較へ入れない
- source側の `sequence_no` が destination側より小さい
- 同じartifact内ではない
- JSON container全体のroot fragmentではない
- `PostToolUse`に複製された`tool_input`ではない
- 情報内容を運ぶsemantic roleである
- text hashが一致する
- 5-gramを共有し、候補上位に入る

fragmentは観測ログとしてすべて保存し、graph構築時にcanonicalな比較対象だけを選びます。比較対象となるroleは次です。

```text
command
query
search_query
content
stdout
stderr
tool_output
final_answer
```

`path`、`server`、`tool`はtool固有adapterが構造情報として使い、一般類似度比較には入れません。JSON objectやarrayを表すroot fragmentも比較から除外します。ただし、平文tool outputやfinal answerはroot fragmentが本文そのものなので残します。

同じtool callの入力はPreToolUseとPostToolUseの両方に含まれます。正式な入力ノードはPreToolUse側とし、PostToolUse側の複製入力は保存だけ行います。複製間の`same_content` edgeは情報の新しい移動を表さないため作りません。

現在は、次の順に比較します。

1. exact hash
2. substring
3. 5-gram Jaccard
4. embedding cosineは将来の拡張点

全artifactの総当たりではなく、hash indexとshingle inverted indexから候補を作ります。

## source binding

protected source は、artifactグラフ完成後に接続します。

```text
source chunk
  -> exact / substring / shingle
  -> artifact fragment
  -> 既存artifact graphを伝播
```

この構造により、後からsourceを追加してもartifact間比較をやり直す必要がありません。追加sourceとartifact fragmentのseed探索、およびlineageの再計算だけを行います。

seed探索も全artifactとの総当たりにはせず、artifact間比較と同じcanonical fragmentを対象に、text hashと5-gram inverted indexから候補を取得します。これにより、protected sourceをJSON container全体、path、tool名、PostToolUse側の複製入力へ直接bindingしません。

secretfileの値にはchunk単位のsource-binding signalを付けます。selectorなしは`registered_source`、明示選択した通常項目は`selected_field`、明示選択したsecurity fieldだけ`selected_security_field`です。長く多様な英字だけの単一tokenを文章内のsubstringとして結ぶ場合は`selected_security_field`を必須とし、公開compoundの偶然一致を抑えます。exact一致とartifact間比較の規則は変えません。このsignalはSQLite source chunkとcompleted run snapshotにも保存され、full / incremental解析で同じpair判定へ渡されます。

静的curl submissionはこの一般候補探索に加わる特殊経路です。直接呼ばれたcurlのbody operand全体とdecoded source chunk本文がraw exact equalityの場合だけ、`content_exact / bash_submission_exact / score=1.0`の`source_binding`を元のsegmentへ作ります。substring、`name=value`のvalue部分だけ、curlが複数operandから合成する最終bodyを1.0へ昇格させません。従来のcommand / segment一般類似度は別経路として残します。先行するRead artifactから同じsegmentへ弱い類似経路が存在しても、この直接の送信証明は冗長seedとして削除せず、critical scoreを弱めません。

抽出規則のversionはruntime / offline両方のdetector versionへ含めます。optionやquote規則を変えた場合、古いanalysis cursorやgraph cacheを同じ意味として再利用しません。

operation snapshotにより、成功したapply_patchなどが書き込んだ対象fileのPost時点のhashは保持できます。ただし、sourceを後から追加した時点でファイル内容が既に変わっており、過去内容もHook I/OやGitに残っていない場合、当時のsource内容は復元できません。現在のsnapshotは変更対象pathだけを取得するwrite後の証拠であり、protected sourceの履歴snapshotやworkspace全体のbackupではありません。過去内容の復元にはGit blob、read結果、暗号化したsource snapshotなどが別途必要です。

## lineage の伝播

source bindingを起点に、edge scoreの積を経路scoreとして伝播します。

```text
path_score =
  source_binding_score
  * edge_1_score
  * edge_2_score
  * ...
```

各source chunkとnodeの組み合わせについて、最もscoreが高い経路だけを `lineage_assignments` に保存します。

これにより、次のような分岐も別々の経路として保持できます。

```text
.env
├── xx.md
│   └── search A
└── yy.md
    └── search B
```

search Aとsearch Bのどちらから逆向きにたどっても、同じsource chunkへ到達できます。

## DB構造

主なテーブルは次の通りです。

- `workspaces`
  - canonical rootとworkspace identity
- `events`
  - Hook eventの時系列記録
- `artifacts`
  - tool input / output全体
- `artifact_fragments`
  - 比較用に分割した文字列
- `tool_operations`
  - PreToolUseから抽出したfile operation、path、segment、connector、対応fragment
- `tool_operation_outcomes`
  - `(post_event_id, operation_id)`単位の三値outcome履歴
- `resource_snapshots`
  - operationごとのPost resource state、capture status、SHA-256、任意本文、error、duration
- `information_flow_edges`
  - source非依存のartifact間・resource間グラフ
- `resource_versions`
  - Filesystem adapterが再構成したファイルversion
  - operation ID/index、snapshot ID、resource stateを持つ
- `sink_candidates`
  - Search、Bash、MCPなどのadapterが作る外部流出候補node
- `protected_sources`
  - 保護対象の設定
- `source_chunks`
  - sourceの比較単位
- `analysis_runs`
  - workspace、任意session、source設定、解析条件ごとの実行記録
- `analysis_node_snapshots` / `analysis_run_nodes`
  - completed offline runのnode metadataをcontent-addressedに固定するsnapshotとrun membership
- `analysis_run_graphs` / `analysis_run_flow_edges`
  - completed runのgraph coverageとedge membership
- `source_binding_edges`
  - source chunkからartifact fragmentへの接続
- `lineage_assignments`
  - sourceから各nodeへの最良経路
- `workspace_analysis_state`
  - workspaceごとのartifactグラフfingerprintとdetector version
- `analysis_cursors`
  - `(workspace_id, session_id)`ごとのruntime差分位置
- `redaction_plans` / `redaction_targets`
  - current MCP callのeligible / rejected previewと全finding targetをimmutableなhash-only auditとして保存
- `redaction_decision_links`
  - preview BLOCK根拠と将来REDACT identityをfinding単位で結ぶhash-only監査table。情報流edgeやruntime actionではない

既存の `flow_edges` は初期実装との互換性のため残していますが、新しい解析では使用しません。

## 再解析

次のコマンドでグラフとlineageを構築します。

```bash
python3 scripts/rebuild_lineage.py \
  --db .tooluseproxy/events.db \
  --workspace-root "$PWD"
```

artifact、tool operation outcome、resource snapshotの集合とdetector versionが変わっていなければ、artifact/resourceグラフは再利用されます。protected sourceだけを変更した場合は、source bindingとlineageのみ再計算します。

比較アルゴリズムを変更した場合など、artifact間グラフを強制的に作り直すには次を使います。

```bash
python3 scripts/rebuild_lineage.py \
  --db .tooluseproxy/events.db \
  --workspace-root "$PWD" \
  --rebuild-graph
```

offline CLIはglobalなlatestへfallbackしません。再構築後のrunを読むときは、`--analysis-run ID`か`--workspace-root PATH --latest`のどちらかを明示します。workspaceの`--latest`はcompleted offline runだけを選び、completedを含むruntime run、incomplete offline run、legacy unscoped runは選びません。

completed offline runはedge membership、source binding、lineageだけでなく、artifact fragment、protected source、source chunk、resource version、sink candidateのmetadataもcontent-addressed snapshotへ固定します。同じnode IDのlive metadataが後から変わっても、過去runは当時のpayloadを読みます。これに対してruntime runは低latencyを優先した現在sessionのmutable graph viewです。

`rebuild_lineage.py`はadapter、edge、source binding、lineageを先にPythonメモリ上で計算し、`publish_workspace_analysis_run()`でworkspaceのlive source/resource/sink/graph、run snapshot、source binding、lineage、graph state、`completed_at`を1 transactionへpromoteします。`completed_at`は最後に設定するため、途中のvalidation、INSERT、state更新が失敗した場合は旧live derived rows/stateと旧latest completed runがそのまま残り、incomplete runも残りません。generic fragmentと旧ログ向けのdeterministic Bash segment fragmentは`INSERT OR IGNORE`でidempotentに補完し、この破壊的でないbackfillだけはpublish境界の外で行います。既存のrich fragmentをgeneric fragmentで上書きしません。

入力の混在を防ぐため、selected workspaceのevent payload、artifact/fragment、operation/outcome、resource snapshot、DB上のsource catalogを一時的にSHA-256へ集約します。本文を新しいtableへ保存する処理ではありません。CLIは読込前後のrevision一致を確認し、publish時には同じWAL read snapshotでrevision、直前のcompleted offline run、graph stateをCASします。workspaceの`protected_sources.json`を使う場合は、設定の有無と、source/chunk本文を含むcatalog fingerprintもpublish直前に再読込して照合します。filesystem自体はDB transactionへ参加できないため最終照合後の変更までlockはしませんが、publishされるcatalogは解析に使った読込済みsnapshotと一致し、次回rebuildではその後のfilesystem変更を新しい入力として扱います。

graph再利用時はlive edge集合とpayloadの完全一致も確認し、runtime cursor/stateを消しません。重いrevision計算はdeferred WAL read snapshotで行うため、その間のHook writerは待たされません。同時writerにより古いread snapshotからwriteへupgradeできない場合、offline publishは全rollbackして最大3回まで再試行します。別workspaceだけの変更でselected workspaceのrevisionとCAS対象が同じなら内部retryで完了し、selected workspaceの入力が変わった場合はstaleな計算結果をpublishせず再実行を要求します。graphを再構築する場合だけ、従来どおりworkspaceのruntime derived cacheをinvalidateします。

## 現時点の制限

現在の実装は、Hook I/Oの文字列類似度、Filesystem adapterによるread/writeのstructured edge、Search/Bash/MCP/final answer adapterによるsink candidate、静的curl body operandのexact projection、Stop hookの実継続、Bash/MCPの実行前遮断、operation単位fragment、成功Post後のbounded snapshot、session差分解析、MCP redaction previewのhash-only監査、dormant decision linkageとPost confirmationを扱うMVPです。previewはcurrent callの全critical findingの後にだけ実行し、参照source chunkをworkspace ownership付きで最大32 IDに制限します。新規auditは完了runのcurrent-call critical lineageとpure planner結果へ完全一致させ、sink metadataもrow / call byte上限内でだけ再読込します。dormant enforce preparationは既存のworkspace / session scoped previewとcompleted analysis runだけをboundedに再証明し、graph、cursor、incremental analysisの対象集合を拡張しません。`enforce / eligible` plan、target exact clone、全findingのBLOCK-to-REDACT linkは同じtransactionで保存・再読込しますが、現行runtimeはprepare APIを呼ばずrendererも持ちません。eventの保存JSON byte数・hash、sequence、redaction call scope、bounded Post input hash/statusはwideなpayload rowと分離したsidecarへ同じtransactionで記録します。confirmationは将来rendererが作るenforce/rendered planだけをstable profileで照合し、owner、最小Post、verified preview、全decision linkを再証明して`events` tableを読みません。preview / prepared planは遷移させず、失敗時は既存denyと記録済みPost eventを維持し、runtime rewriteは行いません。final sidecar直前の実Codex E2Eではpublic callはplanなしでPre / Postとserver副作用が各1件、protected callはeligible previewのままPreで止まりPost / server副作用が0件でした。final hash-only schemaとdormant linkageはruntime配線を増やしておらず、実Codex再試行はusage limitでturn開始前に停止しました。実Hook entrypointを含むlocal回帰で同じdeny / no-rewrite契約を固定しています。

Stop / PreToolUse runtimeでは`analysis_cursors`にworkspace・sessionごとの処理済みsequenceを保存し、canonical fragmentを1 rowの`fragment_exact_index`へ、5-gramを`fragment_shingles`へ索引化します。exact lookupは`workspace / session / text_hash / sequence`複合indexから直前1件だけを取得し、同値履歴全件のJOIN / sortへ戻しません。通常は新fragmentと同じworkspace・sessionの候補だけを比較し、新しいPost evidenceがあれば同じtool useのPre context、operation、snapshotも依存取得します。新edgeからlineage scoreが改善する範囲だけを伝播します。detectorまたはそのworkspaceのsource manifestが変わった場合は、そのworkspace・sessionだけをfull rebuildします。両indexはraw evidenceではなく再生成可能なderived tableで、workspace analysis schemaの不整合時はsession evidenceから再構築します。

duplicate Postやcursor更新前の部分保存によって、delta operation IDが既存resource versionへ再度当たる場合も、重複versionとcycleを避けるため同じworkspace・sessionをraw evidenceからfull rebuildします。これは稀な整合性fallbackであり、全DBをruntime Hook内で再解析するものではありません。

まだ次は実装していません。

- Bash commandでshell展開を必要とする変数、command substitution、glob / brace / tilde、heredocの値解決。single quoteやescapeでliteralになった記号、直接curlの静的body operand、workspace内の限定的なfile-backed bodyはexact projection / resolution済み。未解決値を伴う既知external commandはsink visibilityを残し、protected sourceが有効なら実行前denyする
- MCP adapterのserver/tool分類拡張
- user promptのnode化
- embedding backend
- protected sourceの履歴snapshotとretention/prune
- native Web Searchの実行前遮断
- warn、redactの実行時適用

既知の設計上の制限もあります。offline publishはatomicになりましたが、永続shadow tableとgeneration pointerを使う短時間swapではありません。最初のlive table writeからrun completionまでは1 writer transactionであり、選択workspaceのnode/edge件数に応じてwriter lock時間が増えます。重いevidence revision計算はdeferred WAL read snapshotで行いHook writerを塞ぎませんが、offline rebuild自体は低頻度の運用コマンドとして扱います。1,000 resource / 999 edgeの並行回帰ではwriter transaction中の別workspace Hook writeを1秒未満に収めるguardを置いています。このpublish APIを呼ぶHook経路はなく、今回の変更自体は通常のPreToolUse / PostToolUse / Stop latencyへ処理を追加しません。またruntime runをrun IDで後から読む場合は、そのsessionの現在のmutable graphを使うため、offline completed runのような完全な履歴snapshotではありません。全runtime runをsnapshotするとsession成長に対してmembership/edge rowとHook latencyが二次的に増え、artifact/source plaintext retentionも広がるため、現時点では意図的に見送ります。

特に、モデル内部で行われた要約や言い換えは直接観測できません。現段階では前後artifactの類似度から推定します。将来的にはembedding、コード特徴量、tool固有adapterを比較し、推定精度を評価します。

## 条件付きの長期再評価項目

現在の実装優先順位は[実装タスク](../運用/実装タスク.md)を正本とし、GitHub Issues / Projectで進捗を管理します。次の項目は着手順ではなく、前提条件が成立した場合だけ再評価します。

1. 過去runtime判断を再現する具体的な監査要件が生じた場合、全run snapshotではなくnon-allow decisionのbounded evidence capsuleまたはsession checkpointを設計する
2. Codex側のexclusive rewrite、または完全管理されたsingleton配備境界が成立した場合、enforce rendererを再評価する
3. lexical profileの固定corpus、privacy invariant、Hook latency境界を維持できるoffline実験として、embeddingとコード向け特徴量を比較する

PermissionRequestは公式sourceと実Codex E2Eまで評価し、汎用runtime接続を見送りました。payloadに`tool_use_id`がないためPreToolUseとのheuristic joinは行わず、同じinputを重複artifactとしてgraphへ入れません。network approvalの`description`もsegmentへ帰属できないため、command全体をtaintしません。将来、PreToolUseにないcoverageとstableな相関情報が確認できた場合だけdeny-onlyの独立eventとして再評価します。redactは [Redact設計](Redact.md) の通り、Bash、apply_patch、MCPを一括で文字列置換せず、MCP profileとpreviewから進めます。現行Codexの複数rewrite競合が解消するまでcritical external sinkはdenyを維持し、未サポートの`permissionDecision: ask`には依存しません。
