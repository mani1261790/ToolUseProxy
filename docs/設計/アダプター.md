# Tool Adapter

## Adapterとは何か

adapterは、toolごとに異なる入力・出力を、ToolUseProxy共通の情報流グラフへ翻訳する処理です。

Hookから届くJSONを保存するだけでは、その値が何を意味しているかまでは分かりません。

たとえば次の入力には、ファイルpathが含まれています。

```json
{
  "path": "private.py"
}
```

しかし、汎用の類似度計算だけでは、これがファイルのreadなのかwriteなのか、出力されたコードがどのファイル由来なのか判断できません。

Filesystem adapterはtool名とJSON構造を解釈し、次の共通表現へ変換します。

```text
Read:
resource_version(private.py)
  -> tool_output

Write:
tool_input.content
  -> resource_version(xx.md)
```

外部へ出る可能性があるtool inputは `sink_candidate` へ変換します。

```text
Search:
tool_input.query
  -> sink_candidate(external_search)
```

`adapter` は変換処理です。`resource_version` や `sink_candidate` は、変換後にgraph上へ置かれるnodeです。SinkCandidateの設計は [外部流出候補.md](外部流出候補.md) にまとめています。

役割は次のように分かれます。

- adapter
  - toolの操作内容を理解する
  - path、content、outputなどの役割を抽出する
  - resource versionやsink candidateなどの共通nodeへ変換する
  - tool構造に基づく確定的なedgeを作る
- similarity
  - コピー、部分一致、少し崩れた再利用を推定する
- lineage
  - source bindingからedgeをたどり、各nodeのsourceを求める

## なぜadapterが必要か

類似度だけでは、無関係な文章が偶然似ている場合に誤ったedgeが作られる可能性があります。また、path文字列とファイル本文は似ていないため、ファイルreadの関係は内容比較だけでは説明できません。

adapterでは、次のようなtoolの構造を証拠にできます。

```text
tool_name = Read
tool_input.path = private.py
tool_response.content = 未公開コード
```

この場合、本文同士の類似度を使わず、

```text
private.pyのresource version
  -> 未公開コードを含むtool output
```

という`structured` edgeをscore `1.0`で作ります。

## Resource Version

同じpathのファイルでも、上書き前後では内容が異なります。そのため、pathそのものではなく`resource_version`をnodeとして扱います。

```text
notes.md version 1
  -> Writeで更新
notes.md version 2
  -> Readで取得
```

現在のresource versionは、主に次から識別します。

- session
- 絶対path
- content hash
- event sequence
- tool use ID
- operation ID / operation index
- snapshot ID
- resource state (`present` / `deleted` / `missing` / `unknown`)

write後に同じpathをreadし、内容hashも一致した場合は、同じresource versionを経由させます。

## Protected Sourceとの接続

`protected_sources.json`に登録されたpathとresource versionのpathが一致した場合、次の確定edgeを作ります。

```text
protected_source(private.py)
  -> resource_version(private.py)
```

そのため、sourceファイルの現在の内容とtool outputが似ていなくても、指定pathをreadした事実からlineageを開始できます。

一方、未登録の`public.md`をreadしてもprotected sourceからのedgeは作られません。ほかの類似度edgeから接続されない限り、そのnodeはsource lineageの外に残ります。

## 現在実装しているAdapter

現在はFilesystem adapter、Search adapter、Bash adapter、MCP adapter、Codex final answer adapterを実装しています。

### Filesystem adapter

対象とするtool名は、正規化後に次のいずれかになるものです。

#### Read

- `read`
- `read_file`
- `readfile`
- `read_text_file`
- `fs_read_file`
- `fs_readfile`
- `filesystem_read_file`
- `filesystem_read_text_file`

#### Write

- `write`
- `write_file`
- `writefile`
- `write_text_file`
- `fs_write_file`
- `fs_writefile`
- `filesystem_write_file`
- `filesystem_write_text_file`

tool nameは小文字化し、`/`、`.`、`-`などを`_`へ正規化して照合します。Codex app-serverにも`fs/readFile`と`fs/writeFile`があるため、この命名も対象にしています。

入力ではsemantic roleが`path`と`content`のfragmentを使います。read出力では`content`、`stdout`、`tool_output`を使います。

#### apply_patch

実Codexの`apply_patch`は、patch全体を`tool_input.command`へ入れます。Filesystem adapterは行単位のparserで`Add File`、`Update File`、`Delete File`、`Move to`を抽出します。親commandは監査用の`operation_container`とし、fileごとに`operation_control`、追加内容の`operation_added`、削除内容の`operation_removed`を作ります。

resource更新として採用するのは、同じsession / `tool_use_id` / tool名 / workspaceのPostToolUseが成功した場合だけです。Post outcomeはPost eventとoperationの組み合わせごとに保存します。`failed`または`unknown`ではsnapshotを取らず、resource更新を確定しません。

```text
operation_added(file A)
  -> written_to
resource_version(file A)

previous resource_version(file A)
  -> updated_from / moved_to
new resource_version(file A)

previous resource_version(file A)
  -> deleted_by
operation_control(file A)
```

`operation_added`だけをcontent-bearing fragmentとしてsimilarityとsource bindingの候補にします。`operation_container`、`operation_control`、`operation_removed`は監査用であり、一般類似度へ入れません。これにより、複数file patchのfile Aにだけ含まれる内容をfile Bへ伝播させません。

patchは更新後ファイル全体を含まないため、patch commandやoperation fragmentのhashをファイル内容hashとして代用しません。成功Post後のbounded snapshotで対象ファイル全体を安定して読み切れた場合だけ、そのSHA-256をresourceの`content_hash`に使います。captureできない場合はhashless resourceへfallbackします。moveではsourceの削除とtargetの現在内容を別々に確認し、deleteでは不在を確認できた場合だけtombstoneを作ります。

#### Bash filesystem

実Codexのshell実行は`tool_name: Bash`、commandは`tool_input.command`として観測されます。完全なshell ASTは作らず、静的lexerが理解できる`;`、`|`、`&&`、`||`でcommandを`bash_segment`へ分けます。各segment内でpathを静的に確定できる次の形式だけを限定的に認識します。

```bash
cat file.txt
cat -- "dir/file name.txt"
cat source.txt > destination.txt
printf text > output.txt
printf text >> output.txt
command 2> error.log
command &> combined.log
```

読み込みpathはPreToolUse時点でresourceから該当segmentへ接続します。external sinkも該当segmentだけへ接続し、親command全体を情報の入力nodeにしません。pipeの場合はsegment間に`piped_to`を作ります。これにより、同じpipelineに`curl`などのexternal sinkが含まれる場合、実行前でも次の経路を作れます。

```text
protected source
  -> resource version
  -> read_by
Bash segment
  -> submitted_to
external sink
```

単純な`cat`がPostToolUseまで完了した場合は、resourceからBash tool outputへ`read_from / bash_cat_output`も作ります。pipe、command separator、output redirectを含む複合commandでは、aggregate outputを元ファイルの直接出力と断定せず、このedgeを作りません。

リダイレクトwriteは、保存されたPost outcomeが`succeeded`の場合だけresource versionへ反映します。Bash stdout本文は自由に偽装できるため、本文に成功・失敗文字列があるだけでは成功としません。Codex CLI `0.142.5` / `gpt-5.5`の実Hookでは成功したno-output Bashと失敗した`false`の両方が空文字responseだったため、現時点ではどちらも`unknown / success_unconfirmed`となり、実Codex Bash snapshotは取得しません。

- `>` / `&>`: commandから新resourceへ`written_to`を作り、古いresourceのlineageは引き継がない
- `>>` / `&>>`: `written_to`に加えて、古いresourceから新resourceへ`updated_from`を作る

同じtool callで同じtargetへ複数回writeする場合は最終writerだけをcaptureし、先行operationを`superseded_by_later_operation`にします。`&&` / `||`では各segmentの実行有無をPost全体から確定できないため`execution_unknown`とし、pipeを含む複数writerが曖昧なら`ambiguous_final_writer`としてresourceをmaterializeしません。

変数展開、command substitution、backtick、glob、brace、heredoc、subshell、cwd mutator、shell reserved grammar、`/dev/null`などは確定pathとして扱いません。unquoted newline / CRLFはcommand境界、unquoted commentは非実行領域、backslash-newlineは継続行としてtokenizeします。現段階では完全なBash parserではなく、理解できる静的構文だけをcommand planとして受理するallowlist recognizerです。planを作れないcommandではfilesystem operationを生成しません。

### Search adapter

Search adapterは、Search toolのquery inputを `sink_candidate: external_search` として構造化します。

対象とするtool名は、正規化後に次のいずれかになるものです。

- `search`
- `web_search`
- `websearch`
- `web_search_query`
- `browser_search`
- `internet_search`

対象fragmentは次の条件を満たすものです。

- `phase = pre_tool_use`
- `artifact_role = tool_input`
- `semantic_role in {"query", "search_query"}`

Search outputは外部流出先ではないため、sink candidateにはしません。

### Bash adapter

Bash adapterは、shell command inputを外部送信候補の `sink_candidate` として構造化します。

対象とするtool名は、正規化後に次のいずれかになるものです。

- `bash`
- `shell`
- `exec`
- `command`
- `terminal`
- `run_command`

対象fragmentは次の条件を満たすものです。

- `phase = pre_tool_use`
- `artifact_role = tool_input`
- `semantic_role = command`

静的command planを作れる場合は、`bash_segment`ごとに外部送信patternを分類します。親commandは`operation_container`として一般類似度から外し、sink candidateは実際に外部送信を行うsegmentへ接続します。pipeで接続されたsegment間には`piped_to` edgeを作ります。planを作れないcommandではfilesystem operationを生成せず、引用符、comment、改行、control operatorを区別する非実行tokenizerで既知external commandだけを保守的に拾います。coarse fallbackはpayloadを解決済みとせず、protected sourceが有効ならexact policyで安全停止します。

- `curl`、`wget`、`http`、`httpie`
  - `external_http_request`
- `scp`、`sftp`、`rsync`、`ssh`
  - `external_file_transfer`
- `git push`
  - `external_git_publish`
- `gh pr create`、`gh issue create`、`gh gist create`、`gh release upload`
  - `external_git_publish`
- `npm publish`、`pnpm publish`、`yarn npm publish`、`twine upload`、`cargo publish`、`docker push`
  - `external_package_publish`
- `wrangler deploy`、`vercel deploy`、`netlify deploy`、`aws`、`gcloud`、`az`
  - `external_deploy`

redirectはFilesystem adapterがsegment単位のread/write operationとして扱います。pipeはsegment間edgeとして扱います。shell runtimeの`-c`、`env` / `command` wrapper、`eval`、`$()` / backtick内の既知external commandもsink visibilityだけは保ちます。ただしstdin本文そのもの、command substitution、heredoc、動的pathを値や個別nodeへ展開する完全なshell解析は行いません。

この分類は「実network接続を観測する仕組み」ではなく、既知command patternの分類です。Pythonの`requests`、Node.jsの`fetch`、raw socket、custom binary、wrapper経由などを完全には網羅しません。現在はbounded static analysisで補い、それでも不明なcallを`unknown`として保守的に扱います。protected flowが初見unknownへ到達した場合は分類を待たず実行前denyし、public-only unknownは値非保持queueと人間reviewで分類を改善します。現行設計は[Externality Judge](ExternalityJudge.md)、研究上の位置付けは[現行研究方針](../研究/現行研究方針.md)を参照してください。Codex network proxyを低レイヤー観測へ使う調査と不採用理由は[履歴資料](../履歴/調査/NetworkEgress観測とAudit改善計画.md)に保存しています。

### MCP adapter

MCP adapterは、MCP tool call inputを外部送信候補の `sink_candidate` として構造化します。

実Codexではtool名が`mcp__<server>__<tool>`となり、`tool_input`はMCP toolへ渡すraw argumentsです。adapterはこのtool名からserverとtoolを分離し、raw argumentsを入力として扱います。従来の`server` / `tool` / `arguments`で包んだimport形式も互換入力として維持します。

対象とするtool名は、正規化後に次のいずれかになるものです。

- `mcp`
- `mcp_call`
- `mcp_tool_call`
- `mcp_server_tool_call`
- `mcpserver_tool_call`

tool名が一致しない場合でも、tool inputに `server` / `tool` / `arguments` のようなMCP相当の構造があれば対象にします。

初期分類は次の通りです。

- Slack、Gmail、mail系serverのsend、post、message、create系tool
  - `external_message`
- GitHub serverのissue、pull request、gist、comment、release、upload系tool
  - `external_git_publish`
- Google Drive、Docs、Sheets、Notion、Linear、Jira系serverのcreate、update、comment、share、send、upload系tool
  - `external_api_call`
- unknown serverでもsend、post、create、update、upload、publish、share、comment系tool
  - `external_api_call`

MCP adapterは、real Codex名`mcp__<server>__<tool>`にexactかつcase-sensitiveで一致するversioned profileを先に解決します。profileはclosed-worldなscalar shape、data / control / file分類、redactable subset、sink type、Post input stabilityを1つのimmutable objectで定義し、adapterと将来のredaction plannerが同じregistryを参照します。初期built-in profileは実Codexで観測した`mcp__tooluseproxy_e2e__publish_text`だけで、必須の`/content` stringをdata / redactableとします。control fieldを含むmulti-field profileは汎用設計のsynthetic test fixtureで検証し、built-inの実schemaと混同しません。未確認のSlackやGitHub schemaを推測してprofile登録しません。

valid profileでは、現在inputに存在するdata fieldとcontrol fieldを1 JSON Pointer = 1 fragment = 1 sinkとして接続します。controlも外部serverへ送られるためsink-visibleにし、将来plannerでは書換不可として扱います。sink metadataにはprofile / registry version、status、absolute / relative pointer、field class、redactable flagを保存し、本文を複製しません。profileとregistryはfrozen dataclassとimmutable tupleで構成されるため、semantic versionはobjectごとに一度だけ計算してprocess内へcacheします。plannerも同じcall内ではversion文字列を一度だけ取得し、sink件数ごとのJSON再生成とSHA-256を行いません。

exact profileのshape不一致やfragment不足では既知fieldだけを部分適用せず、arguments内の全scalar valueとJSON object keyを`shape_rejected` / `fragment_incomplete` fallback sinkへ接続します。unprofiledなwrite-like toolもmessage-like keyだけに絞らず、scalar valueとkey nameを保守的にsink化します。これにより、protected textをJSON keyとして送る経路もsource bindingできます。key nameは一般語による誤taintを避けるため、source bindingとartifact間伝播の両方をraw case-sensitive exact一致だけに限定し、substring / shingle一致を使いません。JSON rootはcontainerとしてsource binding対象外です。scalar fragmentは値が同じでもpointerごとに保持し、MCP以外の一般類似度ではartifact内の同値payloadを再びcanonical dedupします。同一sessionで同じ値が繰り返される場合、artifact graphは全過去nodeへの完全DAGを作らず、各fieldを直前eventの同値代表へ接続する時系列chainにします。同値candidateがあればshingle比較を省略し、full rebuildとincremental queryの両方でedge candidateを1件に揃えます。

MCP policyがopt-inで有効なworkspaceでは、real MCP inputをartifact生成とDB初期化より前にbounded preflightします。compact canonical JSONが32 KiB以下、dict memberとarray elementが合計32以下、rootを0とした深さが8以下の場合だけ通常解析へ進みます。MCPの`get` / `list` / `search`もqueryをserverへ送るためexternal sinkです。上限超過は本文を出さない固定理由でPreToolUse denyし、artifact / DB / graphを作りません。

標準JSON decoderより前では、先頭1 MiBからtop-levelの`tool_name`と`cwd`だけを最大4 KiB/memberで静的抽出します。実Codex名`mcp__<server>__<tool>`かつready workspaceと確定したcallを、envelope全体1 MiB、container深さ64、numeric token 128 chars、finite numberというraw gateの対象にします。上限超過はread/write名にかかわらず固定理由でdenyします。top-level ownerまたはworkspaceを確定できないPreToolUseも安全停止し、別adapterやworkspaceを推測しません。既知の非MCP toolは残りを読み、従来の処理へ進めます。Hook JSONはUTF-8・BOMなしを境界契約とし、UTF-16 / UTF-32やraw NULはdecoderへ渡しません。この抽出はshellや任意JSONの意味解析ではなく、Codexがsmall envelope memberを`tool_input`より前に出す実payload契約に限定したsafety gateです。

`search`、`read`、`get`、`list`などのread-only toolも、queryとargumentsをMCP serverへ送るexternal sinkです。tool名のwrite-like verb分類は`external_message`や`external_git_publish`などsink種別の精密化にだけ使い、external boundary自体を解除しません。`get_or_post`、`get_and_comment`、`get_or_release`のようなcompound名もmutation種別を維持します。server固有の副作用を完全には判定できないため、fallback sinkは安全側のcoverageとして残し、redaction適格性は与えません。運用時は実schema fixtureを追加してからprofileを増やします。

### Codex final answer adapter

Codex final answer adapterは、Codexの `Stop` hook payloadに含まれる最終応答を `sink_candidate: final_answer` として構造化します。

対象fragmentは次の条件を満たすものです。

- `phase = stop`
- `artifact_role = final_answer`
- `semantic_role = final_answer`

現在のparserは、実Codexの`Stop` payloadにある`last_assistant_message`を優先し、旧形式の`final_answer`、`response`、`assistant_response`、`message`も互換入力として`final_answer` artifactへ保存します。

```text
Codex Stop payload
  -> artifact_fragment(final_answer)
  -> sink_candidate(final_answer)
```

`final_answer` は外部tool送信ではなく、ユーザーへ表示される出口です。`detect_leaks.py` はdefaultでは `external_*` sinkだけをfindingにし、`--include-final-answer` を指定した場合に `final_answer` をfindingへ含めます。

## 現在の処理順

```text
Hook event
  -> event / artifact / artifact fragmentを保存
  -> PreToolUseでoperation / Bash segmentを保存
  -> PostToolUseでoperation outcome / bounded snapshotを保存
  -> adapterがoperation / segment evidenceを解釈
  -> resource versionとstructured edgeを生成
  -> similarity edgeと統合
  -> protected sourceをpathまたは内容でbinding
  -> lineageを伝播
```

`scripts/rebuild_lineage.py`を実行すると、adapter解析も同時に実行されます。

```bash
python3 scripts/rebuild_lineage.py \
  --db .tooluseproxy/events.db \
  --workspace-root "$PWD" \
  --rebuild-graph
```

生成されたresourceは`resource_versions`、sink candidateは`sink_candidates`、edgeは`information_flow_edges`へ保存されます。

## 未実装のAdapter

次はまだ実装していません。

- Bash adapterの動的shell解析
  - command substitution、heredoc、shell変数、glob、subshell、一般shell ASTを構造化する
  - sed、awk、grep、rg、head、tail、cp、mv、tee、Python経由のfile I/Oをoperation化する
- MCP server固有の分類拡張
  - 実際のwrite/read tool名に基づいて分類ルールとfixtureを増やす

Bashは理解できる静的segment、pipe、cat、redirectだけをallowlistで扱います。未知構文を推測してfilesystem edgeへ変換しないことで、誤ったpathや実行結果を確定しない方を優先します。

## 現在の制限

- tool名とJSON keyが許容形式に一致しない場合、Filesystem adapterは反応しない
- copy、一般的なrenameは未対応。Codex形式の`apply_patch`によるAdd/Update/Delete/Moveには対応する
- Bash filesystemは静的な`cat`とredirectionだけを対象とし、sed、awk、grep、rg、head、tail、cp、mv、tee、Python経由のI/Oは未対応
- snapshotは成功Postと静的operationに限定され、workspace全体や無関係な外部processの変更は検出しない
- bounded capture対象外、上限超過、symlink、race、I/O errorではhashless resourceへfallbackする
- snapshotはwrite後の現在状態であり、protected sourceの過去内容や更新前本文を保存するsource snapshotではない
- dedicated read outputが省略・切り詰められた場合、その出力由来hashはファイル全体を表さない
- 実Codex Bash Postはstructured statusを返さない場合があり、その場合はoperationを保存してもwrite snapshotとresource更新を確定しない
- 初期化後のPreToolUseでworkspace / session identityを解決できないeventは、別workspaceを推測せず実行前denyする。PostToolUse / Stopは不確かなderived graphを作らずadvisoryに留める
- MCP adapterのserver/tool分類は初期ルールに基づくため、未知serverは保守的に `external_api_call` として扱う場合がある
- Bash external sinkは既知adapterに加え、bounded static analysisで証明できない任意program・wrapperを保守的unknown sinkとして扱う。protected sourceが有効なworkspaceでは、完全なpayload確認ができないunknown external callを実行前denyする
- OS / proxyで接続を観測できても、TLS payloadやhosted Web Search / remote MCP内部の実payloadまではlocal process観測だけで確認できない

## 公式仕様との関係

Codex Hooksは`PreToolUse`と`PostToolUse`を含むライフサイクルイベントを提供します。またCodex app-serverは、絶対pathを扱う`fs/readFile`と`fs/writeFile`を提供しています。

- [Codex configuration reference](https://developers.openai.com/codex/config-reference)
- [Codex app-server API overview](https://developers.openai.com/codex/app-server#api-overview)

ToolUseProxyは、これらのtool固有形式を直接グラフ全体へ持ち込まず、adapterで共通edgeへ変換します。
