# 実プロジェクト試行の記録・比較・改善提案

更新日: 2026-09-05

## 目的

ToolUseProxyを有効にした実プロジェクトで通常作業を続けながら、どこで不要な停止、見逃し候補、判断不能、観測範囲の不足が生じるかを調べる。その結果から検出処理の改善点を漏れなくGitHub Issueへつなげる。

この仕組みは情報流記録そのものではない。既存の情報流記録を根拠として、判断の種類と件数だけを別の操作評価へ写す。保護対象の本文、命令文、URL、接続先、ファイルの場所は、操作評価、比較結果、GitHub Issueのいずれにも入れない。

## 記録する範囲

Maniの環境では、ToolUseProxyを有効にした全プロジェクトで`pilot-recording`を明示的に有効にし、継続評価の対象にする。ToolUseProxyを有効にしただけでは操作評価を保存せず、一般利用者向けの初期状態でも無効にする。

1件の操作評価を作るのは、ToolUseProxyが外部送信の可能性を判断した操作である。ローカルだけのファイル読み取りなどは既存の情報流記録には残るが、操作評価の1件には数えない。

ToolUseProxyへ届かないHosted Web Search、実行中処理への`write_stdin`、未確認の入れ子操作は、作業後にローカルのCodexタスク記録を読み、操作の種類と件数だけを範囲確認として残す。読み取れない場合は不明とする。内容は新しい記録へ写さない。

## 1操作の保存形式

SQLiteへ次の表を追加する。列名は実装時の名前であり、外部へそのまま公開しない。

### `pilot_observations`

| 項目 | 保存内容 |
| --- | --- |
| `observation_id` | 操作評価を識別する無作為なID |
| `observed_at` | 判断した時刻 |
| `workspace_id` | 正規化した作業場所をSHA-256で置き換えた`ws_v1_<sha256>`形式の内部参照。比較用の別名やGitHub送信には使わない |
| `event_ref_sha256` | 既存記録のIDをSHA-256で置き換えた参照値。元のIDや本文は複製しない |
| `product_version` | ToolUseProxyの版 |
| `detector_version` | 判定方式の版 |
| `settings_revision` | 設定の版 |
| `tool_family` | shell、MCP、関数、その他の閉じた分類 |
| `externality` | local、external、unknown、not_visible |
| `payload_resolution` | direct、file、lineage、unresolved、not_applicable |
| `evidence_source` | adapter、static、direct、resolved、lineage、fallback |
| `policy_action` | allowまたはblock |
| `reason_code` | 既存判断から作る閉じた理由番号 |
| `decision_ms` | ToolUseProxy内部の判断時間 |
| `review_state` | not_needed、pending、correct_block、unnecessary_block、unable_to_judge |
| `cause_candidate` | 自動分類した問題原因。材料不足はunidentified |
| `record_state` | complete、reconstructed、incomplete |

自由記述、raw Hook payload、command、URL、host、path、保護内容は列として用意しない。文字列の長さと許可値をSQLiteの制約で固定し、未知の値を自由記述として保存できないようにする。`pilot recent`と`pilot history`はローカル確認専用とし、`workspace_id`を含む出力を外部共有しない。

### `pilot_reviews`

停止確認と訂正を追記方式で保存する。

| 項目 | 保存内容 |
| --- | --- |
| `review_id` | 確認を識別するID |
| `observation_id` | 対象の操作評価 |
| `previous_review_id` | 直前の確認ID。過去の選択はこの履歴から参照する |
| `choice` | 新しい3択の選択 |
| `cause` | 原因の7分類。初期値は未特定 |
| `comparable_count_at_record` | 初回確認時の比較可能件数。訂正時も保持する |
| `recorded_at` | 確認または訂正の時刻 |

集計には最新の選択だけを使う。利用者がチャットに説明を書いても、その文章は保存しない。

### 問題履歴（`pilot_miss_events`と停止確認からの組み立て）

見逃し候補の申告、人工的な再現結果、問題原因の訂正を`pilot_miss_events`へ追記保存する。不要な停止と判断不能は、保存済みの停止確認の最新版から同じ問題形式へ組み立てる。元の停止確認履歴は消さない。観測不能・記録漏れの保存は第4段階で追加する。

| 項目 | 保存内容 |
| --- | --- |
| `problem_event_id` | 問題の記録を識別するID |
| `observation_id` | 対応する操作評価。観測不能なら空欄 |
| `symptom` | unnecessary_block、miss_candidate、reproduced_miss、unable_to_judge、not_visible、record_failure |
| `cause` | 問題原因の7分類 |
| `classified_by` | automaticまたはhuman |
| `previous_problem_event_id` | 訂正前の記録。初回は空欄 |
| `comparable_count_at_record` | 問題を記録した時点の、そのプロジェクトの比較可能件数 |
| `recorded_at` | 申告、再現、訂正の時刻 |

見逃し候補は、人工的な保護内容と送信先で再現できたときだけ`reproduced_miss`へ進める。再現用の内容はこの表へ保存しない。

### `pilot_record_failures`

保護判定には成功したが操作評価だけを保存できなかった場合に、時刻、`workspace_id`、失敗理由、後から補えたかだけを残す。`workspace_id`は同じ内部参照であり、比較用の別名やGitHub送信には使わない。既存記録から補えるものは`reconstructed`として復元し、補えない項目は不明にする。この失敗を理由に許可・停止の結果は変えない。既存の情報流解析または保護処理そのものが失敗した場合は、従来どおり安全側に停止する。

### 比較とIssue送信を管理する表

- `pilot_comparisons`: 比較ID、判定方式の版、対象期間、プロジェクト数、各件数、作成時刻を保存する
- `pilot_comparison_checkpoints`: プロジェクトと判定方式の版ごとに、どの20件まで比較済みかを保存する
- `pilot_issue_jobs`: 同一問題ID、比較ID、送信状態、GitHub Issue番号、再試行回数、閉じた失敗理由を保存する

比較結果の保存と比較済み位置の更新は1つのSQLite処理で行い、同時に複数のタスクが終了しても同じ比較を二重作成しない。GitHubの生のエラー文は保存せず、未導入、未認証、通信失敗、応答不正などの閉じた理由へ変換する。

## 停止確認

停止時の説明に、内容を含まない確認IDと、Codexが通常のチャットで次を尋ねる指示を加える。

- 正しく止めた
- 止める必要はなかった
- 判断できない

回答後、Codexはローカルの確認コマンドへ確認IDと選択肢だけを渡す。回答されなかった操作は`pending`のまま残すが、比較全体は保留しない。後から一覧を表示して確認または訂正できるようにする。

利用者が止める必要のあった操作を見つけた場合は、`tooluseproxy pilot recent`で時刻、道具の種類、許可・停止だけの一覧から操作評価IDを選び、`tooluseproxy pilot report-miss`で登録する。操作評価IDを特定できない観測不能操作は、タスクと道具の種類だけを閉じた値で登録する。原因調査用の説明文は操作評価へ保存しない。

## 比較結果

同じ判定方式の版について、比較可能な操作評価が20件以上あるプロジェクトが2つ以上になったら、タスク終了時に初回比較を作る。`pending`の停止は20件に含めず、除外件数として表示する。20件未満のプロジェクトは待たない。

初回比較後は、比較対象になった各プロジェクトで比較可能な操作がさらに20件ずつ増えるたびに継続比較を作る。判定方式の版が変わった場合は以前の件数と混ぜない。alpha.12以前の記録は集計処理の試験には使えるが、新しい20件には含めない。

比較結果には次だけを含める。

- 判定方式の版
- 対象期間
- プロジェクト数。プロジェクト名は含めない
- 全操作、許可、停止の件数
- 正しい停止、不要な停止、判断不能、未確認で除外した停止の件数
- 見逃し候補と、人工的な再現で確認できた見逃しの件数
- 外部性、送信内容解決、照合根拠、情報流追跡、観測範囲の分布
- 問題原因ごとの件数
- 判断時間の中央値と95パーセント地点
- 評価記録漏れと範囲確認の不明件数

通常利用では、許可された全操作が正しかったとは確認できない。このため、全体の正解率や見逃し率を算出しない。「観測した範囲の件数」として報告する。

## 問題分類

問題の現れ方と原因を分ける。現れ方は、不要な停止、見逃し候補、再現済み見逃し、判断不能、観測不能、評価記録漏れである。原因は次の7分類とする。

| 原因 | 意味 | 主な改善場所 |
| --- | --- | --- |
| `externality` | 外部へ出る操作かどうかの判断違い | adapter、静的解析、外部性規則 |
| `payload_resolution` | 実際に送る内容を取り出せない、または違う内容を選んだ | file、Git、archive、uploadの解決処理 |
| `protected_match` | 送信内容と保護対象の照合違い | exact、structured、lexical、将来のsemantic |
| `lineage` | 読み取り、変換、生成物、送信先のつながりが切れた、または誤ってつながった | 情報流追跡 |
| `coverage_boundary` | Hookへ届かない、継続入力を見られないなど観測範囲の不足 | Codex連携境界 |
| `explanation` | 判断自体よりも説明不足で利用者が判定できない | 停止理由と確認導線 |
| `unidentified` | 保存された構造情報だけでは原因を決められない | 人工的な再現から調査 |

自動分類は候補であり断定ではない。原因の訂正も履歴を残し、最新版だけを集計に使う。

自動分類は次の順で行い、途中で根拠が足りなくなったら`unidentified`にする。

1. 操作がHookへ届かなければ`coverage_boundary`
2. 外部操作かどうかの判定が期待と違えば`externality`
3. 外部操作だが送信内容を取り出せなければ`payload_resolution`
4. 送信内容を取り出せたが保護対象との照合が違えば`protected_match`
5. 直接照合は正しいが、情報の流れの接続が違えば`lineage`
6. 利用者が判断できない主因が説明不足なら`explanation`
7. 上記を構造情報だけで決められなければ`unidentified`

## GitHub Issueへの接続

比較で見つかった問題は、`unidentified`を含めてすべて改善提案Issueへつなげる。同じ判定方式、原因、理由番号、道具の種類から内容非保持の同一問題IDを作る。

- 同じ問題の開いたIssueがあれば件数と比較結果を追記する
- 同じ問題の解決済みIssueがあれば再度開いて追記する
- 一致するIssueがなければ新規作成する
- 原因が異なる問題は別Issueにする

Issueへ送る文章は許可項目の一覧から組み立て、禁止項目が混入していないことを機械確認する。Issueには対象プロジェクト数、操作数、停止確認の件数、原因、改善理由、人工的な再現例の作成方針、改善後に比べる数値を含める。個別の操作評価とプロジェクト名は含めない。

Stop Hookは比較結果と送信待ちの仕事をローカルへ保存するだけにし、通信を待たない。Hook終了後の別処理が`gh`を使ってIssueを作成または更新する。未導入、未認証、通信失敗の場合は送信待ちを残し、次回終了時に再試行する。失敗しても保護判定やローカル比較へ影響させない。コード、ブランチ、Pull Request、GitHub Projectの状態は自動変更しない。

### 1. 集計器と人工データ

状態: **完了（2026-09-05）**

新しい保存形式をPythonの型と閉じた値として定義し、人工データから内容非保持の比較を作る。alpha.12以前に相当する記録は`legacy`として新しい比較から除外する。ここではHookと本番DBを変更しない。

主な追加先:

- `hook_monitor/runtime/pilot_models.py`
- `hook_monitor/evaluation/pilot_aggregate.py`
- `tests/test_pilot_aggregate.py`

完了条件:

- 20件境界、複数プロジェクト、版の分離、未確認除外、継続20件を自動試験する
- 出力に禁止項目が存在しないことを試験する
- alpha.12以前の記録が新しい比較件数へ入らないことを試験する

実装結果:

- 各プロジェクトの20件目、40件目、60件目を同じ比較回として扱う
- 利用の少ないプロジェクトを待たず、同じ回に到達した2つ以上で比較する
- 同一入力集合から生成する比較ではプロジェクトの仮名を統一する。入力に新しいプロジェクトが加わると番号が変わり得るため、仮名を永続IDやIssueの重複判定に使わない
- 未確認停止と不完全な評価記録を20件から除外し、除外件数として示す
- 訂正履歴の循環と枝分かれを拒否し、最新版だけを数える
- 専用試験15件、全自動試験1055件、1590個の補助確認、コード検査、差分検査が合格した

第1段階の最終点検（#101）では、同じ操作への問題の重複登録を拒否し、停止確認訂正後の古い誤停止を集計から除外した。偶数件の中央値は中央2値の平均に修正した。見逃し候補から再現済みへの更新、入力順序によらない結果も回帰試験へ追加した。上記の全試験件数は最終点検前の実行結果であり、最終点検の検証結果はIssue #101へ別途記録する。

現段階の集計器は入力の最新状態から累積結果を再計算する純粋関数である。作成済み比較の保存、履歴を固定した比較、送信済み判定、同時実行時の一度だけの生成は第4・5段階で実装する。今回の試験合格をその実装済み証拠にはしない。

### 2. 操作評価の保存

状態: **ローカル実装・検証済み（Issue #102、未commit・未配布）**

保存形式v8に操作評価表を追加し、`pilot-recording`設定を追加した。既定値は無効で、通常の設定コマンドまたは`TOOLUSEPROXY_PILOT_RECORDING`環境変数で有効化する。現在の作業では利用者の実DBや設定を更新していない。

評価の保存は既存の保護判断が終わった後に行う。SQLiteだけが利用できない場合は、DBと同じ管理領域の再保存待ちに内容非保持の評価だけを残し、Stop時に最大32件ずつ再試行する。復元済みの待機記録は削除せず保持する。記録先全体が書けない場合は診断を出し、保存できたと扱わない。

人工の保護対象を使う実処理経路で、許可・停止・保護処理の例外・入力拒否を確認した。評価保存が失敗しても判断は変わらず、保護処理の例外は停止として残る。旧形式v7の退避・更新・復元と、配布物への同梱も確認した。全体試験1069件合格、2件スキップ、補助確認1590件合格。その後の入力拒否記録・復元試験の追加は対象試験238件、補助確認95件で確認した。

入力自体を読めない場合やプロジェクト・操作の識別ができない場合は、偽の操作IDを作って評価へ混ぜない。従来の停止を維持し、操作評価が存在するとは扱わない。この範囲の件数は第4段階で扱う観測範囲の確認対象とし、取得できなければ不明とする。識別済みの入力拒否と保護処理の例外は、不完全な評価として記録し通常の比較から除く。

SQLiteを次の版へ移行し、`EventStore`へ追記専用の保存・参照処理を加える。`runner.py`と`pre_tool_policy.py`で既存判断から閉じた項目だけを組み立てる。判断時間はPreToolUse受付から判断完了までを単調時計で測る。

主な変更先:

- `hook_monitor/runtime/storage.py`
- `hook_monitor/runtime/models.py`
- `hook_monitor/runtime/runner.py`
- `hook_monitor/runtime/pre_tool_policy.py`
- `hook_monitor/runtime/settings.py`

完了条件:

- 一般向け初期状態では記録されない
- Maniの設定では対象となる全操作が記録される
- 本文、命令文、URL、接続先、ファイルの場所が新表へ入らない
- 評価保存失敗が許可・停止を変えず、保護処理失敗は従来どおり安全側に止まる
- 旧DBの更新とrollback試験が通る

### 3. 停止確認と訂正

状態: **ローカル実装・検証済み（Issue #103、未commit・未配布）**

全体試験1077件合格、2件スキップ、補助確認1590件合格。その後の比較位置の固定、復元しても不完全な評価を比較可能へ変えない修正、確認案内の追加失敗でも停止を維持する修正を含む対象試験256件、補助確認95件が合格、1件スキップ。コード検査・差分検査も合格した。実際のチャットUIを用いた利用確認は第6段階で行う。

保存形式v9へ停止確認と見逃し候補の追記表を追加した。同じ依頼IDの再試行は重複せず、訂正では直前の確認IDが一致しなければ拒否する。別プロジェクトの確認ID、許可した操作への停止確認、自由記述を拒否する。操作評価自体は変更しない。

`tooluseproxy pilot review`、`pilot pending`、`pilot recent`、`pilot amend`、`pilot report-miss`を追加する。停止結果には確認IDだけを加え、Codexへ3択の質問を促す。

確認は`review 確認ID 選択値 --request-id 依頼ID`、訂正は`amend 確認ID 選択値 --request-id 新しい依頼ID --previous-id 直前の確認履歴ID`を使う。各コマンドは`--workspace`と、必要なら`--db`または`--data-dir`を指定できる。`history`で訂正前を含む履歴を確認できる。自由記述を保存する引数はない。

人工データで再現を確認した後だけ、`reproduce-miss 確認ID --request-id 新しい依頼ID --previous-id 候補ID --artificial-reproduction-confirmed`を使う。このコマンドは確認済みという申告を保存するもので、実データの外部送信や再現試験の自動実行はしない。

主な変更先:

- `tooluseproxy/cli.py`
- `hook_monitor/policy/codex_output.py`
- `hook_monitor/runtime/storage.py`
- `tests/test_pilot_review.py`

完了条件:

- 3択以外を拒否する
- 自由記述を保存しない
- 訂正前の履歴を消さず、集計には最新版だけを使う
- 未回答でも次の比較を止めない
- 見逃し候補と人工的に再現できた見逃しを区別する

### 4. タスク終了時の自動比較と範囲確認
