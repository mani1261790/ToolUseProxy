# 依存エッジ生成の先行研究

調査日: 2026-09-24。以下は原論文の本文・付録を確認した設計調査。
論文の実装を動かした再現実験ではなく、ToolUseProxyへの適用案は未実装。
既存製品の計測値と論文の評価値を同一条件として比較しない。

## 近い研究と適用範囲

AgentArmorの§5.4本文とTable 1には異なる評価値があるため、今回の選定根拠に
検出率の数値は使わない。論文の成功率だけで実装方式を採用しない。

## 「直近5ノードだけ」について

局所的な文脈だけを抽出に使う先例はある。しかしZepの過去4メッセージは
実体抽出の文脈幅であり、既存グラフとの関係を古いものから一律に切る数ではない。
「ToolCallの直近5件だけで情報継承が十分に復元できる」という根拠は、今回読んだ
研究からは得られていない。5は評価する設定値の一つとして扱う。

## 適用案（論文の再現ではなく、本プロジェクト向けの設計仮説）

1. 新規ToolCallの記録とノード追加は機械処理する。
2. 資源の内容版、実際の読み書き、既知の引数・出力参照から確定できる直接関係を追加する。
3. 意味推定の候補は、直近の小さな窓、参照資源の生成元、過去記録の検索結果を統合する。
   検索は候補を見つけるために使い、類似度だけで因果エッジを確定しない。
4. 候補と今回の情報単位をまとめた固定パケットでLLMに継承関係だけを判断させる。
   実装探索・全履歴の再解釈・許可判断は依頼しない。
5. 証拠版が同じ判定は再利用する。情報源の保護登録変更はポリシー検査へ反映し、
   同じエッジを作り直さない。
6. 外部送信では、既存グラフを機械的に辿る。探索の深さを直近窓と混同しない。

候補検索で取りこぼすとLLMがその依存を判断する機会自体を失う。
候補数を減らしたことだけを成功条件にせず、候補の再現率と最終判定を両方測る。
モデル内部・思考・実行環境の置換を必要とする方式は、プラグイン実装の前提にしない。

## 実装変更の前に比べる条件

- 現行の全履歴、直近5件のみ、直近5件＋資源生成元＋履歴検索。
- 原文、言い換え、無関係な内容、長い間隔後の再利用、別セッションでの再利用、
  ファイルの上書き、複数情報源が混ざる一つの出力。
- 候補に正しい生成元が含まれる割合、意味エッジの精度、見逃し、誤遮断。
- LLM呼び出し数・入力量、初回と再利用時の時間、p50/p95。
- 合成記録での比較と実Desktop Hookの受入を分ける。

現時点では候補制限の本番導入も、Graphiti等の依存追加も行っていない。
