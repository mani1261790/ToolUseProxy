# 展示の見せ方の案

主画面は既存のリアルタイムログビュワーを軸にする。来場者が追いたいのは、
「AIに何を頼んだか」「何をしようとしたか」「何が止まったか」のつながり。
保護する人工ファイルと公開してよい人工ファイルを、短い名前で明示する。

## 案A：来場者が操作を選ぶ

横長の画面に、左はAIへの依頼と返答、右はそのセッションのログビュワーを並べる。
来場者の操作は「公開情報から要約を作る」「保護情報を外へ送ろうとする」など
2〜3個の短い選択に絞る。専用の人工workspaceと受信先を使う。

ログはこの展示project/sessionに固定して開始し、最新の呼び出しを自動選択する。
ToolCallの名前、入力、出力、停止理由を現在の詳細欄で追えるようにする。
主催側で操作できる詳細フィルターは今のポップアップに残す。

## 案B：説明者が進める

同じデモを説明者が操作し、画面の大部分をログビュワーに使う。
依頼の短い文章を上に表示し、正常な操作から保護対象の送信までを順に見せる。
大きな会場画面では細かいJSONを常時出さず、選択したI/Oと理由を中心にする。

## 伝える順番

1. 公開情報の操作が進む。
2. 保護対象を使う操作がログに現れる。
3. 送信前のblock判定と、専用受信先での到達結果を別々に確認する。
4. 必要なら、将来予測による追加停止の試験を別のデモとして見せる。

予測は主画面の必須条件にしない。実結果がある場合だけ表示し、既存保護による停止と
「将来予測による追加停止（試験）」を区別する。架空の予測経路や精度は描かない。
予測できなかった場合も隠さず、通常の保護が動く様子を説明する。

両案とも合成した録画をリアルタイム実行に見せかけない。録画を予備として使うなら
「録画」と表示する。現時点では画面案であり、展示シナリオの実装・実演受入は別。
新しい画面の実装前に、来場者操作型か説明者操作型かを決める。
