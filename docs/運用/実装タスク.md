# 実装タスク計画

ToolUseProxyの現在地、優先順位、完了条件をまとめる実装ロードマップです。2026-07-19時点の実装基準は`70f9711`以降です。

日々のStatusと担当単位は[GitHub Issues](https://github.com/mani1261790/ToolUseProxy/issues)と[Project #1](https://github.com/users/mani1261790/projects/1)を正本とし、この文書は複数Issueにまたがる順序とrelease gateを説明します。過去の詳細な実装履歴はGit履歴とclosed Issueに残します。

## 結論

当初の3目標は、いずれも中核実装まで到達しました。

| 目標 | 現在の判定 | 残っていること |
| --- | --- | --- |
| Codex Plugin化 | alpha.3の機能基盤は完了 | 公開artifact、release metadata、cross-platform lifecycle E2E |
| 類似度精度 | profile v2をproduction化 | 公開compound反例、有限candidate cap、repository外holdout |
| secret JSON登録のagent支援 | 明示承認型workflowは完了 | 実Plugin onboarding、Windows、runtime observation / auto-enrollの研究判断 |

従って、次は新機能を広げる前に「配布物を固定して実環境で再現できる状態」をP0とします。そのartifactでdogfoodした後、類似度v2.1とonboardingを並行して進めます。

- Ubuntu Python 3.11 / 3.12 matrixとmacOS Python 3.12 package smoke定義
- support matrix、known limitations、privacy / local data retention契約
- clean artifactのisolated Codex installからprotect / allow-deny / Stop / trace / removeまでのsynthetic dogfood Phase A
- reproducibleなwheel / sdist / Plugin ZIP、release manifest、SHA256SUMS、CycloneDX 1.7 SBOM、release notes候補の一括builder / verifier
- Plugin remove後のdata保持と、stale-safeな`uninstall plan / apply`による管理data削除workflow
- immutable alpha.1 / schema v1からalpha.3候補 / schema v4へのupgrade、backupを使うsafe rollback、disable / remove rehearsal
- `init --codex`、`doctor`、`status`、`trace`
- Hook trustを迂回しないsetupと、未初期化・schema不整合時のfail-open

- `exact -> canonical exact -> substring -> token-equivalent -> shingle Jaccard`の説明可能な比較器
- artifact / sourceでminimum lengthを分けたdual-objective candidate ranking
- production helperをoffline評価、full rebuild、incremental SQLiteで共用
- 38 pair、9 E2E、16 retrieval poolをdevelopment / validationで固定
- pair F1、candidate recall、E2E action、full / incremental parityが全て`1.0`
- false blockとprivacy exposureが`0`
- dataset digest `241a4f536ea53694b8172accc5a528961673a843983f99702651357cff3619b3`

### Protected source候補の提案・承認登録

- bounded offline `protect scan`と明示pathの`protect suggest`
- 値を含めないcandidate summaryと、1件ずつのexact proposal
- `approve` / `reject` / `ignore`、detector-version単位の再提示抑止
- expected manifest hashによるCAS、workspace lock、atomic replace、fsync、recovery
- legacy manifestの`migrate plan` / exact approval / `migrate apply`
- 32 workspace・416 filesの評価でfile / selector precision・recall・F1が`1.0`、privacy exposureが`0`
- coding agentによる無承認登録、一括承認、Hook中のscan / migrationは意図的に禁止

### Trace / Detect / Stop基盤

- workspace・session分離されたevent / artifact / resource / sink graph
- structured adapter、bounded snapshot、source binding、lineage、finding、policy decision
- opt-inのBash / MCP PreToolUse denyと、Stopの`continue_review`
- hash-bounded監査、atomic offline publish、reproducible analysis run
- runtime redactは複数Hook rewriteの最終採用inputを証明できないため無効

1. 固定済みartifact契約をCIで維持する

   - Windowsはexperimentalとし、未対応機能を成功扱いせず明示エラーにする
2. support / privacy contractを維持する

   - local data retention、plaintext、telemetryなしの契約を維持する
3. 公開metadataを揃える
   - LICENSE
   - privacy / data retention / telemetry方針（文書化済み）
   - support matrixとknown limitations（文書化済み）
   - version整合、release notesの雛形

完了条件:

- wheel / sdistの内容が機械的なallowlist testで固定される

- license、privacy、support / unsupported範囲、local data保持が文書化される

### P1: 固定artifactをdogfoodする

担当Issue: [#19](https://github.com/mani1261790/ToolUseProxy/issues/19)、[#18](https://github.com/mani1261790/ToolUseProxy/issues/18)

immutableなcommitまたはprerelease候補から、次の一連を新しい環境で検証します。

Hook payloadをinstalled launcherへ渡す自動Phase Aは、clean artifact build、isolated marketplace install、init / status、candidate approve、public Bash / MCP allow、protected Bash / MCP deny、Stop review、decision trace、remove後のcode残留0とdata保持まで実装済みです。Hook trustと実tool invocationのside effect 0は自動で迂回・代行せず、pre-release候補のmanual Phase Bで確認します。手順とvalue-freeな結果schemaは[Pluginドッグフード](Pluginドッグフード.md)を参照してください。

1. marketplace add / Plugin install
2. Hook definitionのreview / trust
3. `init` / `doctor` / `status`
4. `protect scan` → exact proposal → `approve`
5. public Bash / MCP allow
6. protected Bash / MCP deny、final answer review
7. `trace`で根拠を確認
8. Plugin update後のapproved source保持とstale proposal処理
9. Plugin remove後のHook残留確認とlocal data保持確認

完了条件:

- protected canaryの外部副作用、raw値露出、active Hook残留が0件
- public fixtureのfalse blockが0件
- install開始から最初のprotected blockまで5分以内
- update後もapproved sourceと監査dataが保持される
- failure時に`doctor`または導入文書が次の操作を説明できる

### P1: Similarity v2.1をadversarial評価する

担当Issue: [#20](https://github.com/mani1261790/ToolUseProxy/issues/20)

現profileは20文字以上・異なる英字10種類以上の値をdistinctive secretとして扱うため、`documentationreference`のような公開compoundもsource bindingで誤認し得ます。またartifact 50 / source 200のcandidate上限は意図したbounded heuristicであり、両rankingのquota外になる任意のadversarial集合までは保証しません。

1. 長い英字の公開compoundをnegative corpusへ追加する
2. alpha-only secret positiveと同じ形式のhard positiveを維持する
3. global thresholdを安易に緩めず、selectorやsecurity fieldなどsource-binding固有のsignalを比較する
4. 1,000〜10,000候補の生成poolでrecall、saturation率、SQLite parity、p95 latencyを測る
5. developmentで案を固定し、validationとrepository外holdoutを最後に評価する

現在地: 1〜4の基盤、development規則、独立validation familyまで実装済みです。公開compoundの偽陽性を導入前baselineで再現し、`selected_security_field`に限ってalpha-only containmentを許可するsource-binding限定規則へ固定しました。freeze後に比較器を変更せずvalidationも全gateを通過したため、次はrepository外holdoutの入力・集約結果schemaを定義します。

完了条件:

- 新しいpublic compoundを全件TN、alpha-secret hard positiveを全件TPにする
- 既存v2のpair F1、candidate recall、E2E action、parity `1.0`とfalse block `0`を維持する
- full / incremental / SQLiteの候補集合と判断が一致する
- Hook latency budgetとprivacy gateを悪化させない
- capの限界を隠さず、saturationを観測可能にする

### P1: Protected source onboardingを閉じる

担当Issue: [#18](https://github.com/mani1261790/ToolUseProxy/issues/18)

明示承認型のalpha scopeを実Pluginで通し、Issue本文と操作文書を実態に合わせます。runtime observed-path detectorとopt-in auto-enrollは、初回alphaの必須機能へ混ぜません。

完了条件:

- install済みPluginからscan / suggest / approve / reject / ignoreをE2Eできる
- candidate summary、agent説明、監査、errorにraw protected値が出ない
- source / manifest変更時にstale proposalを安全に拒否し、再scanへ誘導する
- Windowsを対応するかunsupportedとするかを明記する

runtime observed-pathはHook latency / privacy budget付きの別設計、auto-enrollはprecision 99%以上を独立評価できた場合だけopt-in候補とします。

## 条件付きの長期課題

次は近いreleaseへ入れず、成立条件が揃ったときだけ再評価します。

- runtime redact renderer: CodexまたはPluginがexclusive enforcement / 最終rewrite確認を提供した場合
- bounded evidence capsule: retention・監査要件が具体化した場合
- runtime observed-path scan: p95 latencyとraw-value非露出を同時に証明できる場合
- opt-in auto-enroll: rule別precision 99%以上をrepository外でも確認した場合
- local embedding: lexical v2.1のfailure taxonomyに意味類似の実需要が残り、observe-onlyでprivacy / latencyを評価できる場合
- Bashの一般AST: 未知構文を推測せず、対象commandを安全に限定できる場合
