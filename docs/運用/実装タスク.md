# 実装タスク計画

ToolUseProxy の次に実装する内容を整理する作業計画です。

現在の研究フェーズは第3段階「情報流出をStopする」の途中です。情報流グラフ、外部sink、final answer sink、最小漏えい検知、policy decision、Stop継続、Bash/MCP PreToolUse denyまで実runtimeへ接続しています。apply_patch/Bashのoperation単位fragment、成功PostToolUse後のbounded snapshot、複数workspace分離、workspace単位のoffline run snapshot、MCP exact profileと全scalar value / JSON key sink coverage、critical blockを維持するredaction preview planner、hash-only audit、future renderer向けのdormant decision linkageとPost confirmation、O(1) hash-only event sidecarも実装しました。offline rebuildはlive derived stateとcompleted run snapshotを1 transactionでatomic publishするようになりました。`PermissionRequest`は公式source、実payload、実Codexのdeny / allowを検証し、汎用runtime接続を追加しないと判断しました。dormant Post confirmationのproduction no-opとprotected block fallbackは一つ前のsize-only sidecarで実Codex再検証済みです。最終hash-only sidecarとdecision linkageはlocal testで検証し、runtime配線を追加していません。実Codex再実行はusage limitにより未完了です。複数rewriterはCodex 0.142.5の一般Hook環境では安全に解消できないため、rendererと`updatedInput`は実装しません。全runtime runの履歴snapshotもHook latency、保存量、plaintext retentionを増やすため見送り、監査要件が具体化した時点でnon-allow decisionのbounded evidence capsuleまたはsession checkpointを設計します。

## 現在の到達点

実装済みの基盤は次の通りです。

- Codex Hooks から `PreToolUse` / `PostToolUse` / `Stop` の payload を受け取る
- Hook payload を event、artifact、artifact fragment として SQLite に保存する
- artifact fragment 間の exact、substring、shingle 類似度から情報流 edge を作る
- JSON container rootとPostToolUse側の複製入力を除外し、session/turn境界内のcanonical fragmentだけを比較する
- protected source を後から graph へ binding する
- source binding を起点に lineage を伝播する
- Filesystem adapter により、ファイル read/write を resource version 経由の edge として表現する
- 実Codexの`apply_patch`をAdd/Update/Delete/Moveへ分解し、成功したPostToolUseだけをresource versionへ反映する
- apply_patchのfile operationごとにadded/control/removed fragmentを分離し、複数file patchの過剰taintを防ぐ
- Bashを静的な`;` / `|` / `&&` / `||` segmentへ分け、cat、redirection、external sinkを該当segmentへ限定する
- Post outcomeをPost event / operation単位の履歴として`succeeded` / `failed` / `unknown`で保存する
- 成功を確認できたPostToolUse後だけ、静的pathをworkspace、byte、path数、時間上限内でsnapshotする
- snapshot本文を既定で保存せず、安定した全file読込のSHA-256、capture status、move/delete tombstoneをresource versionへ接続する
- operation outcomeとsnapshotをsession差分解析へ統合し、稀な重複時も同一sessionだけを再構築する
- Bashの静的な`cat`とredirectionをresource versionへ接続し、protected pathから同一segment内のexternal sinkまで実行前lineageを作る
- Search / Bash / MCP adapter により、外部へ出る可能性があるtool inputを `sink_candidate` として表現する
- Codex final answer adapter により、最終応答を `sink_candidate: final_answer` として表現する
- `trace_lineage.py` と `export_graph.py` により、source から sink candidate までの経路を確認する
- canonical workspace rootからidentityを作り、event、source、cursor、resource、sink、edge、analysis runを分離する
- runtimeは現在eventと同じworkspace・sessionだけを差分更新し、別workspaceの同名source/pathを判断へ混ぜない
- completed offline runのedgeとnode metadataをimmutable snapshotへ固定し、CLIのscope指定を必須にする
- MCP current callの全critical findingを集約し、全件をprofile済みdata pointerとraw source chunkへ直接対応できる場合だけwhole-field redaction previewを作る
- preview planにはhash、scope、profile version、finding単位targetだけを残し、reject時はpartial targetと候補本文を破棄する
- current-call全critical findingの後にpreview plannerを呼び、参照するworkspace-owned source chunk IDだけを32件以下で取得する
- eligible / rejected planと全targetをplaintext本文なしのimmutable auditとして1 transactionで保存する
- previewのsource取得、planner、保存の失敗で先にrenderしたdenyを維持し、`updatedInput`は返さない
- redaction audit schema driftを推測修復せずauditだけ無効化し、audit read / writeのSQLite lockは10 ms `busy_timeout`でfail-fastしてdenyを維持する
- `cleanup_redaction_audits.py`でevent-scoped auditを既定dry-runし、execute時はforeign key cascadeに依存せずlink、target、planの順で明示削除する
- 保存JSONの正確なUTF-8 byte数 / SHA-256と、boundedなredaction scope / sequence / Post input hash / structure hash / profile / observation statusを、plaintextなしの`event_payload_metadata`へ同一transactionで保存する
- Post confirmationはplan、hash-only sidecarの順に検索し、`events` tableを一切読まず、metadata欠落・不整合・1 MiB超過では未確認にする
- sidecar replayをrecord時点のimmutable observationとして扱い、registry driftで上書きせず、metadata全体のintegrity digestとclosed-world schema制約を検証する
- eligible previewから`enforce / eligible` plan、target exact clone、全findingのversioned BLOCK-to-REDACT decision linkを同一transactionで準備する
- prepare専用connectionだけSQLite foreign key enforcementを有効化し、plan / target / linkをcommit前に再読込してpartial保存をrollbackする
- generic `policy_decisions`を増やさず、decision link欠落・改変をPost terminal replay / compare-and-setより前に全件再証明する
- cleanupをlink、target、planの明示順にし、dry-run / executeで各件数を返す

未実装の大きな部分は、runtime rewriteを安全に有効化するexclusive enforcement gateです。offline publishのatomic境界、Post input hash、O(1) hash-only sidecar、derived redact decision linkageによるdormantな準備・確認経路は実装済みです。複数Hook rewrite競合は現行Codexの一般Hook環境ではHook内から最終rewriteを証明できません。従ってruntime redactを有効化しません。

## グラフ設計の前提

情報流グラフは有向グラフとして扱います。

理由は、情報流には「どこから来て、どこへ行ったか」という向きがあるためです。たとえば次の2つは意味が異なります。

```text
.env -> tool_output -> search_query
search_query -> tool_output -> .env
```

無向グラフにすると、source、経由点、sink の区別が失われ、漏えい検知の根拠を説明できなくなります。

この graph は広い意味ではナレッジグラフと呼べますが、研究上は `information-flow graph` または `provenance graph` と呼ぶ方が正確です。目的は一般的な知識表現ではなく、観測された tool I/O の由来と伝播経路を追跡することだからです。

現時点では動的ナレッジグラフとして複雑な更新モデルを作る必要はありません。event と edge を時系列で保存し、再解析によって lineage を更新できれば、第1段階の MVP として十分です。

実装済みです。

目的は、複数file apply_patchや複数segment Bash commandをtool call全体でtaintせず、operationごとの情報入力と実行後resourceを結び付けることです。

- successful PostToolUse後だけのbounded hash-only capture

完了条件:

- 複数file apply_patchでfile固有fragment以外のresourceへsource lineageを伝播しない

- 成功Postで取得したsnapshot SHA-256がdisk内容と一致する

2026-07-15の現行差分では296 testsを収録し、機能回帰に失敗はない。current full rerunは既存redaction previewの10 ms p95 guardだけが、端末負荷下でmax eligible 20.681 ms、max rejected 18.958 msとなり2 subcase失敗した。WU8追加前のfull 295 testsと追加したread-snapshot test単体は通過しており、WU8機能failureではない。うちredaction audit / decision linkageは59 testsである。単一configured rootの実Codex E2Eでprotected Bash送信のHTTP到達0、public送信の到達1、Stopのclean回答への修正を確認した。一つ前のsize-only sidecarでのMCP再検証ではpublic callがPre / Post各1件、metadata 2件、server call 1件、plan / decision 0件となり、protected callはPre 1件、metadata 1件、Post / server call各0件、`block / critical / external_api_call` 1件、`preview / eligible` 1件のまま停止した。最終hash-only schemaとdecision linkageはruntime配線を増やしていない。実Codex再実行は、既定modelの非互換後、明示modelでもusage limitに達してturn開始前に停止したため、Hook event / server callのない無効試行として除外し、未完了として残す。

最終hash-only sidecarのlocal benchmarkでは、10 MiB rendered oversize confirmationは旧p95 8.01 msから300 sample p95 0.839 msへ低下し、10 MiB no-planはp95 0.789 ms、terminal replayはp95 0.993 ms、new transitionはp95 3.291 msだった。downward-corrupt metadata + 20 MiB event rowはp95 0.477 msで、confirmationは`events` tableを読まない。record時の10 MiB SHA-256はp95 4.175 ms、small / near-32 KiB observerはp95 0.033 / 0.198 ms、paired sidecar + observer overheadはp95 1.350 msだった。no-planとrendered oversizeの単発maxには34.054 / 29.766 msのoutlierがあるため、p95とmaxを混同しない。1,002 prior eventのworkspace session差分解析はp95 104.412 ms、Post Hookは最大case p95 144.381 ms、pure captureは最大case p95 7.217 msだった。32 × 32 KiBのpaired overhead p95は31.010 msで運用warning 35 ms内だが、最適化目標25 msは未達として残す。MCP同値fragment 1,500 call / 3,000 contextsのfull graph回帰では2,998 edges、graph構築23.052 msを確認し、完全DAG化を解消した。derived exact index 4,800 rowsではnewest lookup 1,000回の平均が0.2534 msで、covering index使用をquery planでも確認した。pure redaction plannerは単一target p95 0.0729 ms、32 fields / 32 KiB / 16 target p95 2.9471 ms、最大caseの16件目reject p95 2.6957 msで、10 ms目標内だった。
