## 現在地

開発状況は、次の2層に分けて扱います。

1. **Codex対応は完了**: install、5 Hook、workspace setup、現在セッションのHook到達確認、Hookから見えるlocal toolの実行前block、update / rollback / removeまで、`0.1.0-alpha.12`で一連の動作を確認しました。`0.1.0-alpha.13`で未設定projectを巻き込まない利用対象判定を、`0.1.0-alpha.15`で大きい実運用DBでも操作前判定の時間切れによる素通りを防ぐ境界を、`0.1.0-alpha.18`で保護対象の個別解除と正規のローカル管理操作の自己ブロック防止を公開しました。
2. **ToolUseProxy本体の検出精度は改善中**: protected sourceから外部sinkまでの検出を、より多くのcommand、payload、変換、session境界で正しく行うことが現在の中心課題です。

2026-08-30にはPromptPredictionで、設定済みであっても現在のタスクへPreToolUseが届いた証拠を得られず、protected curlが起動する問題が見つかりました。alpha.12では、設定や過去の成功だけを`active`の根拠にせず、verification command自身のPreToolUse eventをsession、Plugin版、Hook定義hashへ結び付けるよう修正しました。その後の新しいPromptPredictionタスクでは、5件・12チャンクの保護対象を維持したまま、現在セッションへのPreToolUse到達と実行前blockを確認しています。

したがって、Codex integrationやDesktop Phase Bをもう一度作り直すことは、現在の優先事項ではありません。次は実project pilotから検出の誤りと未対応範囲を測り、製品本体を改善します。

## P1: sink-first / lineage比較（Issue #36）

direct lexicalとresolved payloadをbaselineにし、lineageを加えた場合にrecallがどれだけ改善するかを比較します。graphを作ること自体ではなく、検出精度、false block、latency、保存量の改善を完了条件にします。

評価方法は[Sink中心の情報流評価計画](../調査/Sink中心の情報流評価計画.md)と[Sink-first比較評価](Sink-first比較評価.md)を参照してください。

## P1: 外部性とdynamic shell（Issues #54、#24）

既知adapterとbounded static analysisで判定できないcallを、単純なcommand名の列挙へ依存せず分類します。

- Codex network proxyのOTLP eventはevaluation-onlyを維持する
- 実行前callbackとtool-use単位の厳密joinが得られるまではproduction denyへ接続しない
- dynamic shellは、sourceから変数、変数からsinkまでの由来を値非保持で追う
- 判断不能なprotected flowはfail closedを維持しつつ、public callの不必要なblockを減らす
- Externality JudgeはHook外の一時的Codex sessionだけで動かし、自動でallow ruleを昇格しない

## P1: sink payload coverage（Issue #38を含む）

外部性を分類できても、実際に送られるbytesを解決できなければ漏えいを確定できません。bounded resolverを追加し、direct comparisonとの差分を測ります。

優先順:

1. file-backed HTTP payloadとTOCTOU境界
2. Git pushのoutgoing commit / blob
3. archive / upload
4. MCP profileの実schema coverage
5. hosted toolのHook非可視境界

## P2: semantic対応（Issue #46）

local semanticをobserve-onlyで評価します。semantic similarityは候補抽出には使えても、因果的な情報流の証明ではありません。独立評価を終えるまでsemantic-onlyの結果を自動blockへ使いません。

## P2: session・Git境界（Issues #37、#39）

task再開、compaction、subagent、branch、worktree、別cloneで、どのidentityとrevisionを引き継ぐべきかをbounded reconcileとして設計します。alpha.11で追加したprotected-source manifest reconcileと、分析session / Git境界のreconcileは別問題として扱います。

## P3: auditと将来の学習（Issue #55）

実利用ログから精度を改善できる評価基盤を作ります。raw protected valueを学習dataや外部serviceへ送らず、集計可能な構造情報、明示的な人間review、holdout評価を使います。学習結果をそのままallowへ接続しません。

## 維持する安全条件

- protected flowを判断不能なexternal / unknown callへ到達させない
- runtime / policy / schema / bounded analysis失敗をallowへ変換しない
- revision、workspace、receiptの不一致を安全側で拒否する
- raw command、path、host、protected valueをExternality Judgeへ渡さない
- broad reusable permissionやsystem-wide interceptionを要求しない
- Hook内でLLMやnetwork応答を待たない
- LLM verdictからallow ruleを自動作成しない
- 既存adapterやstatic blockを新しい仕組みで弱めない

## release方針

文書、Project、Issueの整理だけではPlugin版を上げません。runtime、Hook、skill、manifestなど配布物が実質的に変わり、clean artifact、CI、必要なDesktop gateを通したときにだけ次のalphaを作ります。

Linux / Windows、hosted tool、任意program、数学的な偽陰性ゼロは、証拠なしに保証へ含めません。

## 現在行わないこと

- Codex integrationやDesktop Phase Bの全面的なやり直し
- direct OpenAI API、API key設定、provider fallback
- Hook内でLLM応答を待つこと
- broad reusable permissionやsystem-wide interception
- LLM verdictからallow ruleを自動作成すること
- Codex network OTLP eventをproduction denyへ接続すること
- runtime redactの有効化
