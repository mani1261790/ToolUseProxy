## 優先順位

### P0: sink-first検査とlineageの有効性を比較する

担当Issue: [#36](https://github.com/mani1261790/ToolUseProxy/issues/36)

最初に、次の4方式を同じversioned corpusとpolicy条件で比較します。

1. sink tool inputへのdirect lexical comparison
2. sink固有adapterで解決した実payloadへのtyped comparison
3. local semantic comparisonをobserve-onlyで追加
4. semantic / resolved payloadへlineage evidenceを追加

評価は `Source × Transformation × Boundary × Sink` で整理し、credential、private prose、source code、Git diff、数値・判断材料を分けます。semantic similarityを因果関係の証明とは呼ばず、semantic-onlyの自動blockは独立validationと人間評価を通るまで有効にしません。

現在地: 独立benchmark foundation、evaluated-only / end-to-end指標の分離、bounded `--data-binary @file` resolver、POSIX component-safe reader、値非保持のpayload evidence契約、production PreToolUseのopt-in shadow観測、別flagのexact-only enforcementまでmainへmerge済みです。v1.1 corpusではdirect end-to-end recall `0.333`に対してresolved recall `0.667`、precision `1.0`、payload resolution 4 / 4、raw fixture exposure 0です。2026-07-27のfile-backed専用TUI shadow Phase Bは`passed`で、`allow->would_allow` / `allow->would_block`各1件、policy block 0件、raw exposure 0件、p95 `0.746 ms`でした。同日のTUI exact-enforcement Phase Bも`passed`で、public side effect 1件、protected side effect 0件、exact policy block 1件、raw exposure 0件、p95 `0.874 ms`でした。enforcementはevaluated resolved-file exact / exact-substringだけをdenyへ昇格し、public / unsupported / semanticは新しいblockを作りません。TUIの明示opt-inは受入基準を満たしましたが、Desktop / GUI、既定有効化、semantic、unsupported、TOCTOUは未検証・未保証です。

### P1: 実network egressでadapter coverageを測る

担当Issue: [#54](https://github.com/mani1261790/ToolUseProxy/issues/54)

Bash adapterのexternal sink判定は既知command patternのallowlistであり、実network接続そのものの観測ではありません。Python / Node.js、raw socket、DNS、custom binary、wrapper経由の偽陰性があり得ますが、現在は実network attemptの分母がないため率を測れていません。

最初はblockを変えず、value-freeな低レイヤー観測とadapter分類をsynthetic corpusで突き合わせます。ここでは「接続をexternalと分類できたか」というexternality recallと、「protected内容を検知できたか」というleakage recallを分離します。TLS payloadとhosted Web Search / MCP内部はlocal process観測だけでは見えないため、unknownとして残します。

詳細は[Network egress観測とAudit改善計画](../調査/NetworkEgress観測とAudit改善計画.md)を正本にします。

### P2: AuditログからMLとrule候補を安全に育てる

担当Issue: [#55](https://github.com/mani1261790/ToolUseProxy/issues/55)

これは強化学習やonline self-learningではありません。値を含まないfeatureと人間labelを使い、active learning、クラスタリング、rule miningでreview順序と未知patternの発見を効率化します。allow eventの無作為sampleも残し、block候補だけを見るselection biasを避けます。

modelの初期用途はreview priority、cluster、rule candidate、offline replayに限定します。候補はversion付きdataset、独立validation、shadow mode、人間reviewを通し、model単独でallow例外やblock規則をproductionへ配信しません。network fact、exact secret match、Git object解析のような決定的判定はMLへ置き換えません。

### P1: 固定artifactをdogfoodする

担当Issue: [#19](https://github.com/mani1261790/ToolUseProxy/issues/19)。protected source onboarding本体の[#18](https://github.com/mani1261790/ToolUseProxy/issues/18)は完了済みです。

manual Phase B用のprepare / verify harnessも実装済みです。最初のhuman runではHook trust、candidate説明、明示approveまでは成功しましたが、Codexのshell環境復元でsystem curlが選ばれ、さらにagentがprotected値を`$TOKEN`として動的展開したため、実行前blockを証明できず`needs_followup`になりました。宛先は合成fixture用の無効domainで送信は成立していませんが、成功扱いにはしていません。

Phase B v2はPATH依存を廃止し、絶対path・mode・SHA-256を固定したfake sink、prepare/run間のCodex version preflight、mode `0600` context、Codex session / Hook DB / markerのcall ID相互照合を追加しました。2026-07-24のfresh human runでpublic callの実行、静的なsynthetic protected callのPreToolUse block、protected side effect 0、candidate / manifest / session / Hook DBの一致はすべて確認できました。

最初の人間評価はHook review理解`no`、proposal説明理解`no`でした。起動前guideとcandidate review cardを追加した次のfresh runではcandidate説明と機能動作を確認できましたが、command承認説明が起動前guideの記憶に依存していました。ユーザーは長い`sh ...`を理解せず承認直前の説明だけでは判断できず、command説明を`no`と評価しました。verifierは引き続き`needs_followup`で、manual Phase Bを完了扱いにしていません。

現在は各command承認を、exact command argumentsから作る自己完結型7項目（実行する操作、目的、読むもの、変更するもの、外部通信、元に戻せるか、承認判断）へ改修中です。また既存harnessのsurfaceを`codex_cli_tui`に限定して結果へ記録します。Codex Desktop / GUIは公式にPlugin利用可能であることと、ToolUseProxyのHook review・command承認・blockが同じUXで動くことを区別し、後者は別のhuman Phase Bが終わるまで未検証です。

### P1: Similarity v2.1をadversarial評価する

担当Issue: [#20](https://github.com/mani1261790/ToolUseProxy/issues/20)

現profileは20文字以上・異なる英字10種類以上の値をdistinctive secretとして扱うため、`documentationreference`のような公開compoundもsource bindingで誤認し得ます。またartifact 50 / source 200のcandidate上限は意図したbounded heuristicであり、両rankingのquota外になる任意のadversarial集合までは保証しません。

1. 長い英字の公開compoundをnegative corpusへ追加する
2. alpha-only secret positiveと同じ形式のhard positiveを維持する
3. global thresholdを安易に緩めず、selectorやsecurity fieldなどsource-binding固有のsignalを比較する
4. 1,000〜10,000候補の生成poolでrecall、saturation率、SQLite parity、p95 latencyを測る
5. developmentで案を固定し、validationとrepository外holdoutを最後に評価する

現在地: 1〜4の基盤、development規則、独立validation family、repository外holdout contractまで実装済みです。公開compoundの偽陽性を導入前baselineで再現し、`selected_security_field`に限ってalpha-only containmentを許可するsource-binding限定規則へ固定しました。freeze後に比較器を変更せずvalidationも全gateを通過しています。10,000候補stressにはhost差を許容する広いoffline p95 warning envelopeを固定し、超過をCI invariantにしました。外部holdout runnerはprivate corpusをrepository外に強制し、aggregate-only public reportだけを生成します。次は実際の非公開corpusを用意してlocal実行し、集約結果だけをIssueへ記録します。

完了条件:

- 新しいpublic compoundを全件TN、alpha-secret hard positiveを全件TPにする
- 既存v2のpair F1、candidate recall、E2E action、parity `1.0`とfalse block `0`を維持する
- full / incremental / SQLiteの候補集合と判断が一致する
