# 現行実装タスク

この文書は、2026-08-22時点の実装順序と完了条件を示す正本です。研究上の理由と評価モデルは[現行研究方針](../研究/現行研究方針.md)、日々の担当と状態は[GitHub Issues](https://github.com/mani1261790/ToolUseProxy/issues)と[Project #1](https://github.com/users/mani1261790/projects/1)を参照してください。

## 現在地

ToolUseProxyはTrace、Detect、Stop、Plugin package、workspace setup、protected sourceの明示承認登録までを実装しています。2026-08-22の実project利用で、alpha.8のfile-backed curl resolverが未対応optionと32 KiB超payloadを`allow`へ落とす問題、および正式公開前の3 Hook artifactが同じalpha.8版番号でcacheされる問題を確認しました。現在のP0はalpha.9でこのfail-openと更新不整合を解消し、fresh Desktopで再検証することです。

実装済みのExternality Protectionは次を含みます。

- 既知adapterとbounded static analysis
- 初見unknownへprotected flowが到達した場合の保守的な実行前deny
- raw valueを持たないlocal classification queue
- jobごとの隔離済み`codex exec --ephemeral` judge
- LLM verdictを自動採用しない人間review
- workspace、revision、完全一致構造で限定したlocal rule
- 既存adapter / static blockを弱めない単調なpolicy

alpha.9の通常setupはlocal static/cache externality判定を有効にし、安全に確認できないHook-visible external payloadを実行前denyします。LLM providerとHook外workerは引き続き既定offです。alpha.8のfresh Desktop合格は当時の限定commandに対する証拠として保持しますが、今回見つかったoption・size回避を覆わないためalpha.9の合格証拠には流用しません。

## P0: alpha.9 fail-closed修正

状態: 実装と自動回帰試験は完了。fresh Desktop release gate待ち。

完了条件:

- `--max-time`等の通常curl optionがfile payload照合を無効化しない
- 未知option、解析例外、payload / source上限超過はallowせず実行前deny
- curl以外の未確認external sinkと未知function toolは、保護sourceがあるworkspaceで安全停止
- PreToolUse runtime / policy failure、未知schema、壊れたHook payloadは値を表示せずdeny
- `setup verify`は`configuration_passed`とruntime証拠を分離し、設定だけで「動作中」と報告しない
- 3 Hookのstale alpha.8から別version alpha.9へ置換し、Plugin dataを保持
- batch protected-source reviewは最大10件のまま維持
- isolated artifactでpublic allow、protected block、runtime evidence、raw exposure 0
- fresh Desktopで5 Hook、設定確認、public allow、option付き／大容量protected block、raw exposure 0

## P0: isolated dogfood

状態: 2026-08-12完了。

合成値とfresh Plugin dataだけを使い、runtime全体をE2Eで確認します。

完了条件:

- public local callが実行される
- public unknown callが止まらず、値非保持queueへ1件だけ入る
- protected unknown callが初回から実行前denyされる
- static externalとprotected flowの組合せが実行前denyされる
- background分類後もruleの自動昇格が0件
- stale revision、別workspace、invalid receiptからruleを採用しない
- approved local ruleが同一unknownだけを解除する
- existing adapter / static blockのdowngradeが0件
- Hook内network、raw command / path / host / protected value exposureが0件
- Hook p50 / p95が設定したbudget内

fresh `0.1.0-alpha.8` artifactとfresh Plugin dataによるrunで全条件が合格しました。初回の10 sample測定はnearest-rank p95がmaxと同値になるため、公開後のmainではprotected unknownの反復を含む20 sample以上へ修正しました。wall-clock latencyは利用者影響の観測値として残し、共有CI runnerの待ち時間に左右されるhard gateは子processのCPU time p95へ分離します。500 msのbudget自体は維持します。Hook network、protected external side effect、raw exposure、自動rule昇格、stale採用、別workspaceへのrule流用はいずれも0件でした。

この合格は合成値を使うisolated gateです。実Codexのcapabilityは別probeで確認済みですが、実projectの分類精度、Desktop UX、Linux / Windowsを証明しません。

手順と段階導入条件は[Externality Protectionロードマップ](ExternalityProtectionRoadmap.md)を参照してください。

## P1: 低riskな実project pilot

状態: 着手可能。利用者による実project利用とvalue-free feedbackを優先する。

isolated dogfood合格後、顧客dataやproduction credentialを含まない複数projectでobserve / block結果を集計します。

測定項目:

- protected unknownの実行前block率
- public unknownのfalse block
- adapter、static、reviewed rule別の寄与
- queue重複排除率と人間review件数
- Hook latency
- raw exposure、workspace混線、stale採用、block downgrade

利用者がraw Hook payloadやSQLiteを読む運用にはしません。分類理由、影響、revisionを一画面で判断できるreview UI / CLIを整備します。

## P1: sink payload coverage

外部性を分類できても、実際に送られるbytesを解決できなければ漏えいを確定できません。sinkごとにbounded resolverを追加し、direct comparisonとの差分を測ります。

優先順:

1. file-backed HTTP payloadの保証境界とTOCTOU
2. Git pushのoutgoing commit / blob
3. archive / upload
4. MCP profileの実schema coverage
5. hosted toolのHook非可視境界

評価方法は[Sink中心の情報流評価計画](../調査/Sink中心の情報流評価計画.md)と[Sink-first比較評価](Sink-first比較評価.md)を参照してください。

## P2: semanticとlineageの追加価値

direct / resolved lexicalをbaselineにし、local semanticとlineageをobserve-onlyで加えます。

進める条件:

- protected valueをremote serviceへ送らない
- semantic-onlyを自動blockへ使わない
- development / validation / repository外holdoutを分離する
- lineage追加によるrecall改善、false positive、latency、保存量を別々に報告する
- 改善しない一般graph処理はruntime優先度を下げる

## 次releaseのgate

alpha.9をpublic channelへ昇格する前に、少なくとも次を満たします。alpha.8の過去合格は今回の回避形を含まないため、alpha.9へ流用しません。

- full pytest、ruff、package artifact、lifecycle、diff checkが合格
- clean artifactからinstall / setup / protect / allow / deny / trace / update / rollback / removeが合格
- fresh Codex Desktop runでpublic allow、protected block、raw exposure 0
- Hook内network 0、LLM verdict自動昇格0、既存block downgrade 0
- macOS実機の結果と文書が一致
- Linux / Windowsの未検証範囲を保証対象に含めない
- 少人数pilotで重大なfalse blockや復旧不能な状態がない

## 現在行わないこと

- Hook内でLLM応答を待つこと
- broad reusable permissionやsystem-wide interception
- LLM verdictからallow ruleを自動作成すること
- Codex network OTLP eventをproduction denyへ接続すること
- runtime redactの有効化
