# 実装タスク計画

ToolUseProxy の次に実装する内容を整理する作業計画です。

現在の研究フェーズは第3段階「情報流出をStopする」の途中です。情報流グラフ、外部sink、final answer sink、最小漏えい検知、policy decision、Stop継続、Bash/MCP PreToolUse denyまで実runtimeへ接続しています。apply_patch/Bashのoperation単位fragmentと、成功PostToolUse後のbounded snapshotも実装しました。次に優先するのは、複数workspace間でsource、cursor、resourceを分離することです。

## 現在の到達点

実装済みの基盤は次の通りです。

- Codex Hooks から `PreToolUse` / `PostToolUse` / `Stop` の payload を受け取る
- Hook payload を event、artifact、artifact fragment として SQLite に保存する
- artifact fragment 間の exact、substring、shingle 類似度から情報流 edge を作る
- JSON container rootとPostToolUse側の複製入力を除外し、session/turn境界内のcanonical fragmentだけを比較する
- protected source を後から graph へ binding する
- source binding を起点に lineage を伝播する
- Filesystem adapter により、ファイル read/write を resource version 経由の edge として表現する
- 実Codexの`apply_patch`をAdd/Update/Delete/Moveへ分解し、成功したPostToolUseだけをresource versionへ反映する
- apply_patchのfile operationごとにadded/control/removed fragmentを分離し、複数file patchの過剰taintを防ぐ
- Bashを静的な`;` / `|` / `&&` / `||` segmentへ分け、cat、redirection、external sinkを該当segmentへ限定する
- Post outcomeをPost event / operation単位の履歴として`succeeded` / `failed` / `unknown`で保存する
- 成功を確認できたPostToolUse後だけ、静的pathをworkspace、byte、path数、時間上限内でsnapshotする
- snapshot本文を既定で保存せず、安定した全file読込のSHA-256、capture status、move/delete tombstoneをresource versionへ接続する
- operation outcomeとsnapshotをsession差分解析へ統合し、稀な重複時も同一sessionだけを再構築する
- Bashの静的な`cat`とredirectionをresource versionへ接続し、protected pathから同一segment内のexternal sinkまで実行前lineageを作る
- Search / Bash / MCP adapter により、外部へ出る可能性があるtool inputを `sink_candidate` として表現する
- Codex final answer adapter により、最終応答を `sink_candidate: final_answer` として表現する
- `trace_lineage.py` と `export_graph.py` により、source から sink candidate までの経路を確認する

未実装の大きな部分は、複数workspaceの分離、`PermissionRequest`接続の必要性評価、tool形状を壊さないredact、MCP server固有分類です。

## グラフ設計の前提

情報流グラフは有向グラフとして扱います。

理由は、情報流には「どこから来て、どこへ行ったか」という向きがあるためです。たとえば次の2つは意味が異なります。

```text
.env -> tool_output -> search_query
search_query -> tool_output -> .env
```

無向グラフにすると、source、経由点、sink の区別が失われ、漏えい検知の根拠を説明できなくなります。

この graph は広い意味ではナレッジグラフと呼べますが、研究上は `information-flow graph` または `provenance graph` と呼ぶ方が正確です。目的は一般的な知識表現ではなく、観測された tool I/O の由来と伝播経路を追跡することだからです。

現時点では動的ナレッジグラフとして複雑な更新モデルを作る必要はありません。event と edge を時系列で保存し、再解析によって lineage を更新できれば、第1段階の MVP として十分です。

### 8. Codex Hook接続

Stop hookの`continue_review`に加え、実payloadを確認済みのBashとMCPを対象に、PreToolUseから`permissionDecision: deny`を返すopt-in接続を追加しました。MCPはmaster gateとは別の追加opt-inを必要とします。どちらも同じsession差分graphを使い、現在eventのsinkだけを評価します。Hookが返したdeny / warn / continue_reviewは`policy_decisions`へ保存します。

Stop / PreToolUse runtimeはsession単位の差分解析を共有します。初回、detector変更、source manifest変更、cursor不整合時だけ同一sessionをfull rebuildし、通常は未処理sequenceのcanonical fragment、adapter edge、source binding、lineageだけを追加します。source設定が変わらない場合はprotected source本文を再読込しません。

目的は、PolicyDecisionをCodex Hookの返却形式へ変換し、実行時のwarn / block / continueに接続することです。

作るもの:

- `hook_monitor/policy/codex_output.py`
- `hook_monitor/policy/explanation.py`
- `hook_monitor/runtime/stop_policy.py`
- `hook_monitor/runtime/pre_tool_policy.py`
- `hook_monitor/runtime/policy_audit.py`
- `scripts/list_policy_decisions.py`
- `PreToolUse` の `permissionDecision: deny`
- `Stop` の `decision: block` による追加確認ターン

完了条件:

- `block` をCodexのhook stdout JSONへ変換できる
- `continue_review` をStop hookの継続指示へ変換できる
- Codexに未サポートの `permissionDecision: ask` へ依存しない
- Hook接続前にoffline policy evaluationで判断を検証できる
- Stop hookで最終応答を記録した直後に `final_answer` の判断を返せる
- Hook reasonで根拠を追えるが、raw protected textは出さない
- Stop hookで返した判断をDBに保存し、decision idで追跡できる
- Bash external sinkを実CodexのPreToolUseで実行前denyできる
- MCP write-like external sinkを実CodexのPreToolUseで実行前denyできる
- deny時にHTTP副作用とPostToolUseが発生しないことを確認できる
- MCP deny時に`tools/call`とPostToolUseが発生しないことを確認できる

残り:

- native Web SearchのHook捕捉手段がCodex側に追加された場合の再評価
- MCP server固有のwrite/read分類fixture追加
- 複数workspace分離後に、`PermissionRequest`の実payloadとPreToolUse denyの役割差を観測し、実接続する必要があるか評価する
- Bash / apply_patch / MCPごとに安全なredactが可能か、書換契約、監査、失敗時fallbackを設計する
- `LeakFinding` と `PolicyDecision` を別テーブルへ分けるか決める

### 9. Operation fragmentとbounded snapshot

実装済みです。

目的は、複数file apply_patchや複数segment Bash commandをtool call全体でtaintせず、operationごとの情報入力と実行後resourceを結び付けることです。

作ったもの:

- `hook_monitor/runtime/operations.py`
- `hook_monitor/runtime/tool_outcome.py`
- `hook_monitor/runtime/snapshot_capture.py`
- `artifact_fragments`のoperation metadata
- `tool_operations`、`tool_operation_outcomes`、`resource_snapshots` table
- `resource_versions`のoperation / snapshot / resource state metadata
- apply_patch file operation fragmentとBash static segment
- successful PostToolUse後だけのbounded hash-only capture
- move/delete tombstone、append lineage、same-path final writer処理
- session incrementalへのoperation outcome / snapshot統合

完了条件:

- 複数file apply_patchでfile固有fragment以外のresourceへsource lineageを伝播しない
- patch文字列hashをfile content hashとして使わない
- 成功Postで取得したsnapshot SHA-256がdisk内容と一致する
- `failed` / `unknown` Postではsnapshotを取得しない
- workspace外、symlink、binary、上限超過、race、I/O failureをstatusで監査できる
- plaintextはopt-inで、既定では`body_text=NULL`
- runtime Hook内でworkspace全体、network、embedding、全DB再解析を行わない
- snapshot capture p95 `< 250 ms`、追加overhead p95 `<= 25 ms`、Post Hook p95 `< 150 ms`を満たす
- session incremental p95 `< 300 ms`を満たす

2026-07-15の実Codex E2Eでは、1回の複数file apply_patchから2 operation / 2 file fragment / 2 hash-only snapshotを作り、それぞれoperation/snapshot-backed resource versionへ接続しました。Bashは2 static segment operationを保存できましたが、Codex CLI `0.142.5`の成功no-output Bashと失敗`false`がともに空文字responseだったため、両者を`unknown / success_unconfirmed`として保存し、Bash snapshotは作成しませんでした。このHook contract制約を成功snapshotとして数えません。

## 次セッションの推奨作業

次セッションでは、次の順で実装します。

1. 複数workspaceのsource / cursor / resource分離を設計・実装する
2. `PermissionRequest`の実payloadとPreToolUse denyとの差を観測し、実接続の必要性を評価する
3. tool形状を壊さないredactの必要条件、監査、fallbackを設計する
4. MCP server固有のwrite/read分類fixtureを追加する
5. ローカルembeddingによる意味類似候補を評価する

Search / Bash / MCP / Codex final answer adapterで作った`sink_candidate`を使う最小漏えい検知、policy判断、Stop継続、Bash/MCP PreToolUse deny、operation fragment、apply_patch snapshotまで動いています。native Web Searchは現行Codex Hookで捕捉できないためoffline adapterに留めています。次はworkspace境界をgraphとcursorの主keyへ昇格させ、そのscopeを前提に`PermissionRequest`、最後に安全なredactを扱います。未サポートの`permissionDecision: ask`には依存しません。
