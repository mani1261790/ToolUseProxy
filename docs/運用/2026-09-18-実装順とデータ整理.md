# 実装順とデータ整理（2026-09-18）

## 実装順

利用者指定の最新版。展示が近いため、画面は自動探索より先に完成させる。

1. **Unsetup（#188）**。指定プロジェクトだけ利用を解除する。履歴削除は別操作。他プロジェクトと元ファイルを維持し、再初期化時の登録の扱いも明示する。判定時間切れ・DB使用中・破損時にも正規のUnsetupを実行できるようにし、通常の外部操作が解除命令を装って通らないことも検証する。
2. **展示画面（#189）**。既存の固定人工試験と記録再生で、情報の移動・停止理由・受信結果を表示する。自動探索に依存させない。再生とライブ、判定と受信事実を区別し、秘密の本文を出さない。実画面と展示手順まで確認する。
3. **自動探索と改善一式（#144 → #130 → #131 → #132、関連#140）**。探索、独立した受信確認、原因調査、再現の短縮、修正、正常操作を含む再検証、Issueへの接続を一組の成果とする。Issue単位でGoalを進めるが、探索だけで全体完成とはしない。試験回数・費用・保存量に上限を設け、本番への自動反映とは分離する。
4. **将来予測（#133〜#138）**。分岐する未来と正解を作り、簡単な方式と比較して複数手の経路予測へ進む。予測記録から開始し、未使用問題で評価した後に試験環境で介入を比較する。
5. **Jev比較（#190）**。上記の後。提供条件・ローカル実行可否を確認し、人工問題で精度・遅延・費用を比較する。実利用ログを外部へ送らない。

容量対策の主要実装・初回整理と今回の手動整理は実施済み。ただし#153/#159の最終実動作確認、自動整理の延期継続、#167の高速化、#169の移行前計画は完了と偽らず残件に置く。展示準備の前提条件から外す。#169は次のDB形式変更前に対応する。展示日は未確定のため架空の期限は設定しない。

クラウド退避は、非公開保存、転送前暗号化、復号鍵の別保管、取り出した内容の一致確認、期限付き保持を要件とする。同期先から消える可能性のある単純なミラー同期は使わない。暗号化しても外部送信なので、送信先の承認と通常のToolUseProxy判定が必要。

## この時点の確認

- 現役DBは読み取り専用のSQLite quick_checkに合格、形式番号12、空きページ0。縮小だけで回収できる空きページはない。
- v11退避も読み取り専用のquick_checkに合格。退避整理用ロックを取得し、対象と残す退避の種類・容量・inodeを再確認してv7退避1個を削除した。削除量3,654,492,160 bytes（約3.65GB）。通常のゴミ箱からは復元できず、v7固有の復旧点は失われる。
- 削除後の専用保存領域はdu表示6.8GiB（約7.3GB）。現役DBとv11退避の残存を確認。OSのスナップショット等がある場合、実際の空き容量増加は遅れることがある。
- 退避管理台帳は直接変更していない。削除済みv7の履歴項目は残るが、製品の退避探索は実在ファイルを対象とし、次回の管理処理で不在項目を整理する。
- rootのprotected_sources.jsonは閲覧・変更・削除していない。

### v7削除の証拠と未記録事項

個別のquick_checkはDB内部の整合性検査であり、現行DBとv11退避の内容一致を
示さない。退避整理契約も両DBの内容一致そのものは要求していない。
この文書に残っている証拠を契約条件ごとに区別する。

| 契約条件 | 記録の状態 |
| --- | --- |
| setup verifyによる新版監視処理への到達 | 削除判断に結び付く記録なし |
| 退避から7日経過 | 削除判断に結び付く記録なし |
| 現行DBの形式とquick_check | 形式12・quick_check合格を記録済み |
| 未確認・変更された退避がない | 全退避についての確認記録なし |
| 削除直前の退避一覧が計画と同一 | 対象と残す退避の種類・容量・inodeの再確認のみ記録。計画との一覧全体の一致は未記録 |

削除済みv7の復旧点が戻ったとは扱わない。今後の退避削除は、上記の全条件の
記録がそろうまで保留する。下記の「ローカル削除可能」はこの条件を満たした
将来の操作を指し、現時点で削除してよいという案内ではない。
