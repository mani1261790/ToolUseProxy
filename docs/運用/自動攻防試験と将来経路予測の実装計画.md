# 自動攻防試験と将来経路予測の実装計画

作成日: 2026-09-06。状態: **段階実装を開始**。

利用者からIssue単位・Goal単位での実装開始の指示を受け、親Issue #126、A01〜A06を#127〜#132、F01〜F06を#133〜#138、通常利用開始の確認を#139として作成した。A01等は文書内の作業番号であり、実際の管理は対応するGitHub Issueで行う。

最初の報告地点は #127 → #128 → #129 → 既存 #112 → 既存 #113 → #139。利用者が通常利用できる状態と残件を#139で報告してから、#130以降の探索・修正の継続運転へ進む。初期の試験範囲と上限は本書の推奨値を採用し、将来予測による自動停止は別の判断とする。

## 1. 何を作るか

目的は、通信するコマンドの名前を増やすことではなく、**保護対象に由来する情報が外へ出る操作を、普通の仕事を邪魔せず止められる範囲を広げること**である。

そのために次の二つを作る。

1. **自動攻防試験**: 偽物の保護情報と試験専用の受信先を用意し、Codexが送り方を考え、試し、止められた結果から別の方法を試す。実際の到達を検出器とは別に確認し、見つかった問題を再現試験と改善提案Issueへつなげる。
2. **将来経路予測**: 今までに観測した操作を基に、「どの保護情報が、何を経由し、何手以内に、どの送信先へ届きそうか」を予測する。まず予測を記録して採点するだけにし、有効性を確認してから停止への利用を別判断する。

例えば「非公開の売上表を読む → 集計ファイルを作る → 要約を保存する → メッセージとして送る」という流れについて、現在の検出は送信操作の直前を守る。追加機能は、集計や保存の時点でその後の経路を予測する。予測が外れても、既存の送信直前の保護は残す。

```text
安全に閉じた試験環境
  └─ 固定の試験 → Codexによる探索 → 再現・比較 → 改善提案Issue
                         │                         └─ 個別修正 → 再試験
                         └─ 正常作業・分岐試行を追加
                              → 将来経路の学習・評価
                              → 製品で予測だけを記録
                              → 効果が確認できた場合だけ早期停止を検討
```

自動化するのは実行、観測、集計、比較、再試行、提案である。未知の全経路の安全性、任意の要約の意味的由来、研究の新規性まで自動的に証明するものではない。

## 3. 確定済みの境界と、今回の提案

### 維持する境界

- root `protected_sources.json`は読み取りによる内容取得も、編集・削除・stage・commitも行わない。試験では専用の設定を新規生成する。
- 未設定の実プロジェクトへ通知・記録・停止を追加しない。研究機能は明示的に有効化した対象だけで動く。
- 実利用の記録、人工試験の記録、予測による推測を混ぜない。今回、過去の実利用記録を一括コピーしない。
- Hook内でLLMや通信の返答を待たない。既存の停止を予測の「安全そう」で解除しない。
- 改善提案は全問題を対象とするが、同種の問題はまとめる。自動Issue作成はコード修正・PR・merge・公開を意味しない。
- GitHubへ実情報、操作本文、実行時のパス、接続先、個別プロジェクト名を載せない。人工試験でも生の実行記録は掲載しない。
- 新しいAPIキー、直接OpenAI API呼び出し、別providerへの自動切り替えを前提にしない。

### 確認したい提案と判断の順序

既に決まった安全条件は再質問しない。残る選択を次の三つにまとめる。

1. **最初の自動試験の広さ**: ファイル・端末操作・HTTP送信までを先に完成させる案を推奨する。Git、独自MCP、保存をまたぐ操作は、同じ基盤へ順に追加する。最初から12〜20種類の道具を実装しない。
2. **予測の初期利用**: 最初の製品導入では、明示的に有効化しても予測の記録だけにする案を推奨する。予測を理由とした自動停止はF06の別判断にする。
3. **自動探索の初期上限**: 同時実行1、1組20試行、各試行10操作、1組30分、保存上限1GiBの小規模運転を推奨する。消費量を確認してから増やす。勝手に無制限の常駐運転へ広げない。

利用者の実装開始指示を受け、基盤はこの推奨値で着手する。モデル構成、学習量、停止基準の詳細は、その前提となる測定結果が出てから決める。後段の不確定事項を理由に前段全体を保留しない。

## 4. 安全な試験環境

### 実行責務を分ける

- **管理役**: 試験の作成、Codexへの問い合わせ、残量管理、実行開始・終了、結果保存を担当する。認証情報はここだけに置く。
- **試験実行側**: 偽物の情報を扱い、試験専用ToolUseProxyを通して道具を実行する。ホストのhome、実プロジェクト、実DB、Docker socket、管理役の認証情報へアクセスできない。
- **試験受信先**: 試験実行側とは別の管理領域に置き、受信を記録する。ここへの送信は「試験上、保護領域から外へ出る操作」と明示的に定義する。
- **独立した観測・保存側**: 通信の試行、受信、Hook到達、設定版を記録する。攻撃役が改ざん・削除できる場所に採点結果を置かない。

試験対象のToolUseProxy本体、Hook定義、試験用の保護対象定義も攻撃役から変更できないようにする。判定器を無効化して送信した結果を「検出精度の穴」に含めない。起動前後の同一性を確認し、境界の破損は試験基盤の異常として扱う。

最初はLinuxの隔離環境を候補とする。ただし、Dockerの内部ネットワーク指定だけを安全性の証明にせず、ホスト接続、DNS、IPv6、転送先変更、代理通信、子プロセスからの出口を確認する。管理された受信先以外への経路を遮断する。許可されない実インターネット送信を試す代わりに、管理下の「到達してはいけない受信先」で遮断を検証する。

モデルとの通信は、管理役の制御用通信として試験送信と分ける。既存のCodex認証を攻撃役のファイルシステムへコピーしない。Codexの道具実行を隔離側へ確実に向ける接続方式はA01で検証する。対応できない場合は固定命令試験まで進め、実モデル探索だけを未対応として報告する。ホスト上での自由実行へ黙って切り替えない。

この制御用通信には人工課題だけを渡し、試験上の流出先には数えない。ホスト側で動く組み込み検索、MCP、関数操作は、実行先を隔離側へ接続できたと確認するまで、探索役には提供せず対象外・観測不能として記録する。端末操作の隔離成功を全Codex操作へ一般化しない。

試験受信先がprivate addressであることと、製品の外部性判定は別である。試験専用の境界設定と製品既定値を分け、試験設定での成功をそのまま実インターネット全般への検出率としない。境界設定を追加する場合、通常利用へ適用されないことも回帰試験する。

### 最初に対象にする脅威

初期の攻撃役は「ToolUseProxyを通る操作で、偽物の保護情報を試験受信先へ届けようとするCodex」である。攻撃役のモデル、道具、上限、見える情報を固定し、版とともに記録する。

信頼できない文書に命令を仕込み、通常作業中の別のCodexを誘導する試験は別の課題群とする。検出器を直接試す攻撃役と、誘導された通常作業役を同じ母集団にしない。OSやコンテナの未知の脆弱性を探す実験は対象外。

## 5. 「何の記録か」と保存形式

保存するものは、実利用の集計とは別の**試験記録**である。「何を試したか」「検出器がどう判断したか」「本当に届いたか」「予測した未来と実行後の結果」を再現・比較するために使う。

人工試験内の命令・出力・偽物の情報は、ローカルの試験専用保存領域に再現用として保持できる。実プロジェクトの情報をここへ流用しない。LLMの非公開な内部思考は取得・保存の前提にせず、観測できる入力、出力、操作、使用量だけを対象にする。

### 共通形式の案

| 記録 | 最小項目 | 用途・制約 |
| --- | --- | --- |
| 試験全体 `run` | `schema_version`, `run_id`, `suite_version`, `detector_revision`, `policy_revision`, `agent_version`, `model_id`, `environment_digest`, `budget`, UTC開始終了時刻 | 後から同条件を特定する。画像・実行物・設定の版も固定する |
| 一回の試行 `attempt` | `attempt_id`, `run_id`, `scenario_family`, `root_case_id`, `mode`, `seed`, `termination_reason` | `mode`は固定再生・適応探索・正常作業を区別する |
| 操作 `step` | `attempt_id`, `step_id`, `sequence_no`, `tool_use_id`, `parent_step_id`, `hook_receipt`, `decision`, `execution_status` | 時刻だけで対応付けない。並行処理は親関係も残す |
| 独立した結果 `outcome` | `network_attempt`, `receiver_arrival`, `protected_arrival`, `task_success`, `evidence_kind`, `evidence_ref`, `coverage`, `unknown_reason` | 二値に押し込めず不明を保持する。正常な送信成功と保護情報到達を分ける |
| 情報物 `object` | 試験内ID、版、種類、元の情報物ID、観測時点 | ファイル名や本文をIDにしない。対応表はローカル限定 |
| 情報の移動 `transfer` | 元・先ID、操作、関係種別、`evidence_kind`、根拠参照 | 確認した移動、内容対応、推定した影響を区別する |
| 予測時点 `prefix` | `prefix_id`, `max_sequence_no`, `snapshot_digest`, 見えている道具・権限、候補操作参照 | 入力を固定し、後から未来の情報が混入しないようにする |
| 続き `continuation` | `prefix_id`, `branch_id`, `policy_mode`, `replay_kind`, 実行結果 | 防御有効・観測専用、固定再生・再生成を区別する |
| 予測 `forecast` | 予測器版、入力版、対象source/sink、手数、候補経路、確率、不明・未列挙の確率量、作成時刻 | 実行済みグラフに予測の辺を書き足さない |
| 介入 `intervention` | 対象操作、適用条件、旧新方針、実行の有無、結果 | F06までは「仮に停止するなら」という採点だけ |
| 問題 `finding` | 原因候補、症状、根拠の確かさ、再現状態、問題キー、観測ごとの送信キー | 問題の同一性と、投稿の重複防止を分離する |

順序番号・実行ID・設定版の不一致、欠落、重複、順序逆転、時刻ずれ、途中終了、移行不能な形式を検出する。未知の形式は既存の結果として取り込まず隔離する。移行はコピーを作って検証し、原本を上書きしない。

実利用DBとは別の保存先とし、追跡するsourceとsinkの対応は試験内で閉じる。実行中は追記記録、完了後は版付きの固定成果物へまとめる。未完了成果物を学習用へ採用しない。容量上限では新規試行を止め、過去の記録を黙って削除しない。

外部共有では、閉じた分類・件数・集計値・公開されたソフトウェアの版だけへ変換する。ローカルID、digest、命令、例外文、モデルの自由記述をそのままIssue本文にしない。

## 6. 正解判定を検出器から独立させる

次の五つは別々に測る。

1. 操作がToolUseProxyへ届いたか。
2. ToolUseProxyが許可したか、停止したか、判断に失敗したか。
3. 道具や子プロセスが実行を始めたか。
4. 通信しようとしたか。試験環境の制限で拒否されたか。
5. 試験受信先へ保護情報が届いたか。正常な作業は終わったか。

「受信ゼロ」だけでは防御成功にしない。モデルが何も試さなかった、通信先が故障した、隔離環境が止めた、観測器が落ちた場合を分ける。事前の正常送信と、試験専用の観測モードでの保護情報送信を対照として確認する。停止を記録したのに届いた場合は、不一致として重大な問題候補にする。

最初に完全自動で採点するのは、直接コピー、既知の可逆変換、ファイル受け渡しなど、独立して由来と到達を確かめられるものだけとする。送信先を所有しているため、TLS暗号化された経路でも受信側の復号後データで到達を確認できる。通信観測だけで本文を判定したとは扱わない。

要約、選択による漏えい、行動への影響は別の根拠区分にする。既知の人工課題で正解を構成できる場合は採点できるが、自由な自然言語変換は別LLMの判断だけで正解を確定しない。わからない中間経路は不明のまま残す。手作業の対象は、このような意味判断や矛盾例に絞る。

## 7. 自動探索・比較・Issue化

### 一組の実行

1. 環境、受信、Hook到達、設定版、残量を確認する。
2. 固定試験を実行し、比較の基準を取る。
3. 攻撃役が新しい操作列を提案し、管理役が範囲と上限を検査して隔離側で実行する。
4. 攻撃役へ許可・停止と制限された結果を返し、次の方法を考えさせる。詳しい検出理由を見せる試験と、判定だけの試験は分ける。
5. 到達、誤停止、観測不足、実行基盤の故障を分類する。同じ方法の繰り返しだけなら、その課題を終了する。
6. 問題候補を新しい試験状態から再現し、余分な操作を減らす。最初は3回の再実行を提案するが、3回成功を一般的な再現保証とはしない。
7. 凍結した旧版と修正版を、同じ固定操作列・同じ課題で比較する。新たな自由探索の結果は別表にする。
8. 全問題をローカルに登録し、内容検査後に同種のIssueへまとめて同期する。

修正版の作成・採用は別Issueの仕事であり、探索プログラムが勝手にコードを書き換えない。固定試験で塞げた後も、別表現・別プログラム・正常作業を用いて狭い当てはめになっていないかを確かめる。

### 止まった後も続けられる実行管理

- 状態を「待ち・実行中・判定待ち・完了・再試行可能な失敗・上限終了・要確認」として保存する。
- 再開時に同じ試行を二重実行せず、実行結果不明の送信は独立した受信記録で照合する。
- 停止・時間切れでは子プロセス群と接続を閉じ、孤立したプロセスが残らないことを確認する。
- 使用量が取れれば記録し、最初は1組100,000 tokenを追加の目安上限とする。送信前に次の要求の余裕も確保する。正確な使用量が取れない接続方式では費用上限を保証したと呼ばず、要求数・時間・操作数で制限する。
- 認証期限切れ、容量不足、モデル拒否、Hook未到達は改善成功と数えない。原因別に処理し、無限再試行しない。
- 最初は明示起動された一組を最後まで自動実行する。定期起動は後から設定し、今回の計画作成では常駐処理やCodexの定期実行を作らない。
- 上限には新しい探索だけでなく、対照試行、再現、短縮、比較も含める。残量不足では残りを保存して終了し、新しい組を自動追加して上限を迂回しない。
- 一組の終了時に、完了・未判定・新しい問題・次の作業を報告する。正常に待っている間の同じ通知は繰り返さない。

## 8. 将来経路予測の設計

### 予測するもの

第一段階は、観測できる操作・情報物・関係を短い列へ変換し、次の操作種別、次の情報物、親となる情報物、移動の種類を予測する。予測した状態からさらに続きを予測し、まず1・2・4操作以内のsource-to-sink到達を出す。8操作、タスクをまたぐ保存、別担当への受け渡しは後段で評価する。

未来の情報物には予測内だけの仮IDを付ける。実行後との比較はファイル名の一致ではなく、種類・親関係・source/sinkとの対応を用いる。辺の確率を独立とみなして掛け合わせず、同じ予測された続きの中で成立した経路から到達確率を集計する。列挙しなかった経路と、判定できない未来の分を明示する。

予測器が動かない場合は「予測なし」であり、安全判定ではない。初期段階の構造予測を、任意の意味的・因果的由来を理解できる機能として説明しない。

### 同じ途中状態から異なる未来を作る

同じ途中状態から、未知の道具出力によって「ローカルで終了」「送信」「保存して後で送信」へ分かれる課題を作る。ただし、**出力が見える前に同じ入力から隠れた分岐を言い当てることは求めない**。出力前は各分岐の分布を予測し、出力が見えた後に予測を適切に更新できるかを測る。

固定するのは観測できる会話、ファイル、道具状態、設定と実行物の版である。Codexのタスク再開だけで環境全体やモデル内部の状態が完全再現できるとはしない。「保存済み操作列の再生」と「同じ観測状態から続きを再生成」を別の再現区分にする。

停止した試行の未来は観測できない。その試行を「流出しなかった安全例」として学習させない。隔離環境内だけで、同じ状態から防御を観測専用にした対照試行を作る。現在の防御下の危険確率と、防御なしの危険確率を別の条件として扱う。

### 学習と評価を汚さない

- 入力は予測時点以前だけ。後から再構築したグラフ、未来の停止理由、受信結果、正解の親IDを入力に混ぜない。
- 同じ元課題・同じ途中状態の分岐・言い換え・短縮版はすべて同じデータ区分へまとめる。行単位のランダム分割はしない。
- 開発用、調整用、最終評価用を分離する。最終評価の結果を見て修正したら、その集合を開発用へ移し、新しい未使用集合を用意する。
- 最初は小規模な人工課題で学習と採点が成立するかを確認し、数百試行で費用・有効率を測る。添付案の5,000〜20,000試行を最初から約束しない。
- 攻撃役の試行だけで「普通に使ったときの流出確率」を学習しない。正常作業、安全に終わる分岐、未知の道具、異なる課題を入れる。
- 探索で見つかった問題の記録と、確率を測るために固定分布から取る評価記録を分ける。攻撃者が意図的に選んだ分岐頻度を、自然な発生頻度と呼ばない。
- 初期学習は人工データに限定する。実利用の原文を外部モデルや学習器へ送る設計変更は今回に含めない。

### 比較する方式

1. 現在のToolUseProxyのみ。
2. 登録した道具と権限から「外へ到達できるか」を保守的に調べる方式。
3. 最近の操作の頻度から次を予測する単純な方式。
4. 経路を出さず、将来の危険度だけを出す学習方式。
5. 次の一手だけを予測する方式。
6. 情報物の由来と複数手先の経路を予測する提案方式。

同じ入力範囲、学習分割、モデル規模・費用条件をそろえる。情報物のID、親関係、複数手の予測を一つずつ外す比較で、どの追加が効いたかを測る。先行研究の論文名を借りた簡易版は「着想を用いた比較」と明記し、著者実装の再現と同一視しない。

### 製品への接続

初期はHook外の処理で予測し、試験または明示的に有効化したプロジェクトに記録するだけとする。追加パッケージ・モデルは通常Pluginへ同梱せず、任意導入の研究用環境へ分ける。現在、評価用パッケージは製品配布から除外され、通常の実行時依存もないため、その境界を保つ。

試験では管理役が保持する人工的な課題・会話を入力候補にできるが、実利用のHookから同じ範囲が見えるとは限らない。予測入力ごとに観測範囲を記録し、実利用で取得できない会話や道具結果を前提とするモデルは、そのまま製品へ接続しない。実利用では構造情報だけでの評価を別に行い、学習時と条件が違えば「適用範囲外」とする。

後に停止へ使う場合も、予測対象のworkspace・session・保護対象版・方針版・観測時点・候補操作が一致する結果だけを扱う。古い予測、計算途中、モデル故障は無効とし、既存の安全判定へ戻す。別タスクの結果を使わない。将来の権限を削る機能がCodex Pluginの接続方式で実現できるかも別途検証する。

## 9. 成功を何で測るか

| 段階 | 測定値 | 合格の考え方 |
| --- | --- | --- |
| 試験基盤 | Hook到達、通信観測、受信の対応率、欠落・重複・改ざん検出 | 固定された対象一式で対応を確定できる。欠落を黙って成功扱いしない |
| 検出改善 | 到達した保護情報、実行前停止、正常作業の不要な停止、正常作業の完了率 | 同じ課題で旧版より改善し、既存の確定した停止・許可を壊さない |
| 自動探索 | 新しい再現可能な問題数、再現率、重複率、1問題あたり試行数・時間・使用量 | 手動で試す工程を減らせる。既知の穴を植えた試験器で探索能力自体も確認する |
| 将来予測 | 到達の適合率・再現率、確率の誤差、未来の辺のF1、上位候補に実経路が入る率 | 単なる危険度予測・一手予測・静的な到達判定との差を示す |
| 早期検知 | 最初の禁止された移動より何操作前に予測できたか | 誤警報率を同じ条件にそろえる。発生後の検出を早期予測に含めない |
| 製品運用 | 予測処理の時間・保存量・Hookへの追加負荷、未設定projectへの影響 | Hook内に重い推論を持ち込まず、未設定では無表示・無記録を維持する |

通信を試みた操作のうち外部性を検出できた割合と、保護情報を実際に送る操作のうち漏えいを検出できた割合は別に計算する。Hookに届かない操作も別集計する。Hook内での成功だけを製品全体の保護率にしない。

F04では正常作業の誤警報率1%・5%を比較候補にするが、数十件から1%を保証しない。必要試料数と信頼区間を先に定め、同一課題の分岐を独立な試料として水増ししない。例えば独立な正常試行300件で誤警報0でも、片側95%上限は約1%であり、それ以上の主張はできない。条件ごとの件数、不明率、課題単位のばらつきを必ず示す。

新方式を採用する条件は、未使用の評価課題で、固定した誤警報条件における早期検知または正常作業の完了に改善があり、経路予測の部品を外すとその利点が減ること。数値目標はF02の基準測定後、F03の学習前に固定する。効果が出ない場合はモデルを本番へ昇格させず、試験基盤と検出改善だけを成果として残す。

## 10. Issue単位の実装順序

親Issueは「自動試験で検出を改善し、将来の流出経路予測を評価する」とする。子Issueは以下の12件を案とし、各1 Goalで進める。A01等は仮番号である。後半の研究は、前半の検出修正を待たせない。

### A01: 隔離実行とCodex接続の成立を確認する

- 依存: 計画の初期範囲・上限の確認。
- 作るもの: 実行方式の比較、試験専用環境の準備確認、Codex認証と道具実行の分離、受信先以外へ出られないことの証拠。
- 候補配置: 新設`research/flow_lab/`の環境定義と、`hook_monitor/evaluation/flow_lab/preflight.py`。
- 完了条件: 偽物だけを読める、管理側を読めない、検出器・Hook・保護対象定義を改ざんできない、Hookが同じ操作に届く、時間切れで子処理を残さない。実モデル接続と道具ごとの隔離は成立・不成立を明示する。
- 不成立時: 固定試験に進める範囲と、追加承認・環境整備が必要な範囲を切り分ける。無制限のホスト実行で代替しない。

### A02: 試験記録と独立した結果形式を作る

- 依存: A01で決まった実行識別と信頼境界。
- 作るもの: 第5節の形式、検証器、追記保存、完了成果物、再開状態。
- 候補配置: 新設`hook_monitor/evaluation/flow_lab/{models,storage,outcomes}.py`と専用tests。
- 完了条件: 重複・欠損・順序逆転・形式違い・途中終了・版違いを人工試験で検出する。実利用DBと初回20件比較に一切混入しない。

### A03: 固定操作で実通信・到達・停止を比較する

- 依存: A02。
- 作るもの: 試験受信器、通信試行の観測器、操作との照合器、固定課題一式。最初はファイル・端末操作・HTTPを対象にする。
- 候補配置: 新設`flow_lab/{receiver,observer,runner,scenarios}.py`。既存`network_egress.py`へ渡す変換は独立ファイルにする。
- 完了条件: 正常送信、保護情報送信、受信故障、環境側拒否、Hook未到達、停止後の到達という各条件を正しく区別する。固定の対象一式では証拠対応の欠落0。
- 既存Issue: #54の観測基盤の一部に証拠を渡す。DNS・任意programなど#54全範囲が終わったとはしない。

### 既存 #112 → #113: 関数操作・端末操作の判断を別々に修正する

- A03の基準試験を得たら優先する。調査と人工的な再現例の作成はそれ以前でも可能。
- 元の実利用Issueの対象を維持する。自動探索の仕組み全体へIssueを拡大しない。
- 完了条件: 当該誤停止の再現、限定した修正、正常な許可と保護情報の停止、alpha.15の時間切れ対策、未設定projectの無表示・無記録を確認する。
- 配布物を変えた場合は第11節の公開・導入条件まで確認する。F01以降の研究完成を待たない。

### A04: Codexが結果を見て次の方法を試す

- 依存: A03、A01の実モデル接続成立。
- 作るもの: 課題提示、構造化した提案、試験実行、結果返却、上限終了、再開。
- 候補配置: 新設`flow_lab/{agent,controller,budget}.py`。
- 完了条件: 人の操作なしで複数試行、拒否後の別案、正常終了、残量不足、認証切れ、モデル拒否、同じ案の反復、途中再開を扱う。試験役が管理権限を要求しても与えない。
- 上限: 第3節の案から開始。実験の終了はGoalの達成と同義ではなく、Issueの完了条件を別に確認する。

### A05: 問題の再現・短縮・旧新版比較を自動化する

- 依存: A03。適応探索との接続はA04後。
- 作るもの: 新しい状態からの再現、余分な操作の削減、固定再生、旧新版比較、恒久的な回帰試験候補。
- 候補配置: 新設`flow_lab/{replay,minimize,compare,findings}.py`。
- 完了条件: 再現しない問題も消さず「未再現」として残す。短縮で原因が変わったら同一としない。受信故障による見かけの改善を検出する。

### A06: 人工試験の問題を自動でIssueへ接続する

- 依存: A05。
- 作るもの: 人工試験専用の外部共有案、内容検査、送信待ち管理、既存Issueとの対応。
- 候補配置: 新設`flow_lab/{proposal,outbox}.py`。既存pilot workerの信頼できる送信部分だけを、回帰試験付きで共用する。
- 完了条件: 未特定・観測不足も提案対象。問題キーを検出器版だけで分割せず、版ごとの観測を同じ問題へ結べる。投稿成功・失敗・結果不明・再送でも重複しない。コード・PR・Project状態を自動変更しない。
- 外部確認: ローカルの疑似GitHub試験と、管理下repositoryでの実投稿を別の証拠として扱う。

### F01: 分岐する未来と独立した経路正解を作る

- 依存: A02・A03。自由探索の記録はA04後に追加する。
- 作るもの: 途中状態の固定、複数の続き、正常作業、対照試行、情報物と既知の派生関係、学習分割。
- 候補配置: 新設`hook_monitor/evaluation/flow_forecast/{dataset,prefix,branches,labels,splits}.py`。
- 完了条件: 見えない未来が入力へ混ざらない。同一途中状態の分岐を別区分へ漏らさない。停止による未観測を安全例にしない。不明な経路を正解として水増ししない。
- 範囲: まず明示的な移動、既知の変換、道具出力による分岐。意味的由来・選択・タスク境界の拡張は別の課題群として件数を示す。

### F02: 簡単な予測方式と採点器を先に作る

- 依存: F01。
- 作るもの: 静的到達、頻度予測、危険度のみ、一手予測の基準、確率・経路・早期検知の採点。
- 候補配置: 新設`flow_forecast/{baselines,metrics,calibration}.py`。
- 完了条件: 既知の確率分岐で採点器を検証する。不明・途中終了・候補にない未来を扱う。最終評価に必要な試料数、費用、採用条件を文書化して凍結する。

### F03: 複数手先の情報物と経路を学習する

- 依存: F02の採用条件と資源見積もり。
- 作るもの: 次の操作・情報物・関係を学ぶ小さなモデル、複数手の予測、確率と予測不能の出力、版固定。
- 候補配置: 新設`research/flow_forecast/`に学習用コードと依存定義。製品から分離する。
- 完了条件: 人工データのみで学習・保存・再読込・固定評価を再現できる。CPU/利用可能な加速器で時間とメモリを測る。モデル構成とライセンスを確定し、通常Pluginに学習依存を追加しない。
- 方針: 小さな操作列モデルから始める。巨大モデル、追加GPU購入、大量試行は測定後の別判断。

### F04: 経路予測を加える価値を未使用問題で検証する

- 依存: F03。
- 作るもの: 第8・9節の比較、部品を外す比較、異なる道具・課題・モデルでの評価、信頼区間、費用表。
- 完了条件: 良い結果だけでなく不利な結果・評価不能も含め、採用条件を満たしたか判定する。既存研究との差は一次文献と実験結果に分ける。
- 分岐: 有効ならF05。無効なら原因をIssue化し、予測停止は導入しない。自動試験と既存検出改善は維持する。

### F05: ToolUseProxyへ予測の記録だけを接続する

- 依存: F04の有効性、運用負荷の確認。
- 作るもの: 任意導入のHook外予測処理、入力版照合、ローカルの説明・結果表示、無効化・復旧。
- 候補配置: 新設の任意機能用workerとCLI。製品側の最小接続位置はA01/F04の結果を基に確定する。
- 完了条件: 判定は変えない。古い入力、モデル不在、DB故障、時間切れ、別タスク、未設定projectを試験する。実際のMac/Codexの同じ実行で追加負荷と既存保護を確認する。
- 注意: ローカルな説明画面へ出す情報と、Issue用集計を分ける。常時通知で通常作業を妨げない。

### F06: 予測による早期停止を試験環境で比較する

- 依存: F05、停止への利用についての明示的な確認。
- 作るもの: 対象操作に結び付いた早期停止、条件不一致時の破棄、緊急無効化、対照試験。
- 完了条件: 既存の停止を解除せず、正常作業の完了率と流出減少を同時に示す。本文の自動書き換え・将来権限の変更は一括導入しない。
- 出口: 本番導入の可否を判断する。F06試験合格だけで、本番の全プロジェクトへ自動有効化しない。

## 11. 段階ごとの完了・公開・報告

### 自動試験基盤の区切り

A01〜A03で固定試験、A04〜A06で適応探索からIssueまでが完成する。A01が成立していないのに「仮想環境で試験できる」と報告しない。固定試験のCIは認証不要・外部接続不要とし、実モデル試験は明示起動の別実行にする。

### 検出修正の区切り

各修正Issueで、局所試験、全体試験、既存安全条件、cleanな配布物、CIを確認する。配布物が変わる場合だけ版を上げる。公開・導入が作業範囲として承認されている段階では、現在のCodexへ導入し、同じ実行のHook到達・許可・停止・未設定の無影響を確かめてから完了する。

Linuxの試験結果はMacの導入確認の代わりにしない。既存の大きなDBでの時間切れ対策を壊さないが、実DBの削除や研究用へのコピーは行わない。環境や認証の不足で外部確認できないときは、実装済みと導入確認済みを明示的に分ける。

### 予測研究の区切り

F01〜F04で研究上の採否を判断する。F05は製品上の観測専用導入、F06は停止への利用を試す別段階である。「モデルが学習できた」「精度が改善した」「本番で有効」「新規研究として成立」は別々の判定とする。

### 進捗管理

- 親Issueは全体の到達目標、子Issueは一つの検証可能な成果とする。既存#112・#113・#54等を重複作成しない。
- 開始時に実在するIssue番号と完了条件を確認し、一つのCodex Goalへ設定する。単なる上限終了や時間切れでGoalを完了にしない。
- 区切りごとに「できたこと・まだできないこと・次のIssue・利用者の操作が必要か」を日本語で報告する。
- 実装完了後も、承認済みの範囲で安全に進められる次の作業が残れば次のIssueへ進む。外部環境や新しい権限が必要なら、必要な操作だけを具体的に伝える。
- Issue #126〜#139は作成・Project登録済み。#127〜#129と既存#112・#113の実装Goalは完了し、現在は#139。人工試験で発見した追加候補は#140へ分離した。公開・導入と後続の継続運転を、コード実装と混同しない。

## 12. 先行研究との関係

添付資料は方向を決める参考として使うが、新規性の確信度や全論文の比較結果を、そのまま確定事実として採用しない。以下は2026-09-06に一次資料の概要を確認した範囲である。

- [ProbGuard / arXiv:2508.00500](https://arxiv.org/abs/2508.00500): 確率的な将来予測に基づく実行時の安全監視。危険確率を出すだけでは差別化にならない。
- [DreamGuard / arXiv:2608.05695](https://arxiv.org/abs/2608.05695): 学習した将来状態を用いる実行時保護。先読みと早期検知自体を新規性としない。
- [SkillGuard / arXiv:2608.30041](https://arxiv.org/abs/2608.30041): 道具の作用の要約を基に、禁止状態への到達を断つ能力制限。可能性の有無と、実際に選ばれそうな経路の分布を分ける。
- [NeuroTaint / arXiv:2604.23374](https://arxiv.org/abs/2604.23374): 実行記録から意味的な伝播を含む由来を事後解析する。推定による監査結果を無条件の正解生成器にしない。

これは全文精査・実装再現・網羅的な新規性調査ではない。同名の研究や改題があるため、以後は名前だけでなく論文ID・版・著者実装の版を固定する。F02〜F04で比較対象の実装可能性を調べる。

狙う研究上の問いは「現在の操作履歴から、まだ存在しない中間の情報物を含む経路を予測すると、危険度だけを予測する場合より早期防御と正常作業の両立が改善するか」である。**相性が良いという設計上の理由と、研究として新しいという主張は分けて検証する**。

## 13. 計画作成時から実装開始への移行

計画作成時には実験・外部変更を行わなかった。その後、利用者の実装指示を受けてIssue作成、Project登録、Goal開始、既存Dockerの起動、試験用コードの実装を開始した。現在の実施結果は[人工試験環境](人工試験環境.md)に記録する。

root `protected_sources.json`の変更、実利用データの移行・学習、認証情報の試験側への移動、予測による本番自動停止は引き続き行わない。定期運転は#139の報告後に扱う。
