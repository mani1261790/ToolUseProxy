# 出力単位の来歴判定

2026-09-23。初回Setup後、返されたログURLを開く操作が `property_graph_incomplete` のまま完了しなかった事例を起点に、判定の対象と証拠の取得方法を変更する。

## 判定するもの

操作全体の挙動、操作が生成した特定の情報、その情報を使う後続操作は別の対象である。ToolCallをノードにすることは維持するが、すべての依存を「前の操作全体」に固定しない。出力の一部分に依存する場合、その観測値の由来を別の不変なリビジョンとして評価する。

部分を選んだだけでは、安全・独立・解析完了にならない。モデルは選ばれた情報の生成に必要な読み取りと変換を評価し、秘密情報源に依存していれば機械的な到達可能性検査で遮断する。出力自身が「秘密は読んでいない」と主張しても、それは証拠として信用しない。

## 必要な証拠

1. 送信しようとしている内容と範囲。既存の送信対象解決・DLPを残す。
2. 依存する観測済み出力。モデルが指定する断片は、保存済み出力に一意に存在することをコントローラーが検証する。曖昧・存在しない断片は採用しない。複数の部分を単一断片で表せないときは操作全体への依存を残す。
3. 資源の識別と観測した世代。プロジェクト内は相対パス、外は絶対パスで表現する。外にあることを理由にアクセスを捨てない。外部ファイルの世代確認はメタデータのみで、内容を一律に読み出さない。
4. 挙動を解釈するための実装定義。モデルは必要なパスと理由を要求し、コントローラーが許可された範囲から読み取り専用・サイズ制限付きで取得する。コードを実行しない。
5. 証拠の時点。Hookで観測した製品ランタイムのコードハッシュと現在の取得内容を照合する。これは境界時点でのコードの観測であり、OSの完全な実行トレースではない。変更があれば過去の実装として扱わない。

証拠取得の範囲はワークスペースと、その呼び出しが明示的に参照する現在の製品ランタイム。任意の絶対パスの内容は取得しない。`protected_sources.json` は対象外。パスの逸脱・シンボリックリンクによる取得範囲の逸脱・特殊ファイルを拒否する。

## 探索と保存

- 全履歴をモデルに順番に再判定させず、対象操作を先に評価し、必要な依存だけを遡る。候補の履歴は省略しない。大きい履歴は既存の全バッチ評価を残す。
- 部分評価と操作全体の評価は別のキャッシュキー・リビジョンを使う。部分評価で操作全体の判定を上書きしない。
- ファイルを経由した同一／別セッションの生産者も、観測した世代の一致に基づいて遡る。
- ポリシーは引き続き登録済み情報源への到達可能性で決める。内容一致によるDLPは別経路として維持する。
- Setup前の未観測の履歴を推測して補わない。記録開始時点の資源はグラフの初期資源であり、未登録の資源を「全履歴が不明だから全て秘密」とは扱わない。記録内の生産者や登録済み情報源へのアクセスは消さない。

## 不足時の動作

モデルの不正な出力には、コントローラーの検証エラーを返して修正を求める。証拠要求には取得結果を返して再評価する。操作は実行しない。

証拠不足でグラフが未完了になった場合、足りないノード・理由・要求・取得結果を保存し、同一Hook内の単なる再試行は打ち切る。通信障害に対する再試行とは区別する。バックグラウンドや明示的な再評価は元のToolCallを実行せず、現在の証拠とポリシーを確認する。

## 検証範囲と限界

出力断片の選択と意味的な依存関係はモデルの推論であり、完全な情報流追跡の証明ではない。メタデータ世代もOSレベルの改ざん耐性を保証しない。取得できない実装、未知の変換、非ファイル資源、履歴外での派生は限界として残る。未判定を許可に変えるフォールバックや、localhost／特定ツール名の無条件許可は追加しない。

Desktopの初回導入から表示までの動作と、送信先での受信有無は、ユニットテスト・モデル単体評価と分けて報告する。

## 実装時の検証

- 実モデルを使った初期の試験では、定義の不足、プロジェクト外の資源を表せないこと、モデルには計算できないハッシュ付きファイル名が、順に未完了の理由として現れた。単に再試行回数を増やさず、資源IDの表現とHook時点のメタデータ観測を追加した。
- `tup-real-setup-review-fpsyn83h` は隔離ディレクトリで実際にSetupを実行し、その実出力を実Codexモデルで評価したもの。ログURLを使う操作は `allow / no_protected_path_observed` まで完了した。Desktopの画面操作そのものの受入試験ではない。
- グラフUIは「出力部分の解析」と「操作全体の解析」を区別し、部分的な判定を全体の解析完了と表示しない。
- `tup-setup-hook-proof-ruz6qbtq` は実Setup・実Hookエントリーポイント・実モデルを通し、Hookの許可応答とビューアHTTP 200を確認した。初回は191秒・同一Hook内2試行だった。これを高速な導入完了とは扱わない。後段が取得した定義を前段に戻す共有を追加し、空の再試行を減らした。DesktopのサイドパネルAPI自体はこの試験の対象外。
- `tup-git-proof-k21e1x_q` は実Codex CLIと実GitHubを使った架空データの受入試験。公開ブランチ `acceptance/7f19571d8b4a/public` は受信、原文と別セッションで作った派生内容のブランチは未受信。派生ファイルを削除した後のGit履歴も `protected_source_reachable` で遮断した。
