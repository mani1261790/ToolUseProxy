## Issueの扱い

- 実装済み、配布済み、実機で確認済み、独立した品質評価済みを分けて記録します。
- デモ3例の成功や人工fixtureの合格だけで、一般的な精度や権限分離の受入を完了にしません。
- 完了条件を満たしたIssueは「完了」として閉じます。
- 旧方式を廃止した課題は、残件の引き継ぎ先を示して「見送り」として閉じます。未検証の項目を実装済みにしません。
- 当時の実測・不足・議論は履歴として残します。現在の扱いを本文冒頭で明示します。
- 将来研究を保留にする場合は、理由と再開条件を書きます。日付の到来だけで自動再開しません。

実装タスクや引き継ぎ文書の長い時系列は過去の記録です。そこにある旧版の「次にやること」を、現在の着手指示として扱わないでください。

## Projectのフィールド

| フィールド | 用途 |
| --- | --- |
| Status | Todo＝未着手、In Progress＝進行中、確認待ち＝実機・採用等の確認待ち、保留＝現在は着手しない、Done＝閉じた項目 |
| 対応区分 | 現行製品、評価・検証、実機確認待ち、研究保留、旧版・履歴 |
| Type | Research、Implementation、Evaluation、Documentation |
| Stage | Trace／Detect／Stopという研究上の由来。現在の優先順位には使わない |
| 旧実装順（履歴） | 過去の着手順を保持する欄。現在の作業順には使わない |

閉じた過去の項目はStatusをDoneにしてアーカイブします。完了と見送りの違いはIssueの終了理由を参照します。アーカイブしてもIssue本文や議論は削除されません。

マイルストーンは「v0.2 検出品質と受入」と「イベント後の研究再検討」を使い分けます。前者に残る過去の完了Issueは、その版における履歴であり、現行版の品質証明ではありません。

## 週次報告

1週間につき1件のIssueを作り、`weekly-report`ラベルを付けます。目標、実施内容、分かったこと、成果物、未解決事項、次の作業、達成状況を記録します。

報告としてまとまったら閉じ、作業の残件は別のIssueで追います。翌週以降に実装が進んでも、当時の報告を最新状態に書き換えません。Projectには全文を転載しません。

## ブランチの整理

- `main`と配布用の`public-alpha`は維持します。
- 未統合のPR、追加コミット、実在する作業中worktreeに使われているブランチは一括削除しません。
- mainへの包含、または同一先端のPRが統合済みであることを確認して不要なブランチを削除します。squash mergeの場合はPRと統合先の履歴を照合します。
- 閉じた旧配布PRのブランチは、後継配布とPRに残る履歴を確認して整理します。
- 消えたworktreeの登録を削除する操作と、実在するディレクトリの削除は区別します。
- ブランチ整理のために利用者データを削除したり、Git履歴を書き換えたりしません。
