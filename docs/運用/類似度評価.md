# 類似度baseline評価

production の閾値やHook挙動を変更する前に、現行実装を固定corpusで測るoffline runnerです。直接構築したpair / graphを測る`similarity/v1`と、実source fileからproductionの入力経路全体を測る`similarity/ingestion/v1`、selector-awareな`similarity/ingestion/v2`、静的Bash送信値まで測る`similarity/ingestion/v3`を分けています。入力は手作業のsynthetic dataだけで、network、subprocessによるtarget実行、remote embeddingを使いません。machine reportにはfixture本文や抽出した送信値を含めず、case ID、label、method、score、件数だけを出します。

## 実行

projectをinstallしたPythonから、リポジトリrootで実行します。

    python -m hook_monitor.evaluation.cli \
      --split development \
      --benchmark-repeats 20 \
      --format text \
      --check

完全なJSON reportを保存する場合:

    python -m hook_monitor.evaluation.cli \
      --split development \
      --format json \
      --output-json /tmp/tooluseproxy-similarity-baseline.json

実source fileとraw Hook eventを通すsource-ingestion評価:

    python -m hook_monitor.evaluation.source_ingestion_cli \
      --split development \
      --format text \
      --check

source-ingestion CLIの既定datasetはv3です。過去baselineを再測定するときだけ、`--dataset tests/fixtures/similarity/ingestion/v1`または`v2`を明示します。

完全なsource-ingestion JSON reportをatomicに保存する場合:

    python -m hook_monitor.evaluation.source_ingestion_cli \
      --split development \
      --format json \
      --output-json /tmp/tooluseproxy-source-ingestion.json

直接pair / graphを測る`hook_monitor.evaluation.cli --check`は従来どおりfull / incremental parityだけを検査します。source-ingestion CLIの品質gateはdataset versionで分けます。v1 / v2は既存baselineとの互換性を保つためparityだけを失敗条件にします。既定のv3はparityに加えて、到達F1、policy action accuracy、false block不在、Bash送信値のcase / segment / value / fallback精度をすべて検査します。

- exit 0: 評価完了し、選択datasetの品質gateを通過
- exit 1: `--check`指定時にparity、またはv3のscored quality metricが不一致
- exit 2: dataset、引数、設定値、出力先などの入力エラー

## 測定層

| 層 | 測るもの | productionとの接続 |
| --- | --- | --- |
| candidate retrieval | raw hash優先と5-gram候補eligibility | artifact 50件、source 200件の現行順位規則をofflineで再現 |
| pair classification | TP / FP / TN / FN、precision / recall / F1、method / score | normalize_text()とcompare_text()を直接使用 |
| E2E | source→sink到達、finding、policy action | full graph、source binding、lineage、leak detection、policyを直接使用 |
| Bash submission extraction | case / segment一致、ordered value precision / recall / F1、fallback accuracy | extract_bash_http_submissions()をproductionと共用 |
| parity | fullとincrementalのedge、全lineage assignment、finding、policy decision一致 | EventStore candidate index、delta source binding、propagate_lineage_incremental()を使用 |
| latency | 現host上のoffline evaluator時間 | runtime SLOではなく比較用。incrementalには一時SQLite初期化を含む |

candidate corpusは各scope 12件で、50 / 200件上限を飽和させません。text reportにもpool sizeと`cap_not_exercised`を表示します。このrecallはpaired lexical eligibilityであり、大規模候補順位の代表値ではありません。上限とtie順序は別の決定的unit testで固定しています。

`similarity/v1`のE2E scenarioはSourceChunkとartifact fragmentを直接構築するため、dotenv / JSONの実chunkingとtool adapter extractionは測定外です。

`similarity/ingestion/v1`はscenarioごとに一時workspaceを作り、次のproduction経路を実行します。

1. source fileと`protected_sources.json`を実ファイルとして配置
2. raw JSONを`parse_hook_payload()`へ渡す
3. event、artifact、fragment、Bash operationを通常の保存経路でSQLiteへ記録
4. 公開入口`update_runtime_analysis()`でsource読込、chunking、adapter、lineageを実行
5. source chunk起点だけに限定してfindingとpolicyを評価
6. 全eventを先に保存するfull実行と、eventごとに解析するincremental実行をsource、chunk、edge、lineage、finding、decision、analysis cursor、Bash submission projectionのsemantic signatureで比較

v3ではこれに加え、target Bash eventからproductionと同じ静的送信値projectionを作り、期待したsegment index、抽出種別、値の順序を照合します。reportには一致件数と不一致IDだけを残し、fixtureの送信値、hash、command本文は出しません。

structured path lineageがsource類似度の失敗を隠さないよう、主指標は`source_node_kind=source_chunk`に限定します。chunkingはprotected valueと完全一致するchunkのrecallと、valueを内包するchunkのrecallを分けて表示します。

## split

- **development**: 方式と閾値の検討に使用
- **validation**: developmentで案を確定した後の比較用
- **all**: corpus/runnerの回帰確認用

validationは同じリポジトリから読めるためblind holdoutではありません。真のholdoutが必要な場合は、リポジトリ外の非公開corpusで管理します。

dotenvのkey、comment、`export`、quote wrapperと、JSONのkey、container、非string scalarはchunkへ含めません。曖昧なdotenv構文と不正JSONは従来のparagraph chunkへ戻し、parser不成立によって保護本文を消しません。chunker versionはruntime source digestとdetector versionへ含め、既存cursorが古いwhole-file chunkを再利用しないようにします。

全12ケースではTP / FP / TN / FNが`6 / 2 / 4 / 0`、F1が`0.857143`、action accuracyが`0.666667`です。残る2 FPは登録されたsecretfile内のpublic sibling value、残る2 missed blockはBash command全体へのsubstring scoreがcritical未満になるケースです。前者はfield / JSON pointer単位のsource selector、後者は送信argument抽出の問題として分け、global thresholdは下げません。

最初のprojectionは、直接実行される`curl`のbody optionだけをquote-awareに静的解析します。対象は`-d VALUE`、`-dVALUE`と、`--data`、`--data-ascii`、`--data-binary`、`--data-raw`、`--data-urlencode`、`--json`、`--form-string`のseparated / `=`形式です。複数値は順序を保ちますが、curlが最終的に組み立てるbody全体は合成しません。抽出値全体がsource chunkと完全一致した場合だけ`bash_submission_exact`の`source_binding`をscore 1.0で追加します。包含一致を1.0へ昇格させず、global thresholdも変更しません。

shell変数、command substitution、glob、brace / tilde展開、unsupported option arity、file / stdin参照の`@file`・`@-`、上限超過は実行も展開もせず、そのcurl segment全体を`coarse_fallback`にします。fallbackでも従来のsegment-level sinkとpath / pipe evidenceは維持します。一つでも不確かなbody候補があれば、そのsegmentの一部だけを確実と誤認せず、抽出値をすべて破棄します。上限は1 segmentあたり32値、1値32 KiB、合計128 KiBです。
