# 類似度baseline評価

production の閾値やHook挙動を変更する前に、現行実装を固定corpusで測るoffline runnerです。直接構築したpair / graphを測る既定の`similarity/v2`、履歴用の`similarity/v1`と、実source fileからproductionの入力経路全体を測る`similarity/ingestion/v1`、selector-awareな`similarity/ingestion/v2`、静的Bash送信値まで測る`similarity/ingestion/v3`を分けています。入力は手作業のsynthetic dataだけで、network、subprocessによるtarget実行、remote embeddingを使いません。machine reportにはfixture本文、個別本文のSHA-256、抽出した送信値を含めず、case ID、label、method、score、件数、corpus全体のdigestだけを出します。

`similarity/v2_1`は独立したschema v3 / dataset 2.1.0です。既定datasetはまだv2のままにし、v2.1のdevelopment ruleとvalidationを固定するまでは明示的な`--dataset tests/fixtures/similarity/v2_1`で実行します。

## 実行

projectをinstallしたPythonから、リポジトリrootで実行します。

    python -m hook_monitor.evaluation.cli \
      --split development \
      --benchmark-repeats 20 \
      --format text \
      --check

現baselineの再現だけでなく、promotion基準も要求する場合:

    python -m hook_monitor.evaluation.cli \
      --split validation \
      --benchmark-repeats 1 \
      --format text \
      --check \
      --require-go

`--check`と`--require-go`は別契約です。前者はdataset digest、split別exact outcome baseline、privacy、cap実行、full / incremental parityを検査します。後者はmanifestに固定したprecision / recall / F1、candidate recall、E2E、family精度、false blockを検査します。分離してあるため実験中は「再現するがpromotion不可」を診断できますが、固定済みv2とCIはdevelopment / validation / allのすべてで両方のPASSを要求します。

完全なJSON reportを保存する場合:

    python -m hook_monitor.evaluation.cli \
      --split development \
      --format json \
      --output-json /tmp/tooluseproxy-similarity-baseline.json

実source fileとraw Hook eventを通すsource-ingestion評価:

    python -m hook_monitor.evaluation.source_ingestion_cli \
      --split development \
      --format text \
      --check

source-ingestion CLIの既定datasetはv3です。過去baselineを再測定するときだけ、`--dataset tests/fixtures/similarity/ingestion/v1`または`v2`を明示します。

完全なsource-ingestion JSON reportをatomicに保存する場合:

    python -m hook_monitor.evaluation.source_ingestion_cli \
      --split development \
      --format json \
      --output-json /tmp/tooluseproxy-source-ingestion.json

protected source候補検出を、production scannerとvalue-freeな公開surfaceで評価する場合:

    python -m hook_monitor.evaluation.protected_source_discovery_cli \
      --split validation \
      --format text \
      --check \
      --require-go

このCLIの既定datasetは`protected_source_discovery/v2`です。`--check`はdataset digest、split別のexact outcome baseline、detector version、scan invariant、privacy非露出を検査し、`--require-go`はprecision / recall、selector精度、hard-positive recall、negative family specificity、候補数を検査します。CIではdevelopment、validation、allを別々に実行します。v1はfixture bytesと旧detector baselineを履歴として固定しており、現detectorの品質gateには使いません。

v2は32 workspace × 13 filesで、developmentとvalidationのpath、selector terminal、宣言語彙を分離し、source shape digestとdetector feature overlapも固定しています。validationは構造的なholdoutですが同じリポジトリ内のsynthetic corpusであり、blindな実データ評価ではありません。値、値のSHA-256、canary、absolute workspace path、内部hash、候補contract外fieldがcandidate surfaceやreportへ出た場合はcheckを失敗させます。

直接pair / graphを測る`hook_monitor.evaluation.cli`は既定で`similarity/v2`を読みます。`--check`は再現性と安全性、`--require-go`は品質promotionを担当します。履歴corpusを現productionで再測定するときだけ`--dataset tests/fixtures/similarity/v1`を明示します。source-ingestion CLIの品質gateはdataset versionで分けます。v1 / v2は既存baselineとの互換性を保つためparityだけを失敗条件にします。既定のv3はparityに加えて、到達F1、policy action accuracy、false block不在、Bash送信値のcase / segment / value / fallback精度をすべて検査します。

- exit 0: 評価完了し、選択datasetの品質gateを通過
- exit 1: `--check`の再現・privacy・parity invariant、または`--require-go`の品質基準が不一致
- exit 2: dataset、引数、設定値、出力先などの入力エラー

## 測定層

| 層 | 測るもの | productionとの接続 |
| --- | --- | --- |
| candidate retrieval | production canonical exact keyとcandidate featureによる候補eligibility | `prepare_similarity_text()`と共通ranking規則を使い、artifact 50件、source 200件の上限とscope別minimum lengthをofflineで再現。candidate集合digest、saturation率、saturated case限定recallも公開 |
| pair classification | TP / FP / TN / FN、precision / recall / F1、method / score | normalize_text()とcompare_text()を直接使用 |
| E2E | source→sink到達、finding、policy action | full graph、source binding、lineage、leak detection、policyを直接使用 |
| Bash submission extraction | case / segment一致、ordered value precision / recall / F1、fallback accuracy | extract_bash_http_submissions()をproductionと共用 |
| parity | fullとincrementalのedge、全lineage assignment、finding、policy decision一致 | EventStore candidate index、delta source binding、propagate_lineage_incremental()を使用 |
| latency | 現host上のoffline evaluator時間 | runtime SLOではなく比較用。incrementalには一時SQLite初期化を含む |

candidate reportは通常recallと別に`saturation_rate`と`gate_saturated.recall`を持つため、cap未実行caseの成功でcap圧力下のmissを隠せません。返却candidate ID集合は本文を含まないdomain-separated SHA-256としてpool単位・scope集約の両方へ残し、同じrecallでも集合が変わるdriftを検出できます。

履歴`similarity/v1`のcandidate corpusは各scope 12件で、50 / 200件上限を飽和させません。text reportにもpool sizeと`cap_not_exercised`を表示します。v2ではartifact 53件、source 203件の独立poolを各splitに置き、pair判定では棄却される長いdecoyが、真の短いcontainmentより大きいraw overlapを持つ圧力を作ります。さらにartifact poolでは、5文字のpair-ineligible候補を49件と50件に変え、真のplural-alias候補が旧coverage順位の50位と51位をまたぐcounterfactualを固定します。source poolでは、pair判定が棄却する同一5文字low-signal候補を199件と201件に変え、長いtoken-equivalent真値が旧coverage順位の200位と202位をまたぐ圧力を作ります。production共通helperはnormalized lengthがartifact 8文字、source 4文字に満たないlexical候補を順位付け前に除外したうえで、coverage優先順とoverlap優先順へ上限を均等配分し、重複・不足分をcoverage全順序でbackfillします。canonical / raw exact候補はこのminimum lengthとlexical上限の外で先に保持します。二系統とも有限上限なので、両順位でquota外になる任意のadversarial集合まで完全保証するものではありません。sourceの3 / 4文字境界は、5-shingle上自然なcap圧力を作れないためadapter unitで固定します。family / counterfactual単位のrecallもreportへ残します。

`similarity/v1`のE2E scenarioはSourceChunkとartifact fragmentを直接構築するため、dotenv / JSONの実chunkingとtool adapter extractionは測定外です。

`similarity/ingestion/v1`はscenarioごとに一時workspaceを作り、次のproduction経路を実行します。

1. source fileと`protected_sources.json`を実ファイルとして配置
2. raw JSONを`parse_hook_payload()`へ渡す
3. event、artifact、fragment、Bash operationを通常の保存経路でSQLiteへ記録
4. 公開入口`update_runtime_analysis()`でsource読込、chunking、adapter、lineageを実行
5. source chunk起点だけに限定してfindingとpolicyを評価
6. 全eventを先に保存するfull実行と、eventごとに解析するincremental実行をsource、chunk、edge、lineage、finding、decision、analysis cursor、Bash submission projectionのsemantic signatureで比較

v3ではこれに加え、target Bash eventからproductionと同じ静的送信値projectionを作り、期待したsegment index、抽出種別、値の順序を照合します。reportには一致件数と不一致IDだけを残し、fixtureの送信値、hash、command本文は出しません。

structured path lineageがsource類似度の失敗を隠さないよう、主指標は`source_node_kind=source_chunk`に限定します。chunkingはprotected valueと完全一致するchunkのrecallと、valueを内包するchunkのrecallを分けて表示します。

## split

- **development**: 方式と閾値の検討に使用
- **validation**: developmentで案を確定した後の比較用
- **all**: corpus/runnerの回帰確認用

validationは同じリポジトリから読めるためblind holdoutではありません。真のholdoutが必要な場合は、リポジトリ外の非公開corpusで管理します。

## v2 evaluation contract

`similarity/v2`はrunner schema / report schemaともにv2です。dataset version registryで許可したmanifest、pair、scenario、retrieval poolだけを読み、development / validation / allのexact outcome baselineを別々に固定します。baselineはTP / FP / TN / FN、candidate取得件数、E2E action件数、parity、privacy件数に加え、case IDと公開結果だけから作る3種類のoutcome digestを含みます。fixture本文や個別本文hashはbaselineへ入れません。

corpusはpair 38件、E2E 9件、candidate pool 16件です。scored pairはdevelopment 19件、validation 17件で、それぞれにGO集計外のsemantic paraphraseを1件残しています。semantic類似を実装済みと扱わず、reportの`all`集計で研究gapだけを可視化するためです。E2Eはdevelopment 5件、validation 4件、candidate poolは各split 8件です。長い英字だけの秘密値をwrapper内で検出するsource-binding pair / E2Eと、同じwrapper内の`password` / `credential`を棄却するcounterfactualも採点します。

英字だけの値は、値全体が単一token、または`api key` / `password` / `access token` / `client secret`直後の値であり、20文字以上かつ異なる英字を10種類以上含む場合だけdistinctiveと扱います。これは辞書を持たないbounded heuristicなので、同じ形を持つ公開compound単語がwrapper内に現れる場合は一致し得ます。多語の条件文はnegative回帰で棄却しますが、公開compoundの追加corpusとsource-binding固有signalは[#20](https://github.com/mani1261790/ToolUseProxy/issues/20)で追跡します。

### v2.1の次実験

最初の基盤sliceでは、v2のcaseと判定結果を保ったまま、全pair / scenario / retrieval poolへ`source_binding_signal`を追加しました。artifact flowは`not_applicable`、source bindingは`registered_source`、`selected_field`、`selected_security_field`のいずれかを必須とし、scopeを跨いだsignalをloaderが拒否します。candidate recipeはv2の最大1,000件を変更せず、v2.1だけ最大10,000件まで許可します。development / validationの双方に1,000、5,000、10,000件の生成poolが存在することと、宣言した最小saturation率をloader contractで検査します。

fixtureは`python -m scripts.build_similarity_v21_fixture`で再生成でき、`--check`でcommitted bytes、shape、baseline、dataset digestの一致を検証します。この段階ではsignalをreportへ出すだけで判定にはまだ使用しません。public compound negativeとalpha-only hard positiveをdevelopmentへ追加し、source-binding限定規則を比較するのが次のsliceです。

v2.1では長い英字public compoundをnegative family、同形式のalpha-only secretをhard-positive familyとしてdevelopment / validationへ独立追加します。global thresholdを反例ごとに緩めず、selectorやsecurity fieldなどsource-binding限定signalを比較します。同時に1,000〜10,000候補の生成poolでartifact 50 / source 200の有限capをstressし、recall、saturation率、SQLite parity、p95 latencyを公開結果として残します。

受入条件は、新しいnegativeが全件TN、hard positiveが全件TP、既存v2のpair F1 / candidate recall / E2E action / parityが全て1.0、false block / privacy exposureが0であることです。repository内validationを見て再調整せず、repository外holdoutは入力本文を公開せず集約結果だけを別に報告します。

development / validationはfamily名だけを変えたmirrorではありません。loaderは次を拒否します。

- pair / candidate / E2E familyのsplit間重複
- typed pairでないcounterfactual、またはsplitごとのgroup数変化
- artifact 51件未満、source 201件未満で上限を実行しないcorpus
- 全scored textに共通するnon-stop marker
- case-specific vocabulary / derived featureのsplit間Jaccard上限超過
- development / validationのstructural shape digest一致またはpin不一致

共通prefixを採点featureにしないため、各caseはfamily固有のsynthetic語彙を使います。security fieldなど比較目的の共通語はoverlap計算のstop tokenから除外します。shape digestは本文hashではなく、layer、scope、label、observe-only、候補数、本文長・token数・文字種件数から作る集約構造hashです。reportはJaccard値とshape digestを公開しますが、元本文を復元できる情報は公開しません。

GO基準は次のとおりです。

| 指標 | 基準 |
| --- | ---: |
| pair precision / recall / F1 | それぞれ 0.90 以上 |
| artifact candidate recall@50 | 0.95 以上 |
| source candidate recall@200 | 0.95 以上 |
| E2E reachability F1 / action accuracy | それぞれ 0.90 以上 |
| scored familyの最小accuracy / recall | 0.80 以上 |
| false block | 0 |
| fixture本文・個別本文hash露出 | 0 |

少数familyでは0.80も実質的に全件成功を要求します。`--require-go`はaggregateだけでなくpair / candidate / E2Eの全scored familyから最小値を取るため、大きいfamilyが小さいadversarial familyの失敗を隠せません。

最初のprojectionは、直接実行される`curl`のbody optionだけをquote-awareに静的解析します。対象は`-d VALUE`、`-dVALUE`と、`--data`、`--data-ascii`、`--data-binary`、`--data-raw`、`--data-urlencode`、`--json`、`--form-string`のseparated / `=`形式です。複数値は順序を保ちますが、curlが最終的に組み立てるbody全体は合成しません。抽出値全体がsource chunkと完全一致した場合だけ`bash_submission_exact`の`source_binding`をscore 1.0で追加します。包含一致を1.0へ昇格させず、global thresholdも変更しません。

shell変数、command substitution、glob、brace / tilde展開、unsupported option arity、file / stdin参照の`@file`・`@-`、上限超過は実行も展開もせず、そのcurl segment全体を`coarse_fallback`にします。fallbackでも従来のsegment-level sinkとpath / pipe evidenceは維持します。一つでも不確かなbody候補があれば、そのsegmentの一部だけを確実と誤認せず、抽出値をすべて破棄します。上限は1 segmentあたり32値、1値32 KiB、合計128 KiBです。
