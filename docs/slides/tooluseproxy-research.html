ToolUseProxy / Product Overview
INTRODUCTION

Product Overview / 2026

AIエージェントは、
何を外へ持ち出したのか。

ToolUseProxyは、個人開発や研究の現場で、エージェントが扱った情報の由来・経路・送信先をローカルに追跡する情報流ガードレールです。

FOR STUDENTS LOCAL-FIRST LINEAGE + SINK-FIRST
この資料でわかること

既存DLPの役割、個人導入が難しい理由、情報流を見る意義、そしてToolUseProxyが採る2つの検知方式。

01 / Existing DLP

大規模DLPは、組織全体の
「機密情報の出口」を管理する

02 / Adoption Gap

しかし、個人開発や研究には
大規模DLPは重すぎる

03 / 13
Enterprise DLP

組織の基盤として運用

管理対象端末、ID、クラウド、分類ルール、監査担当、例外申請までを一体で整備する。広く守れる一方、設計と継続運用が前提になる。

Individual / Research

小さく、すぐ試したい

守りたいのは未公開コード、研究ノート、実験データ。専任管理者や統一された端末管理はなく、導入コストが研究そのものを上回りやすい。

必要なのは、大規模DLPの置き換えではなく、エージェントの作業範囲に絞った軽量な観測と判断です。

03 / Why Information Flow

同じコマンドでも、
流出かどうかは決められない

04 / 13
Case A / Public code

公開済みの修正を送る

git push origin main

公開リポジトリへ、すでに公開可能と判断したコードを送る。通常の開発操作として妥当。

Case B / Private research

未公開情報を含む変更を送る

git push origin main

同じコマンドでも、未発表の研究メモや秘密値が混ざっていれば外部流出になり得る。

操作名だけでは足りない。判断には「何に由来する情報が、どの経路で、どこへ送られたか」が必要です。

04 / Information Flow

見るべきものは、
内容だけでなく「流れ」

05 / 13
Sourceどこから来たか

.env、未公開コード、研究ノート、実験データなど、情報の由来。

Use / Transformどう使われたか

ToolUse、ファイル読込、編集、要約、コマンド生成など、途中の操作。

Sinkどこへ出るか

Git push、外部MCP、HTTP送信、最終回答など、情報が届く出口。

Source → 操作 → Sinkが一本につながったとき、初めて「その送信が危険な理由」を説明できます。

05 / ToolUseProxy

エージェントの外側に置く、
ローカルな観測レイヤー

06 / 13
Core proposition
作業をすべて止めるのではなく、情報の由来と出口をつなぎ、危険な場面だけ説明して介入する。
  • LOCAL解析と記録を手元で行う
  • AGENT-AWAREToolUseと最終回答を同じ流れで観測
  • EXPLAINABLE秘密らしさだけでなく到達経路を提示
  • SELECTIVE記録、再確認、拒否を段階的に選択

Source: README / アーキテクチャ概要

07 / Lineage

Lineage方式：
「なぜ危険か」を経路で示す

08 / 13
01protected source未公開の研究設定を保護対象として登録する。
02ToolUse / file読込、出力、編集をevent・artifact・resourceとして関連付ける。
03external sinkGit pushや外部送信へ経路が到達したかを判定する。
  • WHYその送信が危険な理由
  • HOWどの操作を経由したか
  • WHEREどのsinkへ到達したか

Source: 情報流追跡

08 / Sink-first

Sink-first方式：
「何を送るか」を出口で確かめる

09 / 13
01identify sink外部MCPや送信commandなど、外へ出る操作を見つける。
02extract payloadURL、body、引数、stdinなど、実際の送信部分を取り出す。
03compare secret登録secretとの完全一致・包含・表記差を比較する。
  • DIRECT送信直前のpayloadを直接確認
  • FOCUSED外部sinkだけに検査を絞れる
  • LIMIT未知の変形や未登録情報には弱い

Source: 漏えい検知

09 / Combination

2つを組み合わせると、
判断に根拠が生まれる

10 / 13
比較LineageSink-first
出発点守る情報の由来外へ出るpayload
強み変形や転記を含む経路を説明しやすい実際の送信内容を直接確認できる
弱み観測できない操作では経路が切れる未登録・大きく変形した情報には弱い
組み合わせ「なぜ危険か」を説明「何を送るか」を確認
経路の証拠と出口の証拠が揃うほど、通常操作を誤って止めずに、危険な送信へ絞って介入できます。

10 / Intervention

常に遮断せず、
根拠の強さに合わせて介入する

11 / 13
PostToolUse

記録する

ToolUseとファイル操作を保存し、後から情報流を再構築する。

OBSERVE
Stop

再確認する

最終回答へ危険な経路が届いたとき、値を出さない回答へ作り直す。

REVIEW
PreToolUse

拒否する

外部送信payloadに強い根拠がある場合だけ、実行前に止める。

OPT-IN BLOCK

何を守るかは人が明示承認する。無承認の自動登録、Hook中のworkspace-wide scan、曖昧なruntime書換えは行わない。

11 / Fit & Limits

大規模DLPの代替ではなく、
個人のエージェント作業に絞る

12 / 13
Good fit
  • 未公開コードや研究ノートを扱う学生・研究者
  • ローカルでcoding agentを試す個人開発者
  • どの操作から情報が外へ出たかを説明したい場面
Not a complete DLP
  • 組織全体の端末・メール・クラウドを一括管理しない
  • 未知toolや意味的な言い換えを完全には検知できない
  • ローカル監査データ自体にも適切な管理が必要

Source: SUPPORT.md / PRIVACY.md

12 / Conclusion

個人開発と研究にも、説明できる情報流ガードレールを

ToolUseProxyは、Lineage方式で経路を辿り、Sink-first方式で実際の送信内容を確かめる。大規模DLPを持てない現場でも、AIエージェントを安全に使うための判断材料をつくります。
