# 収集データの容量確認（#204）

F02が要求する最小520群へ各4分岐を保存すると2,080分岐となり、従来の単一Datasetの
2,000分岐上限では保存できなかった。80/10/10のhash splitではtest 400群に対して
総数約4,000群が目安になるため、集約artifactの上限を20,000分岐へ拡張した。
ユニークprefixは従来どおり10,000まで。splitへ渡す前に分岐で共有するprefixを重複排除し、
同じprefixを分岐数だけ数えることを防ぐ。学習済みモデルのroot識別子も最大10,000とする。

これは保存/集計単位の容量であり、試行を追加実行する許可ではない。F02の凍結ファイルと
hashは変更せず、各明示バッチの20試行・1,800秒・1GiB・自動延長禁止を維持する。
artifactの32MiB、研究処理の300秒/1GiB、モデルの64MiB、beam/contextの上限も維持する。
baseline学習の集計中とlogistic optimizerの各epochにもBudget確認を追加し、収集量の
増加で長い学習が制限確認をすり抜けないようにした。

## 明示的なオフライン確認

```sh
PYTHONPATH=.:tests python tests/bench_flow_forecast_capacity.py \
  --roots 4000 --output /private/tmp/tooluseproxy-capacity-NEW
```

新規出力先のみ使う。ネットワーク通信、モデルAPI呼出、人工環境の試行は行わない。
学習・調整・test用の機械的なコピーを作り、保存/再読込、8方式の学習・調整・評価を行う。
前後のアプリ実装hashとprobe/fixtureのhash、各工程時間、保存量、プロセスメモリを記録する。
開始から終了まで300秒/1GiBに収まらない場合は未完了として記録する。

このfixtureはsource_versionとroot名を変えたコピーで、独立研究試料ではない。
機械的な4,000 rootを4,000独立課題と数えず、得られた成績を有効性・採用の証拠にしない。
実課題では観測長やobject数が大きくなるので、同じ件数でも32MiBや学習上限を超え得る。
その場合は上限を自動延長せず、必要な分割保存・評価方法を別途検証する。

## 記録した結果

2026-09-19の実装hash付き確認は、4,000 root・16,000分岐、保存15,176,297 bytesで成功した。
hash分割はtrain 3,182 / calibration 410 / test 408。8方式の学習・調整・評価まで
117.05秒、ピーク193,314,816 bytesで、300秒/1GiB以内だった。
`results/capacity-20260919.json`に当時のソース一覧・hashと工程別の実測を保持する。
これは単一マシン・短い機械的fixtureの結果であり、実課題の所要時間や精度を保証しない。

PR #214のcatalog収集処理との接続確認では、この16,000分岐を同じ機械的設計へ
対応付けるとgrouped_root_countは1となり、independence_verified=falseのままだった。
処理は約10.03秒、ピーク209,223,680 bytes。容量を扱えることと独立試料の数を区別する。
