# 独立課題の収集計画（#204）

F02の凍結条件を変更せず、必要な収集量と記録を準備する。これは収集の実行や
独立性の証明ではない。既存の2課題群やその名前・乱数・文章だけを変えたものを
新しい独立課題として数えない。実利用DB・保護対象・Plugin設定には触れない。

## 収集量と費用の見積もり

別々の課題群として、学習20群、調整用正常100群、未使用test正常300群、
未使用test正例100群、合計520群が最低限必要になる。正常・正例は観測結果で
確定するため、失敗・不明・重複群があれば予定数の試行だけでは満たせない。

次のコマンドは計画JSONを標準出力へ返すだけで、試行・通信・課金を開始しない。

```sh
python3 -m research.flow_forecast.collection_plan \
  --attempts-per-root 4 --controls-per-batch 3 --seconds-per-attempt 60
```

ここで4試行/群、受信対照3試行/バッチ、60秒/試行は説明用の仮定であり、
実測値ではない。この仮定では1バッチ4群、130バッチ、対照を含む2470試行、
逐次実行の推定41時間10分となる。準備・モデル起動・再試行の時間は含まない。
実際に必要なobserve/enforce、継続分岐、生成モデル別の試行数を決めて再計算する。
計画の各区分はバッチを共有せず、rootをバッチの途中で分割しない。

各バッチは最大20試行・1800秒・1GiBで停止し、自動で次のバッチへ延長しない。
時間計算は見積もりであり、実行時のdeadlineを代替しない。容量は事前に測定し、
保存済みデータを保持した総使用量と次バッチの余裕を照合する。1GiBを想定使用量と
扱わない。provider費用と保存量は未測定なのでnullとし、無料や0とは表示しない。
まず1つの有限バッチでトークン使用量・課金単価・経過時間・保存量を記録し、
予算見積もりを更新する。失敗した試行も時間・試行・費用に含める。

## 独立性と生成元の記録

課題ごとに、設計元、課題の目的、必要な道具、情報が渡る関係、正常完了条件、
保護情報の独立した受信確認、関連する既存課題群を記録する。課題の独立性は
IDの違いやモデルの自己申告で確定しない。同一設計・共通prefix・派生課題は
同じ群としてまとめ、分割を跨がせない。重複の判断根拠も残す。

生成実行にはprovider、実際のモデル識別子/版、実行ID、時刻、入力仕様のhash、
応答証跡のhash、関連するtrial ID、費用情報の出典を対応付ける。任意の文字列で
モデル名を埋めたfixtureは実モデル実行の証跡にならない。モデル識別子が
取得できない実行はunknownとして別集計し、モデル間評価の条件を満たさない。

## 未使用評価の維持

課題の設計と関連群を確定してから、学習・調整・testの割当てを固定する。
その後、評価資料と生成元証跡をhash付きmanifestで封印し、調整処理からtestを
参照しない。manifestのhashだけでは未使用性を証明できないため、開封する
実行ID、時刻、参照者、用途、評価器の版、直前のモデルと閾値のhashを記録する。
初回開封後にモデルや閾値を調整した場合、そのtestは退役させ、新しい独立testを
収集する。初回開封を示すファイルを削除して未使用扱いに戻す操作は認めない。

## 実装と証拠の残件

この変更で完了するのは、凍結条件からバッチ数・対照試行・時間仮定を算出する
読み取り専用の計画機能と収集仕様である。生成元証跡と既存trialの実接続、
封印/開封/退役の実装、独立課題の設計・収集、費用の実測、未使用testによる
再評価は未完了。#204、#137、#138をこの計画だけで閉じない。

## 実装済み課題収集経路による再見積もり（2026-09-19）

初期の4試行/群の例は現在のtask-world収集経路に適用しない。
`measured_budget`は指定したcaptureとinterventionsを既存の厳格なreaderで検証し、
同じ計算・入力・実行環境への結合を確認して費用を集計する。共有介入は一度だけ
計上し、同じcaptureの二重指定や読み取り途中で証拠が変わった場合は拒否する。

```sh
python -m research.flow_forecast.measured_budget --inputs PAIRS.json
```

PAIRS.jsonは`[{"capture":"CAPTURE_DIR","interventions":"INTERVENTION_DIR"}]`の形式。
試行の起動や次バッチへの自動移行は行わない。

6課題の12完了バッチでは84試行、記録された経過時間81.70秒、report出力前の
artifact合計854,011bytesだった。全6課題ともenforceが最初の操作で止まったため、
11試行/収集に短縮されている。この所要時間を、正常作業を通す将来の見積もりに
外挿しない。これは選択した完了バッチだけの小計であり、モデル準備・失敗した
過去バッチ・report自体・Docker image等を含む総費用ではない。

1独立課題あたり、収集はobserve/enforce各4操作+各3対照の最大14試行、別の介入
バッチはbaseline+2変更の3試行を確保する。520群をすべて新規収集し、1群あたり
この2バッチで必要な結果が揃うという条件では、1,040明示的バッチ・8,840試行の
予約が必要になる。各180秒のdeadline合計は187,200秒（52時間）だが、これは
準備・生成・解析を含む実行時間の予測ではない。各バッチの上限は20試行/180秒/
1GiBで、F02上限を超えない。1GiBを平均保存量として掛け算しない。

生成計画が初回で成功する仮定では520モデル呼出。独立性不合格、失敗、不明ラベル、
必要な正常/正例数の不足、道具・モデル別の追加実行は増分となる。モデル単価・総保存量・
end-to-end時間は未確定のためnullを維持する。既存6群を独立群として差し引かない。
結果はresults/measured-budget-20260919.json。これは条件付きの計画で、バッチ実行の
承認やF02達成の証拠ではない。
