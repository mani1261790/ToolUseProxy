<h1 align="center">ToolUseProxy</h1>

<p align="center">
  <strong>AIに任せる作業にも、外へ出したくない情報がある。</strong><br>
  Codexのツール操作を記録し、保護情報の送信を実行前に検査するプラグイン。
</p>

<p align="center">
  macOS / Linux · Python 3.11–3.12 · 研究用アルファ版
</p>

**ToolUseProxy**は、AIが作業に使った情報の由来をたどり、外部へ送ろうとする内容が保護対象に由来すると判定した場合に、その操作を止めます。未公開の研究ノートを読むことと、その内容をGitHubへ公開することを区別するための仕組みです。

ここでいう「ツール」は、AIがファイルを読んだり、編集したり、コマンドを実行したりするための機能です。1回の呼び出しを **ToolCall** と呼びます。ToolUseProxyはCodexから届くToolCallの入力・出力を記録し、情報のつながりをグラフにします。

[SecHack365](https://sechack365.nict.go.jp/)で研究・開発しています。

[導入する](QUICKSTART.md) · [仕組みとフローチャート](docs/設計/エッジ生成と送信判定.md) · [対応範囲](SUPPORT.md) · [ドキュメント一覧](docs/索引.md)

## 何を確かめるのか

保護対象として登録したメモを使って作業する場合、次の3つを区別します。

| 送ろうとする内容 | 判定の考え方 |
| --- | --- |
| メモそのもの | 保護内容との一致、または情報源への経路が見つかれば遮断する |
| メモから作った手順書 | 原文と表現が違っても、情報を引き継いだ経路が見つかれば遮断する |
| メモとは無関係な受付案内 | 検査が完了し、一致も保護経路もなければ通常の承認手順へ戻す |

**読んだ後の操作をすべて止めるわけではありません。** モデルが情報の依存関係を推定し、送信時にその経路を機械的に検査します。モデルによる推定には見逃し・誤検出があります。

公開済みの **[v0.2.0-alpha.16](https://github.com/mani1261790/ToolUseProxy/releases/tag/v0.2.0-alpha.16)** では、この3種類のGitHub送信をCodex Desktopの実Hookで確認しました。原文と派生手順書は実行前に遮断され、独立した案内だけが送信されました。[検証条件と記録](docs/運用/alpha16検証.md)を公開しています。この1回の結果は、任意の操作や障害に対する保証ではありません。

## 使い始める

プラグインは公開版を配信する `public-alpha` から導入します。

```sh
codex plugin marketplace add mani1261790/ToolUseProxy --ref public-alpha
codex plugin add tooluseproxy@tooluseproxy
```

導入後、Codexで対象プロジェクトを開いて依頼します。

> このプロジェクトでToolUseProxyを使いたい

初期設定では、**記録した入力・出力や検査に必要な情報を、判定用モデルへ送ること**を確認します。記録はその時点から始まり、過去の作業は取り込みません。ログ画面も開きます。

> research_notes.mdを保護して

指定したファイル全体を登録します。登録だけなら本文の読み取りや送信テストは行いません。初期設定だけで勝手にファイルを保護登録することもありません。

対応環境、更新、権限の確認、解除方法は[クイックスタート](QUICKSTART.md)にまとめています。`main`には配布後の変更も入るため、インストール済みの版は別途確認してください。

## ログとグラフを見る

ログ画面では、呼び出したツール、入力・出力、判定結果をリアルタイムに確認できます。プロジェクトやセッションで絞り込み、遮断された操作だけを表示することもできます。

ログとグラフは同じ画面上部から切り替えます。特定の呼び出しを選んでグラフへ移ると、その判定の来歴を表示します。最新の呼び出しを追っている場合は、グラフも更新されます。明暗はシステム設定に合わせます。

ログ画面が開くこと、Hookが届くこと、実際の送信が遮断されることは、それぞれ別の確認です。

## 仕組み

1. **記録する。** ToolCallの実行前の入力と、実行後の出力をローカルの `events.db` に保存します。
2. **情報の由来を結ぶ。** 観測できたファイルの版や読み書きは機械的に扱い、内容の依存関係は独立した `codex exec` のモデルが推定します。
3. **送信前に検査する。** 入力に明示された外部送信について、送る内容を解決し、内容一致の検査とグラフの経路探索を行います。
4. **根拠を残す。** 保護内容との一致、または現在登録されている情報源への経路があれば遮断します。判定未完了は流出検出とは分けます。

[エッジ生成と送信判定](docs/設計/エッジ生成と送信判定.md)には、処理順、フローチャート、モデルの責任、キャッシュ、ファイルの版、実装箇所をまとめています。[研究方針](docs/研究/現行研究方針.md)では、解決したい問題と未検証の範囲を整理しています。

## 利用前に知っておいてほしいこと

- **すべての通信を監視する製品ではありません。** 対象はHookに届き、入力やツールの仕様に外部送信が明示された操作です。スクリプト内部、Gitのフック、ローカルサービスの転送など、入力に現れない通信は検査対象外です。
- **Hookに届かない操作は遮断できません。** Hosted Web Searchなどへ保護情報や派生内容を入力しないでください。
- **判定はローカルだけでは完結しません。** モデルへ渡す情報やローカルのログには、保護内容が含まれ得ます。[データの扱い](PRIVACY.md)を確認してください。
- **判定不能を安全とは扱いません。** 修復可能な応答や一時障害は再試行しますが、現行版には有限の待機期限があり、判定未完了のまま実行が保留される経路も残っています。これは流出を検出した結果ではなく、未解決の運用上の制限です。

保護登録が0件の場合は、操作を記録して通常の承認手順へ戻ります。内容が公開情報だと判断したわけではありません。任意の変換、未記録の由来、実行直前の差し替えなどの限界は[対応範囲と既知の制限](SUPPORT.md)に記載しています。
